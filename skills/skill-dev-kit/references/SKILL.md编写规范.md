## 一、frontmatter 命名规范

| 字段                    | 官方约束                                                          | 说明                                                                 |
| --------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------ |
| name                  | 1–64 字符；小写字母 / 数字 / 连字符；不以连字符开头或结尾；禁止连续连字符 `--`；**必须与父目录名一致** | 「与目录名一致」「禁连续连字符」两条最易漏，发布前逐条核对；命名取向按「**你做什么**」写（动名词 / 动词优先），见下方命名说明 |
| description           | 1–1024 字符；非空；写 what + when                                    | 1024 是**字段自身**的上限，不是整个 frontmatter 的总计；社区建议 ≤500（写法见 §七）           |
| compatibility（可选）     | ≤500 字符；仅在有环境要求时写                                             | 多数技能不需要                                                            |
| metadata（可选）          | 任意 string→string map                                          | 官方合规的可选字段；但本技能发布链路的 `author` / `version` 必须保顶层，不要挪进子块              |
| allowed-tools（可选，实验性） | 空格分隔的预批工具，如 `Bash(git:*) Bash(jq:*) Read`                     | 安全收敛面：预先收敛可用工具范围；不写则走默认权限                                          |

> ⚠️ 另需遵守：`version` 语义化且与发布 tag 一致；其余平台字段各平台不同（SkillHub 需 slug/displayName/summary；GitHub 需 name/description/version/license）。
> ⚠️ SKILL.md 文件名大小写敏感；技能文件夹内**禁止放 README.md**（避免与发布目录 README 冲突）。
> ⚠️ **`name` 按「你做什么」命名（动名词 / 动词优先）**：`generating-reports` 优于 `report-generator`、`extracting-tables` 优于 `table-extraction`——名字本身就说出动作，读的人不必先猜它是什么名词。动名词形式（`generating-reports`）依然是 kebab-case，与上面的字符约束**不冲突**。**目录名已定时以目录名为准**：「必须与父目录名一致」优先级最高，要改命名就重命名父目录，不靠让两者对不上来迁就。

## 二、五要素与引用纪律

**SKILL.md 五要素（缺一不可）**：① **适用与触发**（先写清什么时候该用、什么时候**不该**，再给覆盖所有说法的触发词）② **分步流程**（可直接照做，含完整命令）③ **依赖清单**（环境要求）④ **边界与安全**（红线：隐私约束、敏感数据不上云、凭证用后即删）⑤ **使用示例**（一次完整对话的模拟流程——缺失会导致审查不过）。

**引用纪律（官方三条）**：① 文件引用一律用**相对路径**；② **保持一层深**（`references/x.md`）——官方理由：嵌套引用会被 `head -100` 预览而读不全，**所有 reference 都应从 SKILL.md 直接可链**；③ 单份 reference **超 100 行加置顶目录**。

**拆不拆文件**：默认**能内联就内联**，不为「结构完整」而拆；官方取向是**先脚本化、再拆散文**。值得拆的只有两种——**重参考**（单个片段 **100+ 行**，或整份文件超 **300 行**；拆出去后**单份只装一个主题**）与**可复用工具**（会被多个流程调用的脚本 / 模板 → `scripts/`）。不足 100 行、只被一个流程用一次、拆出去后正文仍得重复解释它的，**都不拆**。

> ⚠️ **「固定三件套」说的是形状，不是任务清单**——它最大的副作用是诱使作者为凑齐三个目录而把本该内联的内容拆散。官方样本实证：19 个技能里约 12 个没有任何子文件引用（§3.7）。
> **多域技能按 variant 拆**：拆成 `references/<域>.md`，让模型**只读当前这单相关的那一份**——不要写「总索引 + 每个域都点名一遍」，那会让每一单都读全部领域，拆了等于没拆。

## 三、骨架：官方四块最小形 + 本地完整形

> **两套骨架不是二选一**：官方四块骨架是**基准形**（合规、够用、篇幅最小）；本地完整形是**扩写形**（多域 / 长流程 / 需门禁的技能才用）。**先按官方形写下全部内容，只在某一块装不下时才展开**——顺序反了（先摆满标题再填）就是本包反复点名的「把骨架当配额」。

### 3.1 官方四块最小骨架（基准形，先写这个）

> 来源：Agent Skills 官方模板（`template/SKILL.md`）。**逐字全文如下，仅 140 字节 / 6 行**——「最小可用」的实证：frontmatter 只两个字段 + 一行提示。（官方 README 的等价示例即把下面的 `[instructions]` 摊成 `# 技能名` + 正文 + `## Examples` + `## Guidelines`。）

```markdown
---
name: template-skill
description: Replace with description of the skill and when Claude should use it.
---

# Insert instructions below
```

**四块的职责与硬线**：

| 块 | 职责 | 硬线 |
| --- | --- | --- |
| **instructions**（正文首块，可再分 `## Overview` / `## Process` 等具体小节） | 说清「做什么、怎么干、干到什么样算完」 | **必须可执行**：给判断规则与完整命令；**不写论证**（见 §4.7） |
| **`## Examples`** | 给**能跑通的完整示例**（一次真实输入 → 产出） | 数量不是判据、**完整度**才是：一个跑得通的完整示例 ＞ 三个被截断的示例 |
| **`## Guidelines`** | 规则、边界、质量门槛、逃逸条款 | 规则直接给（含「因何而定」一句）；形式按失败类型选（§4.2） |
| **可选块**（`## 常见错误` / `## 速查` / `## Verification Checklist`） | 只在**真有内容**时才加 | **没有就整块删**——为对称而凑节等于注水（⚠️ 这条是本包实战结论，**别冠以「官方」**） |

**官方规格的硬线（一手，可直引）**：① **frontmatter 只要求 `name` + `description`**（≤64 / ≤1024 字符）——其余字段（`version` / `license` / `slug` / `summary`…）都是**目标平台或本包的附加要求**，不是合规前提；② **正文推荐小节**为分步指令 / 输入输出示例 / 常见边界情况（官方用词是「推荐」，不是必须），且**明说无格式限制**——所以四块是**推荐形状**，不是校验规则；③ **正文建议 <500 行、触发后建议 <5k token**（两条官方用词均为 recommended）。

**为什么官方形这么短**：正文是按需加载的执行指令，不是教材。官方样本的构成是「决策树 + 几个可直接跑的代码块 + 一两条坑」，**基本没有「为什么这么做」的段落**（样本对照见 §3.7）。行数参考（来源：社区共识）：极简心态型 30–50 / 工具操作型 200–500 / 流程导向型 150–300 / 哲学+执行型 100–150 / 导航型 20–50。

> ⚠️ **即使用最简的官方形，逃逸条款也必须写**（`## Guidelines` 内一行即可）：与用户明确意图冲突时优先保障用户意图，并显式说明偏离理由——本包红线级纪律，不因骨架变短而豁免（写法见 §3.2）。

### 3.2 本地完整形（扩写形，命中条件才用）

> 命中任一条才展开：① 覆盖多个并列领域 ② 主流程 ≥8 步且有分支 ③ 需发布门禁 / 合规红线 ④ 需要「何时不用」的排他边界。
> ⚠️ 其中的 `version` / `license` / 平台字段**不是官方要求**（官方 frontmatter 只两个字段，见 §3.1）——它们是**本包发布链的要求**（`version` 要与发布 tag 一致，其余按目标平台补）。
> ✅ **已按旧骨架写好的技能不必返工**：四块骨架与旧骨架**向后兼容**——旧骨架的「定位 / 何时用 / 触发词 / Goal / Inputs / Constraints / Steps / Verification」都属 `instructions` 那一块（内部小节名可自由取），只需在下次实质改动时把「使用示例」改题 `## Examples`、把纪律类内容归到 `## Guidelines`。**没有功能影响。**

```markdown
---
name: <skill-name>              # kebab-case，与父目录名一致
description: <做什么 + 何时用>    # 第三人称、无 how、含排他边界（按需）
version: <X.Y.Z>                # 语义化，与发布 tag 一致
license: MIT
---

# <技能名>
<一句话价值主张：把什么变成什么>

## 定位                  <这是什么 / 解决什么问题 / 凭什么用它——三行以内，不写背景故事>
## 何时用（适用 / 不适用）   <用它：症状场景｜不用它：看着像其实该走别的路的场景>
## 触发词                 <说法 1> / <说法 2> / ...
## Goal（可验证输出物）      <落笔前先答「质量条五问」，见 §3.5>
## Inputs（必填 / 可选）     <必填：用户必须提供的｜可选：有默认值或可从环境推断的>
## Constraints           <不做什么 + 质量门槛 + 逃逸条款（冲突时优先用户意图并显式说明偏离）>
## Steps（读取 → 处理 → 验证） 1.输入来源与方式 2.核心逻辑含完整命令 3.验收三件套
## Examples              <一次真实输入 → 产出的完整示例>
## Guidelines            <规则：直接给，含一句「因何而定」｜边界>
## 常见错误（可选）         <什么会搞砸> → <怎么修>       # 只收真实踩过的坑
## 速查（可选）             | <高频操作> | <命令 / 要点> |
```

### 3.3 官方四块 ↔ 本地五要素映射（两套不能各说各话）

| 官方块 | 本地五要素（§二） | 备注 |
| --- | --- | --- |
| **instructions** | ① 适用与触发 ② 分步流程（含完整命令）③ 依赖清单 ④ 边界与安全 | 四要素全在 instructions 内，按读者决策顺序排（见下）；**依赖与边界也可落在 `## Guidelines`** |
| **`## Examples`** | ⑤ 使用示例 | 同义，只是标题按官方叫 `Examples` |
| **`## Guidelines`** | ④ 的规则面（门槛 / 纪律 / 逃逸条款） | 禁令与纪律放这里，不散落在 instructions 中 |

> **自检**：五要素逐条能在骨架里指出落点，指不出来就是缺要素；骨架里出现了映射表之外的新块，先问「它装的是哪条要素」，装不下就删块。

### 3.4 排序与留白（硬线）

- **按读者的决策顺序排**：① 要不要读下去（定位）② 要不要叫它（何时用 + 触发词）③ 怎么干（Goal → Inputs → Constraints → Steps）④ 干完怎么收（Verification → Examples → 常见错误 → 速查）。
- **两条官方额度**：正文**建议 <500 行**、触发后**建议 <5k token**——超了就下沉，不是删内容。
- **骨架是上限不是下限**：官方最小骨架 140 字节 / 6 行同样合规；为对称而凑节只会让正文变长。
- **四块是推荐形状，不是校验规则**——**有了内容才给标题**，为空标题凑内容是本末倒置。
- **`## 决策路径（可选）` 三类之外一律不写**：只在 ① 非显然决策点 ② 流程回路 ③ A vs B 取舍时保留。三类之外各换回本来的形式——参考材料用表格、代码展示用代码块、线性指令用编号列表；`step1` / `helper2` 这类纯编号节点直接删。

### 3.5 Goal 节的质量条五问

写「完成时应交付的具体产物」前必须答得出：① 什么**具体的事情为真**？② 什么**证据**能证明？③ 什么**量化或二值阈值**定义成功？④ 哪些**范围边界**要紧？⑤ 什么情况该**停下来问人**？答不上来就说明目标还停在「活动」层面。

两条纪律：**拒绝纯活动目标**（「make progress」「keep investigating」一律打回，除非锐化成可验证结果：谁、在什么条件下、产出什么、怎么验）；**澄清要有节制**（只在「合理改写可能追错结果」时问**一个**问题，围绕缺失的验证器或范围边界，不要抛五问当访谈）。

### 3.6 六类量化启发式（把目标写成可验证）

按任务类型取量化口径，避免「处理好」这类不可校验的措辞：

| 任务类型 | 量化启发式 |
| --- | --- |
| bug 修复 | 复现优先：先给稳定复现步骤，再谈修 |
| 测试 | 点名确切命令 + 通过条件（哪条命令、看到什么算过） |
| 性能 | 指标 + 阈值 + 测量方法 + 重复次数 |
| 质量 | 可观测的验收条（逐项可勾） |
| 研究 | 决策 + 范围 + 证据标准 |
| 运维 | 健康态 + 监控窗口 + 回滚触发条件 |

### 3.7 样本对照（「写成什么样」的实证）

> ⚠️ **超 100 行的参考文档在顶部加目录**（社区实践；⚠️ **不在官方 specification 正文里**）。建议句式：`> **本文件目录**（社区实践）：<小节 ｜ 小节 ｜ …>`。

**官方仓库 19 个技能**（可直引）：正文 **33–606 行**（中位数落 130–210 区间，**>500 行的有 2 个**）｜**仅 1 个**用 `references/` 目录（内只 1 份）｜旁置文档另有两式（根下 `reference.md`、单数 `reference/`）｜**约 12/19 无子文件引用**。

> **对照数据的 token 口径** = 中文字数 × 1 + 非中文字符数 / 4，剔 frontmatter：官方 `webapp-testing` **894 token / 95 行**（决策树 18 行 + 3 个可跑示例 + 1 条坑 + 4 条最佳实践，**0 份 references**）｜官方 `pdf` 1,878 / 314 行｜**样本中位数 1,878**。

**两条可落地结论**：

1. **官方样本几乎不写论证**——`webapp-testing` 95 行里没有一节在解释「为什么」，规则与动作直接给（这正是「不写论证、只写因何而定」的样本依据，见 §4.7）。
2. **`references/` 是例外不是常态**——取向是**先把确定性的东西拉进 `scripts/`，再把散文拉进旁文件**。**拆不拆看内容，不看目录是否齐全。**

> **另一生态实例**：某 Agent 平台随包预置的技能集中，有一个技能用 `references/` 装 6 份分主题文档——正是「**focused：单份只装一个主题**」的现成样本。

## 四、写作原则（共识）

- **模板模式优于散文**：放 `## Report Template` / `ALWAYS use this structure`，让模型填空而非自由发挥。
- **少而精的示例**：明确边界情况处理方式，「好的示例胜过十条规则」。**数量不是判据、完整度才是**——一个能跑通的完整示例 ＞ 三个被截断的示例；不要为了凑「覆盖面」把同一件事用 5 种不同语言 / 写法各写一遍，那是稀释，不是覆盖。
- **按失败类型选形式（不是一律 MUST/NEVER）**：先给 baseline 失败定性，再决定用禁令、正向配方还是结构化槽位——四行对照表见 §4.2。MUST / NEVER 照旧保留，但**只留给纪律型场景**；它们不是禁忌，是不能乱用。
- **本机绝对路径反模式**：用相对路径或环境变量，禁用本机绝对路径硬编码（形如 `/Users/<账号>/…`，也是脱敏第一道防线）。
- **不给过多库选项**：给默认 + 退路，避免模型在选项间犹豫。
- **「魔数」必须注释理由**：`max_retries = 4  # 指数退避封顶 60s，覆盖 95% 瞬时故障`。
- **别把「何时使用」写进 body**（应放 description）——最高频错误。
- **单技能单职责**，不做「万能指令」。
- **固化必带逃逸条款**：SKILL.md 的 MUST/NEVER 是「可更新指南」而非不可置疑的法律。Constraints 节必须写明：与用户明确意图冲突时优先保障用户意图 + 显式说明偏离理由（防「硬编码铁律不容偏离」——`references/反模式清单.md` #19）。
- **先给任务定型，再决定怎么写指令**：纪律型 / 技法型 / 模式型 / 参考型四型，类型同时决定「指令多硬 + 用什么测试 + 怎么算过」——矩阵见 §4.3。写 Steps 前先定型。
- **面向用户端写作（硬约束）**：SKILL.md 与 README 的读者是**技能的最终使用者**，只写「怎么用」，不写「我们怎么开发的」——版本治理章、实测日期与数据、变更来源与内部动因、维护者指令、商业意图一律不写（详见 §4.1）。
- **不写目标受众、不绑单一平台品牌**：「本技能面向谁」删（定位隐喻可留）；「适配 X 平台」改为能力特征描述（「适用于任意 Agent 对话场景」），避免技能在别的环境里读起来像不适用。

### 4.1 面向用户端写作（硬约束）

> 一句话：**随包对外发布的每一份文本，读者都是技能的最终使用者，不是维护者**——不只 SKILL.md 与 README，**`references/` 与版本档案同样不豁免**。只写「怎么用」，不写「我们怎么开发的」。

**判定问句**：这一行，使用者看了能帮他决定怎么用吗？不能，就删或改写。

**禁写 12 类（开发过程信息，一律删）**——可静态匹配的 5 类另见下方「检查面」：

| 类别 | 典型写法 |
| --- | --- |
| 版本治理章 / 治理口吻 | `## 版本与事实源`、「唯一事实源」「版本口径」 |
| 版本归属标注 | `v1.1.0 新增`、`（v1.2.0）` |
| 变更来源与内部动因 | Changelog 的「来源」列、「因接入 X 而新增」 |
| 实测与过程数据 | 「某月某日实测」「覆盖率 N%→100%」 |
| 内部踩坑表 | `## 踩坑内嵌（经验教训，勿重蹈）` |
| 维护者指令 | 「改动本技能后跑一次…」 |
| 内部商业意图 | 「可作为付费技能上架」 |
| 受众说明 | 「本技能面向…用户」 |
| 单一平台品牌绑定 | 「适配某平台对话场景」 |
| 写作规则自曝 | 「（用户侧口径）」「只写使用者能感知的变化」 |
| 发布状态自曝 | 「未发布」「审核中」「平台版停留在 x.x.x」 |

> 版本档案（Changelog）另算：它既给用户看、又必须说「修好了什么」——**收录判据与写法见 `references/Changelog写作模板.md`**。

**改写三原则**：① 内部动因 → 用户可感知能力（「因接入 X」→「可选：取原文 + 时效性 + 溯源 URL」）② 踩坑 → 结果解读（「哪些现象属已知误报、如何处理」）③ 平台绑定 → 能力特征。

**两类要留**：**能力背书**（「实测坐标零误报」是能力承诺，不是开发过程）；**用户侧操作约束**（退出码语义——但**按工具分列**：评测类的 `2`=REVIEW，`preflight` 的 `2`=参数错误一律阻断，别互抄）。

**检查面（口径即实现，别再复述）**：范围 = 随包对外 markdown（`SKILL.md` / `README` / `references/**` / 版本档案 / 包根其余 `.md`）；**非 `.md` 与 `evals/**` 明示不承诺**；两档判定（第一读者面恒判 / `references/` 深层面按发布面分档）；**豁免只能显式逐文件落盘**（`--waive dev_process@references/<文件名> --reason "..."`，默认口径永远是不豁免）；**词表只静态匹配 5 类**，其余 7 类靠三视角通读——**「脚本没报」不等于「这几类没问题」**（逐项与命令见 `references/脚本速查.md`）。
>
> ⚠️ 本规范自身讲规则、必然引用被禁词，故按上表逐文件豁免；**其余文档不得照抄这些词**。
>
> **写完自检**：全文搜「实测 / 事实源 / 口径 / 覆盖率 / 字符 / 来源列 / 改动本技能 / 付费 / 上架」，命中即逐条复核。

### 4.2 按失败类型选形式（替代「一律 MUST/NEVER」）

**先给失败定性，再选形式**——选错形式不是「不够硬」，而是会反向制造失败：

| 失败形态 | 该用的形式 | 反效果的形式 |
| --- | --- | --- |
| 纪律型：知道规则、有压力时仍违反 | 禁令 + 合理解释 + 红旗清单 | 软指导（prefer / consider） |
| 形状不对：啰嗦、结论被埋、复述需求 | **正向配方 / 契约**：写清产物由哪几部分、按什么顺序 | 禁令清单（「不要复述」） |
| 漏了必备元素 | **结构化槽位**：模板里设 REQUIRED 字段 | 模板旁边的文字提醒 |
| 行为应随条件变化 | **条件式**，绑定可观察谓词 | 无条件规则 + 豁免条款 |

两条硬规则：① **不写含糊从句**（「Don't X unless it matters」会重开谈判）；② **豁免不能限定作用域**——「本限制不适用于代码块」仍会压制代码块，要豁免就**改结构**，别加从句。

> **与 `references/反模式清单.md` #19 的分工（不可互相借用）**：#19 讲的是**元层级**——技能的 MUST/NEVER 与用户明确意图冲突时，优先用户意图并显式留痕；本节讲的是**任务层级**——这条指令本身该怎么写。尤其不能拿 #19 的逃逸条款当「含糊从句」的借口：逃逸条款是**冲突时的出口**，不是措辞可以模糊的许可。

### 4.3 定型 → 怎么测、算不算过

| 类型 | 怎么测 | 成功判据 |
| --- | --- | --- |
| 纪律型（TDD、完成前验证） | 压力场景（时间 / 沉没成本 / 疲劳叠加） | 最大压力下仍守规则 |
| 技法型（条件等待、根因追踪） | 应用 + 变体 + 信息缺失测试 | 能用到新场景 |
| 模式型（降复杂度、信息隐藏） | 识别 + 应用 + 反例 | 知道何时**不该**用 |
| 参考型（API 文档、命令手册） | 检索 + 应用 + 缺口测试 | 找得到且用对 |

**要不要建测试用例**：**客观可验证输出**（文件变换、数据抽取、代码生成、固定流程）→ 建；**主观输出**（写作风格、艺术）→ 常常不建。**别硬给需要人判断的东西套断言**，那只会把评估做成走过场。

> 结构框架选型（minimal / pipeline / tool / knowledge / template / full / suite 七套的命中信号）见 `references/全生命周期 10 步 + 认知底座.md` §4.2。

### 4.4 上下文经济（消费方视角：省着用）

供给侧（把 `--help` 当系统提示写）见 `references/脚本速查.md`；**消费侧**两条配对纪律：

1. **脚本当黑盒**：先 `--help` 再调用，**不读脚本源码**——脚本可能很长，读一遍就污染上下文；只有 `--help` 不足且确需看实现时，才只读相关片段。
2. **禁 `@` 式强制加载**：`@skills/xxx/SKILL.md` 会在真正需要之前强制立即加载；正确做法是**只用名字引用 + 显式要求标记**（如 `**REQUIRED SUB-SKILL:**`），让模型按需自己加载。

### 4.5 术语校准（对协作者，不是对使用者）

§4.1 管**最终使用者**读到什么，本条管**一起开发的协作者**听不听得懂——读者不同，**不得合并**。用词跟**对方的熟悉度**走：**通用档**（「评测」「基准」）可直接用；**专有档**（「JSON」「断言」）**必须先有对方懂这个词的信号**（他上一轮用过，或上下文已出现）。

判据：落笔前自问「对方上一轮用过吗？」答不上来就二选一——**换上位替代词**（「JSON」→「结构化数据文件」）或**先解释再用**。

### 4.6 Gotchas 写法（症状 → 原因 → 修复）

Gotchas 是**回报最高的知识形态**：它给出**识别信号**与**处置动作**，读者不必先理解全部规范才知道自己撞上了什么。每条三行一个单元（**只收真实踩过的坑**，症状必须可观察，一个坑一条不合并）：

```text
症状: 可观察到的现象（读者/模型自己能看见）
原因: 为什么会这样（机制，一句话）
修复: 具体怎么做（可执行动作，不是「请注意」）
```

> 例：`症状` 模糊请求（「帮我看看这份合同」）完全不触发 → `原因` description 只写能力名词、没写用户开口那一刻的处境 → `修复` 改成「在动手审查合同条款之前」这类触发前一刻的表述。更多形态见 `references/反模式清单.md`。

### 4.7 规则要带「因何而定」（与「不写论证」的分界）

**讲「因何而定」一句，不写「为什么这个设计好」**——前者可迁移（规则被推翻时知道该保留哪部分、该连带改哪部分），后者是说服，属论证型内容，不进正文。

- **要写**：一条规则后面跟一句「它是被哪次事故逼出来的」或「不这样会怎样」。入库门槛 = **症状可观察 + 有真实事故或实测反例支撑**。
- **不写**：为某个设计选择辩护、解释它为什么优雅、铺陈背景与动机——**读者要被告知，不需要被说服**（官方样本基本没有这类段落，见 §3.7）。
- **例外**：**纪律型**场景（知道规则、有压力时仍违反）仍用「禁令 + 对照表」（见 §4.2）——那类要压的是压力下的妥协，不是理解缺失。

### 4.8 守恒判据：正文不留会漂的东西

**数值、清单、路径表只要会随项目演进变化，就不该写进正文**——写进去那一刻它就开始腐烂，而腐烂后的数字仍看起来合法。正文只留两样：**去哪个文件读** + **一条当场能跑的命令**。

**为什么必须这样**：这类数字被撞歪后**通常仍在合法范围内**，越界检查抓不到（典型翻车：正文自称「10 类禁令」而表实为 12 类；自称「踩坑表 14 条」而实际 18 条——两处都不像错数字，所以一直没人发现）。

**两个例外**：① **frontmatter 的 `summary` / `description` 不受本条约束**——它们是平台的路由依据，写「16 项检查清单」比写「多项」更能命中用户说法（正文不留计数、frontmatter 留，是有意为之的两套口径）；② **正文出现计数时，必须同句给出核对入口**——做得到的计数等于**带自检钩子的指针**，漂移时会被发现。

**守恒判据（改动时的自检）**：凡「改了 A 必须连带改 B」的地方，都给 B 一个可自动校验的判据——**A 动了，B 的计数必须同步变化；没变就说明有东西被静默跳过**。核对命令必须**只覆盖要数的那一节**（用小节标题作起止锚点）——同一文件里总表与候选池都长 `| N |` 形态，全文计数会得到一个更大的数。

**有条件时**用计划上线的多个模型各跑一遍；**多模型环境不具备时属条件项，不作为发布要求**

## 七、description 编写方法论（触发命门）

> 定位：**description 是技能唯一的触发凭据**——模型通过语义匹配决定是否加载技能。描述写不好，技能等于不存在。

### 7.0 它是「命门」

- description 决定**是否触发**，不决定**执行质量**；执行不一致时查正文指令特异性，而不是改 description。
- **触发阈值**：简单单步任务不触发、复杂多步任务必触发——测出触发率低，九成是「测试指令太简单」。
- **默认是「触发不足」，不是「触发过度」**：真正的风险是压根不触发 ⇒ 描述要**写得能被找到**（inclusive + pushy），宁可先放宽、再按实测收紧。
- **不靠手感，靠实测**：本包口径 = `scripts/eval_trigger.py` **留出集实测优先于手感**（`--check` / `--desc-check` / `--holdout 0.4` / `--reps 3`，见 §7.5）。
- 监控真实使用里的意外触发；把「某 prompt 没触发」补进评估集当新用例。

### 7.1 高精准 description 五策略

| # | 策略 | 做法 |
| --- | --- | --- |
| 1 | **能力标签（名词性）+ 触发场景**双维度 | 动作动词 + 具体文件类型 / 领域 + 场景；**不得写入步骤序列、流程顺序、判定结论**。「提取 PDF 表格转 CSV」远胜「文档处理」；❌「执行计划时逐任务派发子 agent 并在任务间做代码审查」= 把正文 Steps 缩进了 description |
| 2 | 推动性语言 | 加「必须优先触发此技能」类指令——模型默认倾向自己处理简单任务，描述要「略显强势」 |
| 3 | 关键词罗列 | 末尾罗列高频口语说法（「提取表格」「PDF 转 Excel」）。**口语触发词不受 §7.2 规则 1 限制**——「我的订阅 / 我要导出」是关键词罗列，不是自称 |
| 4 | 排他边界（**默认不写**） | 默认**以「包含面」为主**；**只在两种情况加排除句**：① 本技能与另一技能会互相误触发（域重叠）② 目标平台门禁要求。加了就**只排除那一处**。依据：官方仓库 19 个技能**均不写排他边界**（域互不重叠）；社区分析的原话是 "If your skills don't compete, don't add it: you'd only reduce your triggering, the worst flaw of all."（来源：社区共识）。**本包与同类评审技能域重叠 ⇒ 本包该写** |
| 5 | 写「触发前一刻的症状」，且**描述问题而非工具** | 触发时机取用户**还没动手、正要动手**那一瞬的处境；要触发的那件事写**问题本身**，而非某语言 / 工具特有的症状（除非技能本身就是技术特定的）。「在动手写实现之前」远胜「提供实现相关能力」 |

> **为什么不能写步骤**：description 是唯一常驻上下文的内容，正文按需加载。description 一旦把流程与结论说完，正文就失去被读取的理由——技能退化成一行 prompt。

### 7.2 三条硬性规则

1. **必须非自称构式**：禁止「I can / 我可以 / 本助手…」等技能自称的表述；**用户口语触发词中的「我的 / 我要」属 §7.1 策略 3 的关键词罗列，不受此限**。
   
   > ⚠️ 判语义属性不能只看字符表面形式：按单字匹配会把用户口语触发词误判为违规，判定必须给到「自称构式」这一层语义形态。
2. **只写「做什么 + 何时用」**，把「怎么做」留给正文——description 试图解释 how 是高频错误。
3. **泛泛描述必死**：「Helps with documents」触发条件过宽，会在错误时机激活或从不激活。

### 7.3 触发机制要点（与正文的分工）

- description 只管触发 → 触发信息只放 description；**「何时使用此技能」写进 body 是最高频错误**。
- 正文负责执行质量 → 触发正确但执行不一致，改正文：先按 §4.2 给失败定性再选形式（禁令 / 配方 / 结构化槽位），而不是一律加 MUST/NEVER。
- 触发词章节（SKILL.md 正文）与 description 互补：description 供语义匹配，触发词章节供人工/脚本检视，两者需同步维护。

### 7.4 正反例与自检

| 反例 | 问题 | 正例 |
| --- | --- | --- |
| Helps with documents. | 泛泛，无功能无场景 | Extracts tables from PDF documents and converts them to CSV for spreadsheet analysis. |
| I can help you create Word documents. | 自称 + 只有动作无场景 | Creates professionally formatted Word documents with tracked revisions for legal review. MUST trigger on 合同 / 修订 / 法律文档. |
| 这个技能可以处理文档。 | 无动作动词、无文件类型、无场景 | 从 PDF / 图片提取表格并转为可编辑 CSV；用户说「提取表格」「PDF 转 Excel」时必须优先触发。不用于文档排版。 |

**写完逐条过**：无自称构式？（口语「我的 / 我要」不算）｜有动作动词？｜有具体对象（文件类型 / 领域 / 数据形态）？｜有场景 / 触发时机？｜无 how 描述？｜末尾有口语触发词？｜排他边界按需（§7.1 策略 4）？｜把 description 单独读一遍，是否泄露了「先做什么再做什么」——是则删。

### 7.5 与工具链的衔接

| 命令 | 用途与判据 |
| --- | --- |
| `--check` | 校验「## 触发词」章节覆盖率（阈值默认 0.7）。**判定基准必须由技能自己提供**（`--intents <file>` 或 `evals/trigger_eval.json`）；两者都没有时输出 **REVIEW（2）不判 FAIL**——没有评估集不等于写得不合格。先 `--gen` 出模板、替成本技能真实说法再判 |
| `--desc-check` | 静态校验 §7.4 自检清单各项：**FAIL 级 2 项**（自称构式 / 无动作动词，命中即不合格）；**WARN 级 5 项**（缺场景 / 含 how / 缺排他边界 / 缺触发词示例 / 含流程摘要），默认只提示、`--strict` 才计入失败。域外场景词用 `--scene-words <file>` 注入，**不判 FAIL** |
| `--holdout <比例>` | **推荐 0.4**：按固定种子确定性切分训练 / 留出集，**判定以留出集覆盖率为准**（防过拟合）；留出集不足 2 条降级 REVIEW |
| `--reps <次数>` | **推荐 3**：重复 N 次独立切分，报留出集覆盖率的**均值 ± 标准差**。标准差大 = **评估集切分不稳** ⇒ 扩量补真实说法，不是继续调措辞。⚠️ 它衡量的是**切分稳定性，不是模型随机性**（后者需真实调用通道，当前未实现） |

> 命令均属 `scripts/eval_trigger.py`；完整命令 / 退出码 / CI 接入见 `references/脚本速查.md`。「关键词罗列」不受「含流程摘要」影响——口语触发词（「我的订阅」「我要导出」）照旧豁免。

## 八、改动已有技能：先判状态，再选改造方式

| 当前状态 | 改造方式 | 为什么 |
| --- | --- | --- |
| **已发布的稳定技能**（线上在用、有存量用户） | **最小侵入 patch**：前置 hook + 覆盖优先于重构 | 用户正在跑，重构会一次翻动所有行为面，回归面不可控 |
| **开发中的新技能**（未发布、无存量） | **一次性批量重构** | 没有存量要护，逐个修补只会留下新旧两套写法并存的中间态 |

> ⚠️ 判定顺序不能反：不要因为「重构更干净」就对已发布技能动刀。**干净是开发期价值，稳定是线上期价值**，冲突时后者优先。

**patch 三条纪律**：① **前置 hook 优先**（能拦截/改写就不动主流程）② **覆盖优先于重构**（加一条例外规则 ＞ 改原条目，diff 一眼能审完）③ **一次只解决一类问题**（别在「修触发词」的 patch 里顺手改 Steps，回归会失去归因）。

**命中任一转批量重构**：同文件已累积 ≥3 处互相有交互的 patch；缺陷是**结构性**的（frontmatter 不满足平台新规范、章节划分本身错）；新旧两套写法已并存。

**验收**：patch 的 diff 应能一句话说清「改了什么、影响哪个行为面」；说不清说明改大了，退回重构。批量重构的独有风险是**静默丢内容**（章节合并漏一节、区间替换删掉夹在中间的段落）——三件套是：术语逐项断言（**清单从原文逐项抄，不凭记忆写**）+ 代码块特征行原样命中 + 逐节关键词断言；命中不了不等于丢失，按「实现迁移进脚本 / 标题重命名」逐条复核放行。**配套两条**：动手前先说清可逆性来源（git / 本地副本 / trace）；**结构重排与内容修改分两次做**，混在一起零丢失校验会把有意的修改报成丢失（可跑的校验脚本与判据表见 `references/发布检查清单.md` 与 `references/反模式清单.md`）。
