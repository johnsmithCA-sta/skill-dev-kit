# 知识产权边界与护城河判定

> **本文件目录**（社区实践）：一 反向检查 ｜ 二 随包文档去留 ｜ 三 「删文档保护城河」是自废武功 ｜ 四 护城河的正确位置 ｜ 五 发布完整性 ｜ 六 对外文档双轨制 ｜ 七 资产边界 ｜ 处置决策流程

> 定位：随包文档（references / README / 发布说明）发布前的知识产权自查与护城河判定，与 `SKILL.md` §八「资产边界」的两条红线（核心知识产权不入包、来源与案例不暴露）配套——那两条防「自家 IP 外泄」，本篇防「别人的 IP 入包」。
> 核心动作：发布前先反向检查「入包的是谁的知识产权」，再谈「自家的会不会丢」。

## 一、反向检查：入包的是谁的知识产权（先于一切发布动作）

技能宣称的能力越「合规/审查」，第三方受限内容入包的信任打击越重——商业平台上架后被投诉即下架。

**检查动作**（发布前对 references 全量扫一遍）：

- 来源标注：文档是否自称基于订阅知识库 / 受权资料 / 内部规范整理？
- 风险信号：出现「因权限限制，部分内容以摘要形式引用」「转载自」类自述；体量最大的参考文档开头即来源声明。
- 判定：来源是公开规范（法规、国标、平台公开文档）还是受限内容的再分发？

**处置**：受限内容 → 按资产红线档位词改写来源口径（官方 / 社区共识 / 个人实战），或改写为公开规范的整理；公开的文号、日期、清单等实质内容保留。改写后全包 grep 来源名，0 残留为准。

## 二、随包文档去留：两条检验

| 检验 | 问法 | 结果 |
|---|---|---|
| 检验一：可推导性 | 内容能否从公开材料两三天复刻七八成？ | 能 → 不是护城河，删了不可惜 |
| 检验二：能力依赖性 | 技能承诺的能力是否以这份文档为执行依据？ | 是 → 删 = 技能残废，不能删 |

- **两条同时成立**（可推导 + 能力依赖）→ 正确动作是**保留并去标识化**，不是删除。
- **易混淆点**：资产红线「核心知识产权不入包」防的是商业资产外泄，**不是**允许把执行依赖外置到包外（作者私有知识库/外部文档）。执行依赖外置 = 用户拿到手跑不出承诺，属发布清单第 15 项「脚本自包含」的文档版，按不通过处理。

## 三、「删文档保护城河」是自废武功

- 护城河判定看「**什么真的难抄**」，不是「什么看起来像核心资产」：删掉参考文档后剩下的往往是最容易抄的部分（正则与校验器，看一遍即可复刻），净收益为负。
- 内容已公开多日时，「删」更是马后炮：历史提交仍可取，护城河救不回来，只伤害新版本用户。

## 四、护城河的正确位置（检测/审查类技能通用）

1. **工程细节**：踩坑调出来的防误报组合、校验与去重逻辑——内建在脚本里，脚本必发、抄不走。
2. **持续更新**：对标规范/平台规则的滚动跟进节奏——不在包里，在维护节奏里；这部分价值靠版本迭代兑现，不靠静态文档。
3. **质量背书**：可执行回归评测集（含边界用例、退出码接 CI）——随包发不构成资产外泄，属可公开的工程资产。

结论：护城河 = 工程细节 × 持续更新 × 质量背书，不在静态文档里。静态文档该发就发，去标识化即可。

## 五、发布完整性：本地历史也要清

内容回退/重写后的重发，若只删远端、不重置本地仓库，推送会把旧提交原样带回，等于白删。GitHub 发布步骤补一条：**本地仓库重新初始化或强推干净历史，并核验全量提交内容**（不只看最新一版）。

## 六、对外文档双轨制

| 轨道 | 载体 | 内容口径 |
|---|---|---|
| 用户轨 | README、发布 summary/description、版本升级说明（changelog） | 以**功能与独创性**为主：能做什么、有何不同、有哪些提升。原则是**写现象、不写根因**——修复类**要写**（用户靠它判断「上次那个毛病好了没」），但只描述可感知的现象，不写实现、脚本名与内部口径 |
| 执行轨 | 包内 SKILL.md 正文、references | 供执行 agent 使用：流程、命令、边界、踩坑——**能力依赖性检验通过即可**（执行 agent 缺了这条就跑不通，属能力必需，不是泄密） |

- 两轨判据看**读者**：用户做选装决策需要什么 vs 执行 agent 跑通链路需要什么（面向用户端写作判据见 `references/SKILL.md编写规范.md` §4.1）。
- 版本升级说明写「提升与改进 + 用户可感知的修复现象」；**问题机理与修复过程**留开发侧档案（工作区验收报告，不入包、不随发布）。写法见 §6.1。
- 实现细节写在包内不算泄密——能从公开材料推导的东西不构成护城河。

### 6.1 版本升级说明的写法

**修复类要写，但只写现象**：用户正是靠这一栏判断「我上次遇到的那个毛病好了没」；禁的是**根因与实现**，不是问题本身。

> ⚠️ **示例一律用虚构内容**：示例会被读者当成可复用的真实范例抄走；**从真实产品摘的条目要重写成通用形态**——保留句式结构、去掉专有特征。

写法（四类条目骨架与公式 / 量化边界 / 正反例对照 / 发布前自检清单）见 `references/Changelog写作模板.md` §二/§三/§四/§七/§九。

## 七、资产边界（防膨胀：新增资产先自问）

**1–4 为默认（可偏离须留痕），5–6 为红线（不可越）。**

1. 领域能力不进编排技能——可独立复用的能力（如脱敏审查）保持独立技能，仅被引用。
2. 复盘文档不入技能——成本分析 / 评估报告是「项目档案」，留工作区。
3. 技能只收「可执行知识」——清单/脚本/模板/方法论纪律可入；档案与一次性结论不可。**会随平台或项目演进漂移的清单与数值同样不入正文**：平台字段表、类目选项集、发布坐标、条目计数这类内容一进包就开始腐烂。它们要么留「去哪个文件读 + 一条命令」，要么由独立技能承接、主包只挂指针。
4. 新增资产三问定位：≥2 技能复用 → 进主技能；仅本技能用 → 进其 references；仅本项目结论 → 留工作区。
5. **核心知识产权不入包**——商业评估报告、付费方法论、未公开策略/数据资产一律不入技能目录（含 references/evals），只在个人工作区留存。
6. **来源与案例不暴露**——正文/脚本/评测用例中不得出现具体训练案例名、方法论来源文档名或其路径；方法论只以「社区共识 / 官方规范 / 个人实战」口径署名。

## 处置决策流程（发布前按序执行）

1. 反向检查第三方受限内容（§一）→ 2. 随包文档逐份过两条检验（§二）→ 3. 受限来源去标识化、0 残留（§一）→ 4. 新增资产先过资产边界判定（§七）→ 5. 对外文档按双轨制改写（§六）→ 6. 干净历史重发、核验全量提交（§五）。
