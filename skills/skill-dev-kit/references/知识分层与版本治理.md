# 知识分层与版本治理

> 来源：社区共识 + 个人实战。回答「什么进技能、什么进记忆文件」，技能自身的版本怎么管，以及什么情况下必须拆分下沉。

---

## 一、什么进技能、什么进记忆文件

**可执行工作流 → 沉淀为 Skill**（可再次执行）；**信息性事实 → 只记记忆文件**；**Skill 优先于记忆文件**。

固化判据见 SKILL.md §一；「留工作区、不进包」的口径见 `references/知识产权边界与护城河判定.md` §七。

> 层级名称与存放位置随宿主而异，本技能不做绑定——判定只看上面这条：**能再跑一遍的是技能，只能查一遍的是记忆**。

### 1.1 量化拆分阈值（什么时候必须拆分下沉）

满足任一条件 ⇒ 必须拆分下沉，不得以「还能读」为由继续堆：

| 信号 | 阈值 | 拆到哪 |
|---|---|---|
| 单个文件过长 | **文件 >300 行** | 按主题拆到 `references/<主题>.md` |
| 单个**步骤**过长 | **单个 Step >100 行** | 把可复用部分下沉为 `scripts/`，正文只留调用命令。⚠️ 这个 100 行与「单个文件 >300 行」是**不同对象、不同落点**：本行管「一个 Step 太长」→ 拆成脚本；上一行管「整份文件太长」→ 拆成 `references/<主题>.md` |

**为什么用数字不用感觉**：「还能读」靠感觉的结果是「一直不拆，直到拆不动」⇒ 用行数触发线。

## 二、技能版本治理

| 动作 | 规则 |
|---|---|
| Git 版本化 | 技能源码进 Git；`version` 与发布 tag 一致，否则不自动更新 |
| bump version | 通用原则：新增能力 / 改行为 → MINOR（x.Y.0）；结构性重写 → MAJOR；纯勘误与表述修正 → PATCH。**本技能的具体类型映射（T1–T6 → PATCH/MINOR/MAJOR）以 `references/发布检查清单.md`「与版本号自然衔接」为准**——本行只给性质分类，落到技能上按那一行判 |
| 季度清理 | 每季度清理过期/失效技能，保留已知良好基线 |
| feature flag | 问题版本用开关禁用，不强制回滚 |
| 团队中心库 | 负责人 + 中心库 + 版本日志，避免分叉漂移 |

## 三、技能自身的版本管理（对齐文档版本管理通用规范）

技能作者对自己的技能做「三位一体」管理（frontmatter + 正文 + 版本档案）：

1. **frontmatter 含 `last_updated`**：每次更新同步日期。
2. **Changelog 独立存档**（如 `references/Changelog.md`，不放发布正文）：追加式记录，一个版本一段、每条一行。**写法**——四类条目（新增能力 / 优化体验 / 修复问题 / 调整边界），不写脚本名、函数名、字段名、内部编号与实测数字，**也不设「来源」列**（写法见 `references/Changelog写作模板.md`）。
3. **更新触发机制**：每次实质改动必须（a）bump version（b）刷新 last_updated（c）追加 Changelog 的版本小节——三者齐备才算完成一次发布。
4. **失效触发条件（主动更新，区别于被动的"季度清理"）**：出现以下任一信号时**必须**触发更新并 bump version，不得拖延到季度评审——
   - 依赖变更：所依赖的工具 / 平台接口 / CLI 行为发生变化（如发布平台改文件白名单、CLI 新增能力）；
   - 误判累积：本技能的清单/脚本对同类问题累计 ≥3 次误判、漏判或误导；
   - 生态变更：社区实践或官方规范出现更优共识，使某条纪律过时。
   > 分工：季度清理是定期体检（防遗漏），失效触发是随诊即改（防带病运行）。命中即记 Changelog「修订」。

> ⚠️ **体积口径**：一律按**字符数**核算，不用 `wc -c`——中文 UTF-8 为 3 字节/字，按字节读会虚高近 2 倍，跨人比对必然对不上。
> ✅ **门禁**：`preflight_release.py` 校验 version 一致性与 name 规范，并已把正文体积纳入检查（warning 级，`--strict` 时阻断），按 `核心公式与量化基准.md` §2 的同一口径现场核算，无需手工回跑；`eval_trigger.py --check` 校验触发覆盖。

## 四、发布前「平台规范现拉」原则

**平台发布规范是活文档，会变。** 必填字段、必含文件、命名规则、审核规则都会随平台迭代调整。因此：**每次发布操作前现拉一次最新规范，再动手**，不要凭上一版的记忆发布。

规范改了没拉，最坏不是发布失败，而是**字段写错却照样发布成功、上线后才暴露**。

**三条执行纪律**：

1. **发布前现拉，不是发布失败后才查**：把「拉规范」放在发布流程的第一步，而不是出错后的排查动作。顺序反了，代价就是一次带病发布。
2. **拉到就对照，对照要留痕**：把本次依据的规范要点（必填字段集、必含文件清单）记进**开发侧留痕**（个人工作区的发布记录），**不要写进 `references/Changelog.md`**。
3. **规范变了要回头修技能**：发现平台规范与技能现状不符时，按本文件「技能自身的版本管理」的「失效触发条件 → 依赖变更」处理——bump version + 刷新 `last_updated` + 记 Changelog。

**关于本技能 preflight 脚本的能力边界（避免虚假承诺）**：

- `scripts/preflight_release.py` 做的是**本地静态校验**：敏感信息扫描 / frontmatter 字段校验 / 必含文件检查 / git 未跟踪文件告警 / 归属检查。
- 它**不会联网拉取平台最新规范**——脚本内的必填字段表 / 必含文件表是硬编码的平台规则表，脚本不含任何网络请求。
- 所以：**「现拉最新规范」目前是人工动作**（查平台当前的发布文档/说明），**「脚本自动拉取平台规范」当前不做**。
- 跑 preflight 只能证明「符合脚本内置的那版规则」，不能证明「符合平台当前规则」。**两者不等价，不要把前者当后者用。**

**验收**：发布前能说清本次依据的规范是「什么时候拉的、从哪拉的、必填字段是哪几个」？三条都说得清，才算真的现拉过。
