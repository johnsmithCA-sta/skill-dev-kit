# 知识分层与版本治理

> 来源：知识分层与发布版本治理实践提纯。回答「什么进技能、什么进 memory、什么留工作区」，以及技能自身的版本怎么管。

---

## 一、三层知识分层体系

| 层级 | 内容 | 写入时机 | 位置 |
|---|---|---|---|
| 每日日志 | 当日做了什么、踩了什么坑、产物在哪 | 每次实质工作后**追加** | `<项目>/.workbuddy/memory/YYYY-MM-DD.md` |
| 项目 MEMORY.md | 长期约定、用户偏好、项目规范 | 发现可跨会话复用的事实 | `<项目>/.workbuddy/memory/MEMORY.md` |
| 用户级 MEMORY.md | 跨项目个人偏好（API key、交付规范） | 用户明确要求记住 | `~/.workbuddy/MEMORY.md` |

**铁律**：可执行工作流 → 沉淀为 **Skill**（可再次执行）；信息性事实 → 只记 **memory**；**Skill 优先于 memory**。

与资产边界红线（SKILL.md §九）的关系：
- 红线②「复盘文档不入技能」对应：具体复盘内容 → 留工作区（项目档案），不进 `references/`。
- 红线③「技能只收可执行知识」对应：清单/脚本/模板/方法论 → 进 Skill；档案与一次性结论 → 留工作区。
- 红线④「新增资产三问」：能被 ≥2 个技能复用 → 进编排技能；仅本技能用 → 进该技能 references；仅本项目结论 → 留工作区。

## 二、技能版本治理

| 动作 | 规则 |
|---|---|
| Git 版本化 | 技能源码进 Git；`version` 与发布 tag 一致，否则不自动更新 |
| bump version | 新增资产/修订 → MINOR（x.Y.0）；结构性重写 → MAJOR；纯勘误 → PATCH |
| 季度清理 | 每季度清理过期/失效技能，保留已知良好基线 |
| feature flag | 问题版本用开关禁用，不强制回滚 |
| 团队中心库 | 负责人 + 中心库 + 版本日志，避免分叉漂移 |

---

## 三、自身版本管理（对齐文档版本管理通用规范）

技能本体应「以身作则」，frontmatter 与正文三位一体：

1. **frontmatter 含 `last_updated`**：每次更新同步日期。
2. **Changelog 独立存档 `references/Changelog.md`**（不放发布正文）：追加式记录，一个版本一段、每条一行。**写法按用户侧口径**——四类条目（新增能力 / 优化体验 / 修复问题 / 调整边界），不写脚本名、函数名、字段名、内部编号与实测数字，**也不设「来源」列**（完整模板与正反例见 `references/知识产权边界与护城河判定.md` §6.1）。理由——版本史是**开发侧档案**，对技能使用者无操作价值，占发布正文体积；渐进披露下 references 按需加载，追溯时仍可查。
3. **更新触发机制**：每次实质改动必须（a）bump version（b）刷新 last_updated（c）追加 Changelog 的版本小节——三者齐备才算完成一次发布。
4. **失效触发条件（主动更新，区别于被动的"季度清理"）**：出现以下任一信号时**必须**触发更新并 bump version，不得拖延到季度评审——
   - 依赖变更：所依赖的工具 / 平台接口 / CLI 行为发生变化（如发布平台改文件白名单、CLI 新增能力）；
   - 误判累积：本技能的清单/脚本对同类问题累计 ≥3 次误判、漏判或误导；
   - 生态变更：社区实践或官方规范出现更优共识，使某条纪律过时。
   > 分工：季度清理是定期体检（防遗漏），失效触发是随诊即改（防带病运行）。命中即记 Changelog「修订」。

> 自合规示例：skill-dev-kit 自身通过 `preflight_release.py` 校验 version 一致性与 name 规范、`eval_trigger.py --check` 校验触发覆盖、按 `核心公式与量化基准.md` §2 的自检命令核算正文体积——「剃头匠自己先剃头」。
> ⚠️ **体积口径**：一律按**字符数**核算，不用 `wc -c`——中文 UTF-8 为 3 字节/字，按字节读会虚高近 2 倍，跨人比对必然对不上。
> ✅ **已有门禁**：`preflight_release.py` 已把正文体积纳入检查（warning 级，`--strict` 时阻断），按 `核心公式与量化基准.md` §2 的同一口径现场核算，无需手工回跑。

## 四、发布前「平台规范现拉」原则

**平台发布规范是活文档，会变。** 必填字段、必含文件、命名规则、审核规则都会随平台迭代调整。因此：**每次发布操作前现拉一次最新规范，再动手**，不要凭上一版的记忆发布。

记忆会过期，而且过期得无声无息——规范改了、你没拉，最坏的情况不是发布失败（失败至少会告诉你），而是**字段写错但照样发布成功、上线后才暴露**。

**三条执行纪律**：

1. **发布前现拉，不是发布失败后才查**：把「拉规范」放在发布流程的第一步，而不是出错后的排查动作。顺序反了，代价就是一次带病发布。
2. **拉到就对照，对照就留痕**：把本次依据的规范要点（必填字段集、必含文件清单）记进 `references/Changelog.md` 的「来源」列，下次一眼能看出规范是哪一版、变了什么。
3. **规范变了要回头修技能**：发现平台规范与技能现状不符时，按 §三 的「失效触发条件 → 依赖变更」处理——bump version + 刷新 `last_updated` + 记 Changelog，不要只在本次发布里绕过，绕过一次就会绕过第二次。

**关于本技能 preflight 脚本的能力边界（避免虚假承诺）**：

- `scripts/preflight_release.py` 做的是**本地静态校验**：敏感信息扫描 / frontmatter 字段校验 / 必含文件检查 / git 未跟踪文件告警 / 归属检查。
- 它**不会联网拉取平台最新规范**——脚本内的 `REQUIRED_FIELDS` / `REQUIRED_FILES` 是硬编码的平台规则表，脚本不含任何网络请求。
- 所以：**「现拉最新规范」目前是人工动作**（查平台当前的发布文档/说明），**「脚本自动拉取平台规范」→ 待实现**。
- 跑 preflight 只能证明「符合脚本内置的那版规则」，不能证明「符合平台当前规则」。**两者不等价，不要把前者当后者用。**

**验收**：发布前能说清本次依据的规范是「什么时候拉的、从哪拉的、必填字段是哪几个」？三条都说得清，才算真的现拉过。
