# 全生命周期 10 步 + 认知底座

> 来源：Skill 本质/技术选型/全生命周期实践提纯。从「该不该做」到「上线后怎么迭代」的完整路线图。

---

## 一、认知底座：Skill 的本质与边界

**定义**：Skill = 可复用的「程序性知识 + 组织上下文」能力包（指令 + 脚本 + 资源），让通用智能体按需获得领域专长。本质是「可复用系统提示词/指令集 + 可执行资源」。

三条核心关系：

| 关系 | 类比 | 结论 |
|---|---|---|
| Skill vs MCP | MCP 是「厨房」（提供外部工具/连接），Skill 是「菜谱」（教 AI 用工具完成任务） | **互补**，MCP + Skill 是王炸组合 |
| Skill vs Command | 旧 Command 体系已并入 Skill | 新功能直接写 Skill（支持脚本/多文件/子代理） |
| Skill vs Memory | 可执行工作流 → Skill；信息性事实 → memory | **Skill 优先于 memory** |

> 谁该用本技能：带「这个流程该不该做成技能 / 怎么做 / 怎么发布」问题来的新技能作者。

## 二、技术选型三岔路口

| 场景 | 方案 | 说明 |
|---|---|---|
| 一次性任务 | 脚本 | 不值得做成 Skill |
| 多次复用 | **Skill** | 本方法论核心对象 |
| 多 Agent 共享 | Framework + Skill Registry | 长期有状态基建 |
| 确定性流程、可预测 | Workflow | 预定义代码路径编排 |
| 开放问题、需自由发挥 | Agent | 模型自主决策 |

**决策铁律**：别被社区技术崇拜带偏，能用简单方案解决的就不要上复杂框架；从简单 Prompt 开始，**先「做成」再「做对」最后「做优雅」**。

**四场景对照（用固化判定公式对号入座）**：

| 场景类型 | 频率 | 步数 | 主要踩坑 | 固化价值 |
|---|---|---|---|---|
| 批量化查询/尽调 | 高频 | 30+ 步 | 数据源假成功、口径冲突 | 高 |
| 一次性数据迁移 | 中频 | 30+ 步 | 系统级加密/格式锁定 | 中高 |
| 年度动态追踪分析 | 年度 | 多阶段×多脚本 | OCR 乱码、隐私硬编码 | 高 |
| 发布前必做审查 | 每次发布 | 多轮扫描 | 工具白名单盲区 | 中 |

## 四、设计端选型最小集

> 落地范围：全生命周期第 2–5 步（原型验证 → 提炼 SKILL.md → 定义触发 → 映射资源）。先判定该不该做成技能，再选结构框架，再按五段骨架填正文，最后把加载关系写成强路由。

### 4.1 准入四问（要不要做成技能）

| # | 问句 | 通过标准 | 不过时改走 |
|---|---|---|---|
| ① 形态合规 | 边界是否清晰——说得出「做什么、不做什么」吗 | 一句话能划出边界，没有「顺便也管…」 | 拆成两个技能 / 转 Rule |
| ② 非元信息 | 是可复用积木，还是一次性操作说明 | 交付的是可再次执行的能力，不是一条结论 | 转 Rule 或脚本 |
| ③ 可链接 | 能写出「关于 X 请参考 [[技能名]]」吗 | 一句引用即可接进已有链路 | 并进宿主技能，不单独建 |
| ④ 复用检验 | 是否 ≥2 个场景需要它 | 数得出至少两个彼此不同的场景 | 不做，留在工作区 |

四问任一不过 → 转 Rule / 脚本 / 不做；四问全过才进入选型。
**疑虑时跳过**：零个新技能好过一堆噪音。

### 4.2 结构框架选型（自上而下命中即停；七套都不中则默认 `pipeline`）

| 框架 | 命中信号 |
|---|---|
| `minimal` 极简型 | 无文件产出 + 无外部调用 + 知识 <5K |
| `pipeline` 流程型 | ≥3 步且有分支 |
| `tool` 工具编排型 | 调外部 API / DB / CLI |
| `knowledge` 知识密集型 | 领域规则为主 |
| `template` 模板产出型 | 有文件产出且格式固定 |
| `full` 全栈工程型 | 对外发布 / 高风险 / 长迭代 |
| `suite` 套件型 | 覆盖多个正交子域 |

```text
# minimal —— 单文件即全部（正文 ≤500 行）
SKILL.md
```

```text
# pipeline —— 正文 + 按需加载 + 可选脚本
SKILL.md
references/<主题>.md
scripts/<工具>.py          # 可选
```

```text
# tool —— 工具白名单最小化 + 调用脚本 + 契约文档
SKILL.md                   # 只留：可用工具白名单 + 何时调哪个
scripts/<client>.py
references/<接口契约>.md
```

```text
# knowledge —— 正文只放要点，一主题一文件
SKILL.md                   # 只放要点与索引
references/<主题A>.md
references/<主题B>.md
references/gotchas.md
```

```text
# template —— 模板 + golden sample + 渲染/校验脚本
SKILL.md
templates/<模板文件>
assets/golden-sample/<样例产物>
scripts/render.py
scripts/validate.py
```

```text
# full —— 五段骨架 + 错误台账 + 看板
SKILL.md                   # 五段骨架见 4.3
references/
scripts/
evals/
错误台账.md
```

```text
# suite —— SKILL.md 作路由器 + 子技能自治
SKILL.md                   # 只做路由，不承载子域细节
references/<子域1>.md
references/<子域2>.md
# 或：子技能目录/*，各自独立 SKILL.md
```

**本技能自身命中 `full` 全栈工程型**（对外发布 + 高风险 + 长迭代）：五段骨架逐段填出，脚本链齐备（8 个零依赖脚本），错误台账落在 `references/发布检查清单.md` 末尾的踩坑表。选型表是给「新技能立项」用的，此处回填自己的归属只为让读者有对照样例——**不要把本技能的形态当成默认推荐**：多数技能命中 `minimal` 或 `pipeline` 就够了。

### 4.3 五段章节骨架（正文该有的五段，逐段填出）

| 段 | 填什么 |
|---|---|
| `## Workflow` | ≤7 步的可执行主流程，每步给完整命令 |
| `## Clarification Protocol` | 何时停下问人、问什么、一次问几个（澄清协议） |
| `## Resource Routing` | 什么信号加载哪份资源（资源强路由，句式见 4.4） |
| `## Failure Handling` | 失败分级、重试 / 降级 / 中止的出口 |
| `## Validation` | 完成前必查项（可勾选），对得上 4.1 的质量门槛 |

逐段填出；**不适用也要写「本技能不适用」，不留白**——留白会让读者分不清「没想过」还是「确实不需要」。

### 4.4 强路由句式 + doNotUse

references 的加载元数据不写「本文档讲了 X」这类目录式说明，写成三段式：**信号 → 加载哪份 → 在什么动作之前**。

> 句式：**若用户提到 X（信号），就在做 Y（动作）之前先加载 Z（哪份）。**

| 信号（用户提到…） | 加载 | 在什么之前 | Do NOT route to / 不路由到 |
|---|---|---|---|
| 「导出 / 出报告」 | `references/报告模板.md` | 生成产物之前 | 数据清洗（→ `references/数据清洗.md`） |
| 「发布 / 上架」 | `references/发布检查.md` | 执行发布动作之前 | 本地调试与试跑 |

**路由表必须带「Do NOT route to / 不路由到」列**，不只说该读什么——不写「不路由到哪」，模型只能靠排除法猜，命中率取决于联想，不取决于表。
