# Changelog（版本史）

> 写给使用者看：每个版本带来什么提升。开发过程、问题机理与内部口径不入此文件——写法见 `知识产权边界与护城河判定.md` §6.1。
> 版本号语义化 X.Y.Z：Z 修复与体验优化 / Y 功能新增 / X 结构性升级。

## 1.13.1 版本发布（2026-09-13）

- **修复**：自身评测的证据切片取错了行——「发布检查清单」顶部是元数据块，取首行只会拿到分隔线而拿不到标题，导致评测分数在同一份包内对不上（包内记录与实际重跑不一致）。现在按首个标题行取
- **优化**：发布预检的「打包卫生」检查不再报告缓存文件——缓存本来就被打包脚本排除、进不了包，报出来只会让报告多出需要人工解释的行；该检查现在只盯「会被真打进包」的临时与备份文件
- **优化**：发布预检调用同目录脚本时，不再在被检技能的目录里留下缓存文件——预检是只读的，不该在检查对象上留下痕迹

## 1.13.0 版本发布（2026-09-13）

- **新增**：发布预检增加第 9 节「结构规范检查」——一次预检即可同时核对：正文里引用的文件是否真实存在、description 的触发面是否完整（排他边界与口语触发词示例）、frontmatter 有无品牌保留词、以及冒号与多行写法带来的截断风险
- **新增**：预检再增两项——**打包卫生**（`.bak` / `.tmp` / `~$*` / `.swp` 这类临时文件不在打包排除名单里、会真被发出去，现在发布前就拦下）与**路由表 doNotUse 列**提示；参考文档的「加载条件」开始按强路由句式给建议
- **新增**：SKILL.md 增加「输出文件约定」一节——一次说清产物写到哪、怎么命名、什么格式、失败时留下什么
- **新增**：正文补上边界输入清单、本机与其他技能的生态分工、以及发布链中断后的续跑锚点
- **优化**：该节另登记若干整洁信息（包内含 README、未被正文引用的文件、参考文档缺少加载条件、索引体量与实际行数漂移、路由表缺 doNotUse 列）——只提示，不参与通过与否
- **优化**：预检结果分「告警」与「登记」两档，前者在 `--strict` 下阻断发布，后者永不阻断——不再为一个格式建议卡住整条发布
- **优化**：自身评测的证据从「章节转储」改为**真跑产物**，每份证据头部写明取得方式与可独立重跑的命令；`benchmark.json` 同时输出**无技能基线对照**与 delta，让「技能到底有没有教出新东西」第一次可量化检验
- **优化**：随包 README 从技能目录移出（技能文件夹内不放 README.md，说明收敛到 SKILL.md 与 references/），仓库根 README 保留并同步更新
- **新增**：description 增加「触发词示例」检查，`eval_trigger.py --desc-check` 由 6 项增至 7 项
- **优化**：疑似密码、手机号、本机路径三条规则的误报大幅下降——技能自身名、依赖包名、标准 HTTP 头与 CSS 属性名、测试用假号码、GitHub 用户名等不再被误报；同一命中出现在多个文件时折叠为一行汇总，报告更短更好读
- **优化**：description 的场景词与动词词表扩充，紧贴中文的缩写（如「API 余额」「CSS 变量」）不再被判「未识别到场景」
- **修复**：前几版的多行写法 description 只会被读到第一行，导致触发面后段整体失效却看不出来；现在按 YAML 规则整段读取，并在预检里把这种写法单独提示出来
- **修复**：评测聚合读取中文产物时，文本探测窗口会截断多字节字符，导致体量较大的中文证据被静默漏评、分数偏低且看上去像「没通过」

## 1.12.1 版本发布（2026-09-12）

- 修正一处参考文档里的命令示例写法：该示例中的变量名会被整体合规扫描规则误判为明文口令，导致发布前扫描报「禁止发布」
- 示例的含义与可读性不变，只是把变量名改成更贴近它实际承载内容的那一个

## 1.12.0 版本发布（2026-09-12）

- 随包参考文档由 15 份收敛为 14 份：「跨会话接续协议」讲的是任何跨会话长任务都适用的通用做法，不专属技能固化与发布，已移出技能包单独留存
- 该协议中「每步落盘中间产物、禁止一次性跑完」的要求已并入发布流程本身，发布链路不受影响
- 修正写作指导里一处按外部样本统计描述的章节排序依据，改为社区共识口径——与「方法论只以官方规范 / 社区共识 / 个人实战 署名」的纪律对齐

## 1.11.2 版本发布（2026-09-12）

- 修正版本说明的写法指引：此前一处参考文档仍按旧口径写（按内部变更类型分类、并要求填「来源」列），与正式的用户侧四类条目写法自相矛盾
- 修正一处指向并不存在的待办清单的引用

## 1.11.1 版本发布（2026-09-12）

- 每个脚本的参数说明补全，帮助信息里不再有只写参数名、不说用途的条目
- 正文精简：合并了几处与参考文档重复的转述，篇幅下降，章节顺序与内容覆盖不变
- 修正示例数量口径——原先几份参考文档对「该有几个示例」说法不一，现统一为按「是否完整可跑」判定，不按条数判定
- 修正体积预算的说明：删去过时的自身实测数值，并写明 ~2000 token 是形态中位数——清单型工具包按「硬上限 + 不重复转述」两条守住即可，不为凑目标值拆散正文

## 1.11.0 版本发布（2026-09-12）

- 新增批量体检：一次给一批技能跑完同一套检查并汇总成一张结构对照表，不必再逐个手工调用；体检报告只留在本地工作区，不会写进被检查的技能目录
- 反模式清单每条补上「可观测判据」——出现什么现象就算踩了这条，可以逐条机械核对；同时新增一条：技能的实际行为与描述不符（含夹带恶意或利用性代码）即属缺陷
- 评测用例补上六条质量标准（独立、只读、复杂、真实、可验证、稳定），不满足就先改用例再谈分数；并新增回哺环节——多个用例各写一遍同一段脚本时，该把它收进公共脚本供调用，而不是让每个用例重复实现
- 写作指导补充：决策路径图的适用边界、什么时候不该拆分文件、面向协作者该选哪些词、命名与示例的质量取向
- 技能描述补充两条写法：写「触发前那一刻的症状」，以及描述问题本身、而不是某种语言特有的症状
- 每个脚本的帮助信息都给出可直接复制运行的示例，不必再翻文档猜参数
- 发布检查清单补「门禁可信任度」纪律：误报率超过一成时先修规则，再谈合规——否则执行者会学着无脑放行
- 技能迭代四步法标注为默认不执行：它依赖执行记录采集机制，机制未就绪时强行执行只会给出假信号
- 修正参考文档里一处过时的体积基准，以及两处指错目标的交叉引用

## 1.10.0 版本发布（2026-09-12）

- 技能文档的章节顺序改为「先讲解决什么问题、再讲会拿到什么」——读者先判断该不该用，不必先读一大段产物规格
- 技能模板新增「定位」与「何时用（适用 / 不适用）」两节；「触发词」提到靠前位置，不再压在文末
- 版本更新说明改为面向使用者的写法：只写能感知的现象与提升，不写内部实现；模板与正反例已写入参考
- 技能自身文档瘦身约两成，细节移入按需加载的参考文件，正文只留结论与指针

## 1.9.0 版本发布（2026-09-12）

- 发布预检新增章节引用检查：文档之间引用的章节号失效时会提示
- 发布预检新增版本回退提示：版本号低于已有发布标记时报警
- 发布预检新增声明一致性检查：文档说做了评测、却拿不出评测资产时会提示
- 新增依赖自检：扫出脚本用到、但没写进依赖清单的第三方包（默认只看声明，不执行代码）
- 自查清单按改动类型分级：小改动只跑该跑的项，改一行描述不必走全量；首次发布与大版本仍走全量
- 新增发布当天闭环清单：建标记 / 补标签 / 加保护 / 复核三处一致
- 新增两条发布踩坑：常规推送各姿势全失败时的正确处置、空仓库走接口报冲突时的绕法
- 市场调研新增发布曝光配套：标签选词方法 + 收录列表的提交时机与门槛

## 1.8.0 版本发布（2026-09-12）

- 写作指导语不再一律用「必须 / 绝不」，改为按失败类型选形式——该严格的严格、该留余地的留余地
- 新增技能类型矩阵：不同类型对应不同的严格度、测试方式与成功判据
- description 不再概括操作步骤，写完会静态提示
- 测试闭环补上「基线对照」：能看出技能到底有没有用，而不只是能不能用
- 新增措辞微型测试法：改一句话先小样本验证，便宜且快，不必等整套评测
- 触发词评估支持留出集与重复采样，防止描述被「背题」——对没见过的说法同样成立才算数
- 发布预检新增技能名规范检查
- 反模式清单新增堵漏机制：合理解释对照表 + 红旗清单
- 发布预检新增正文体积检查；同时修正自查命令的口径偏差，避免达标文件被误报超标
- 推送脚本不再只认一个代码托管平台，自建实例同样可用
- 新增推送兜底通道：常规推送不可用时改走接口
- 发布预检在严格模式下零告警
