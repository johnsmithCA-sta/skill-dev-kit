# 技能发布前必过检查清单（16 项）

> **本文件目录**（社区实践）：改动分级 ｜ 16 项清单正文 ｜ 门禁分级 ｜ 一键执行顺序 ｜ 失败降级路径 ｜ 归属与权益（三档）｜ GitHub 推送踩坑 ｜ 发布后验证 ｜ 踩坑表 ｜ 发布当天闭环

> 复制本清单逐项勾选，全部通过后方可发布。配套脚本 `scripts/preflight_release.py` 可自动覆盖第 1/3/5/6/16 项，另做**六项**与**结构规范检查**（逐项明细见 `references/脚本速查.md` §1）；`scripts/check_deps.py` 单独负责依赖声明完整性。
>
> ⚠️ **对外写作检查的检查面 = 随包对外 markdown**（**`references/` 不豁免**；非 `.md` 资产与 `evals/**` 不承诺）。范围定义与 12 类禁写表的**唯一正文**为 `references/SKILL.md编写规范.md` §4.1。自用（不发布）的包命中只登记，对外发布的包命中即阻断。
> ⚠️ **先判改动类型再勾选**——16 项全量串行会把「改一句 description」和「发首版」按同一成本处理。见下方「改动分级」。

## 改动分级：先定改动类型，再选最小但足够的检查集

**自动项 5 项（1/3/5/6/16）永远全跑，不纳入分级**——零成本。分级只裁**人工项 11 项**。

| 层 | 项 | 说明 |
|---|---|---|
| **L0 人工红线**（无条件必过） | 2 版本号一致 · 11 不含 LICENSE · 16 的第三方受限内容反向检查 · **12 的三视角语义通读子项** | 出错即不可逆或违规，与改动类型无关。16 的自动部分（author / Copyright）在 preflight，反向检查必须人工，**任何改动类型都查** |
| **L1 改动相关**（按类型裁剪） | 4 · 8 · 12 · 13 · 14 · 15 | 见下映射表；横跨多类型取并集 |
| **L2 发布流程收尾**（不是「改动检查」） | 9 · 7 · 10 | 已剥离进发布流程步骤：9 挂实发前，7 / 10 挂实发后（见 `SKILL.md` §七） |

**改动类型 → 追加的人工项**

| 类型 | 改了什么 | 追加项 |
|---|---|---|
| T1 | 元信息 / frontmatter | 4（仅在动了 README 或结构类字段时）；纯 description / summary 文案改动只需 `eval_trigger.py --desc-check` |
| T2 | SKILL.md 行为规则（触发词 / 流程 / 边界 / 示例） | 13 —— **不可豁免**（但 13 本身含一个条件项：多模型实测；无该条件时按单模型 + 真人 prompt 执行，见该项）—— 触发正确性无法靠自动检查补偿 |
| T3 | `scripts/` 脚本 | 8 · 13 · 14 · 15 |
| T4 | `references/` 参考文档 | 12 —— **references 是对外可见文本**（编写规范 §4.1），改动即对外文本变更 ⇒ 走清单 12 的三视角语义通读（该项已列 L0 无条件必过） |
| T5 | 目录结构 / 增删文件 | 4 · 8 · 12 |
| T6 | `evals/` 评测资产 | 12（确认评测产物是否该排除出发布包） |

⚠️ **清单 12 的三视角语义通读不受分级裁剪**：它是一次固定成本的通读，裁它只留语义风险。

**判定规则**

- 改动横跨多类型 → **取并集**（宁多勿漏）；无法确定改动边界 → **升级为全量**。
- 首次发布 / 大版本 / 失效触发随诊即改 → 全量，不启用分级。
- **启用边界**：分级制只服务「小改动快速迭代」。一个技能半年才发一次版，直接全量即可。
- **不可逆步骤不受分级影响**：实发（`skillhub publish` / `git push` / 打 tag）在任何改动类型下都要 dry-run + 目录快照 + 人工确认。
- **与 preflight 分级正交**：preflight 的 critical / warning 管「命中后是阻断还是可豁免」；改动分级管「要不要跑这一项」。两层不冲突，勿混为一谈。
- **与版本号自然衔接**（**本技能的具体映射，逐类以本行为准**）：T1 / T2 / T4 → PATCH；T3 / T6 → MINOR；T5 视影响（资源增删 MINOR，接口变动 MAJOR）。通用原则见 `references/知识分层与版本治理.md` §二「技能版本治理」的 bump version 行——那里按**改动性质**分类，本表按**改动类型**分类，两者是「原则 ↔ 实例」关系，不是两套口径。
- **先判类型靠 `git diff --stat`**，对照上表手判（暂无自动分类脚本）。

## 门禁分级（preflight_release.py 判定口径）

> **分级口径以 `references/脚本速查.md` §1 为准**（**三档判定 critical / warning / 只登记 + 一类处置可豁免**，该表为完整枚举，两处必须同源）。先分级，再决定是「改」还是「豁免」：critical 只能改；warning 可带理由豁免并留痕。

### 挡发布 vs 只报告（两条分界线）

> **内容瑕疵 ≠ 产物不可用。** 话术写得啰嗦不该把发布卡住；脱敏没过必须卡住。
> **判据一句话**：这一项不修就发出去，会不会坏？会坏 ⇒ 挡发布；能用 ⇒ 只报告。

| 分档 | 判据 | 例 |
|---|---|---|
| **挡发布** | 发出去会产生不可逆后果、或被平台直接拒收 | 敏感信息命中、缺 LICENSE `Copyright (c)` 行、frontmatter 必填字段缺失、必含文件缺失或目录为空 |
| **只报告** | 能用，只是不够好；修不修都不改变本次可发布性 | 话术啰嗦、description 字段排序、`references/` 深层面措辞命中（自用档）、references 路由句式非强式、章节引用「未判定」 |

> ⚠️ **别把工具的 warning / 只登记误升为「挡发布」**。按 `preflight_release.py` 的实现：`version 低于已有 tag` 是 **warning 级**（豁免 key `version_tag`，退出码 0），`包内含 README` 是**只登记**（不计入判定），二者默认都不阻断。上面两档是**人工判读的分档**——本表管「这次要不要顺手修」，preflight 的 critical / warning 管「命中后阻断还是可豁免」，`--strict` 只是把 warning 升为 FAIL 的开关。

- **只报告的项仍要登记**：不登记等于没查，「查了没发现」与「没查」必须可区分。
- **分档不等于豁免**：只报告是「本次不阻断」，不是「这项不重要」；同一项反复只报告，说明该回头修规则了（见下文「门禁可信任度」）。
- ⚠️ **只在发版那一刻开 `--strict`**（它把 warning 升为阻断），平时不要常开。

**逐文件豁免（只对 `references/` 深层面开放）**

```
--waive dev_process@references/<文件名>.md --reason "主题即规则：该文档正文必须引用被禁词本身"
```

- 路径**必须真实存在**（不存在即 `rc=2` 报错，不许静默豁免 0 处）；
- **版本档案不接受逐文件豁免**（它属第一读者面，恒判）——想放行就改文本；
- **第一读者面**（`SKILL.md` / `README` / 版本档案）同理：`dev_process` 的逐文件语法只覆盖 `references/` 深层面。
  全局的 `--waive dev_process` 仍可用，但**会把第一读者面的命中一并放行**（报告里会明说）。
- 留痕件 `.preflight-waiver.json` 里每项带 `suppressed_hits`（真实处数）与 `waiver_state`；
  `休眠` 表示本次零命中——**豁免没生效或问题已修完，复核后删掉**，别把它当"已处理"。
- **豁免会在结果行里披露，`--quiet` 下也看得到**：`… ｜ 豁免 N 项（休眠 M）`，
  用了全局 `dev_process` 再追加 `；dev_process 全局豁免连带放行第一读者面 X 处`。
  判据取自**生效的豁免集合**（含 `--waive-file` 读进来的）——CI 里最隐蔽的形态正是
  「命令行一片干净、全局豁免从留痕件继承」，**所以不要只 grep 命令行**。

```bash
# 豁免：--waive 可多次传入，--reason 必填（无理由豁免 = 无审计，直接报参数错误 exit 2）
python3 scripts/preflight_release.py . --platform skillhub --strict \
  --waive localpath --waive email --reason "文档示例路径，非真实个人信息"

# 向后兼容：--skip-ownership 保留为 --waive ownership 的别名，但不落盘
python3 scripts/preflight_release.py . --skip-ownership
```

- **critical 拒绝豁免**：`--waive openai_key` 之类直接报参数错误（exit 2）。真敏感只能删 + 轮换，豁免口子不给它留。
- **落盘审计**：豁免写入 `<目标目录>/.preflight-waiver.json`，记录 项 / 理由 / 时间 / 操作者 / 版本号。打包脚本**已自动排除该文件**（默认路径不必手动删）；**走目录直发时会一起上传**，该路径下发布前须删掉——留痕件里的操作者字段是本机用户名，属个人信息，不该随包外发。复用已有留痕用 `--waive-file`（只读，不写盘）。
  ⚠️ **不带这个参数，磁盘上的留痕件不会被读**——豁免只从 `--waive-file` 进 `waived` 集合，不扫同目录的 `.preflight-waiver.json`。忘了带就会看到「已豁免」行整段消失、原本豁免过的命中重新计入阻断、整轮判 FAIL（已发生过多次）。**判据：报告里出现「已豁免: dev_process@…」行才算生效**；没这行就是没加载。
- **FAIL 必带修复指引**：每条 critical 后面跟一行「修：…」，`--quiet` 下也照样打印（CI 里只看见 FAIL 却不知道改哪儿，等于门禁在制造噪音）。
- ⚠️ 规范里的「frontmatter 建议字段」当前**脚本无独立检查项**：必填字段缺失按 critical 判 FAIL，非必填的建议字段缺失不产生任何告警——这是规范口径，不代表脚本现状。

### 门禁可信任度：误报率必须 < 10%

> **门槛线的误报率（假阳性率）必须 < 10%，否则等于没有门禁**。

**怎么统计**：每次 `--strict` 跑完，人工过一遍输出，数两个数——「命中总数」与「其中确实是问题的条数」；**误报率 = 误报数 ÷ 命中数**。命中数太少（不足一屏）时先攒样本，不要拿三五条就下结论。

**阈值与动作**：

- **误报率 > 10%** → **先修规则，再谈合规**。停下发布动作，回到规则本身：模式是不是缺数字边界、是不是拿本技能的语境当通用基准、是不是把合法写法当成了违规。
- **不要**用逐条 `--waive` / 白名单压噪音——豁免只给「确属误报的零星个例」，**误报要修规则**。

> 误报率一高，执行者只会学会无脑豁免或跳过门禁——比没有门禁更糟，它制造「已检查」的错觉。

**新规则上线前先拿存量样本跑一遍**：首跑若出现批量命中、而逐条人工核对后**全部为误报**——零真问题却批量命中的规则，装进发布链之前先收窄。

## 失败降级路径（失败点 → 降级动作）

> 失败先查本表：多数失败有既定绕法。

| 失败点 | 降级动作 |
|---|---|
| SkillHub 400「不允许的文件类型: LICENSE」 | 改走 `make_skillhub_zip.py` 打包后发 zip（脚本已排除四类，见 `references/脚本速查.md` §2）；同版本已占用则 bump 后再发 |
| 同版本已存在 | **bump 版本号后重发**，禁止删库重来 |
| 预检 critical 不通过 | 修复后重跑（真敏感命中不得豁免，见上文「门禁分级」） |
| 预检 warning 需放行 | `--waive <项> --reason <文本>`（可多次传入）落盘留痕后继续；key 与分级见上文「门禁分级」 |
| 安全扫描挂起 / download 404 | 以 publish 返回 `tags.latest` 为准，扫描队列异步等待（见下文「发布后验证」） |
| `git push` 报 HTTP2 framing / 空回复 | 清空代理变量并降级 HTTP/1.1（见下文「GitHub 推送踩坑」）；仍失败用 `gh api` Contents API 兜底 |
| GitHub tag 推送后发现版本错 | **不可删**——bump 到下一版本重发并公告；禁止临时关闭 ruleset |

## 归属与权益（三档判定）

| 档位 | 必做动作 |
|---|---|
| 已发布自研 | author + LICENSE `Copyright (c)` 行 + homepage 仓库 URL **三处一致**且仓库真实存在；提交用签名密钥 |
| 未发布自用 | frontmatter 预留 author/homepage 元数据即可，LICENSE 可后补 |
| 第三方安装 | **不碰**——不改 author、不标自己为版权人 |

### 合并发布者（发布者 ≠ 作者）

三档判定默认「作者 = 发布者」；**转手发布**（合并上游 AI 产包后由下游发布）时这一假设失效。此时：

- **diff 通过 ≠ 语义合规**：合并 diff 只证明「改动本身」没冲突，证明不了上游产包的内容表述可发布。
- **上游产包一律按「新内容」走三视角语义通读**（清单 12 / `SKILL.md` §七 步骤 2），**不得**因「上游已有 preflight PASS」降级——preflight 只覆盖结构/引用/凭据/大小等机械属性，语义层面的点名/贬损/倾向无从判定，两者是正交维度。

发布前 5 分钟：预检（Copyright 为 critical 必拦；author 为 warning，需强约束用 `--strict`）→ homepage `gh api` 可达 → 三处一致 → 确不需归属时 `--skip-ownership` 并声明理由。

## GitHub 推送踩坑（透明代理环境）

环境存在 `HTTP(S)_PROXY=127.0.0.1:<port>` 透明代理时，`git push` 会报
`Error in the HTTP2 framing layer` 或 `Empty reply from server`。

**方案**：推送时清空代理变量并降级 HTTP/1.1（命令见上方「5) GitHub 发布」）。
`gh` 子命令本身不受影响，可正常走代理；只有 `git` 的 HTTPS 传输会挂。

⚠️ **补充：清代理这条路并非总成立。** 若本环境**直连出口被封**（清掉代理后报
`Failed to connect to github.com port 443 ... Couldn't connect to server`），则清代理只会把
「502」换成「连不上」，两头都不通。此时**不要再试任何 `git` 传输**，直接走 API 兜底：

- **首选 `gh api` Git Data API 单次提交**（blobs → tree → commit → put ref）：一次干净提交，
  历史不碎；适合「已有至少一个提交」的仓库。⚠️ `gh api` 的 POST **必须显式带
  `-H "Content-Type: application/json"`**，否则 `git/blobs` 回 **422 Validation Failed**
  （错误信息不含原因，极易误判为内容过大）。
- 备选 `scripts/gh_push_files.py`（Contents API 逐文件 PUT）：**空仓唯一可行**（Git Data API 对空仓回 409），
  但**一文件一提交**，且会把未改动的文件也各推一个提交 ⇒ 只在空仓初始化或极少量文件时用。

⚠️⚠️ **伴随风险**：`git` 传输挂掉时 **`git fetch` 同样挂** ⇒ 本地的
`origin/*` 是**过期引用**。此时执行 `git reset --hard origin/main` / `git checkout origin/main`
**不会报错**，而是把工作区**静默回退到旧提交、丢掉未推送的改动**。
**铁律：`git fetch` 未成功返回前，禁用一切基于 `origin/*` 的 reset / checkout。**
回退后若远端内容才是对的，用 `gh api .../git/blobs/<sha>` 逐文件拉回并**校验 blob SHA**（`sha1("blob <len>\0"+content)`）确认一致。

**签名配置（= 发版签名开关；无全局 `~/.gitconfig` 时按仓库设置）**

签名材料（私钥 + `.pub` + `allowed_signers`，**同一把**）放在你自己的密钥目录里，**不一定在 `~/.ssh/`**。
⚠️ **别只去 `~/.ssh/` 找**——那里通常只有登录用的密钥（指纹不同）；只按「git 签名密钥」去 `~/.ssh/` 找，会得出「签名做不成」的错误结论（实际是找错了地方）。

```bash
# 全局只配格式、密钥与 trust anchor；**故意不设 commit.gpgsign**
git config --global gpg.format ssh
git config --global user.signingkey <签名私钥路径>
git config --global gpg.ssh.allowedSignersFile <allowed_signers 路径>
# 发版时**按仓**开启（或每次显式 -S / tag -s）—— 不设全局开关是为了
# 不让第三方上游仓（clone 来的项目）的提交被误签
git -C <repo> config commit.gpgsign true
git commit -S -m "..."                 # 或每次显式 -S
git tag -s vX.Y.Z -m "..."             # 版本 tag 同样要签
```

⚠️ **重签已发布的 commit / tag**：必须临时把 tag 保护 ruleset 置 `disabled`（**该 `evaluate` 模式在部分仓库 plan 上不可用**，用它会得到 422），改完立刻恢复 `active`；且验证保护是否生效请用**可牺牲的探针 tag**，不要拿真版本 tag 试删 —— 试删会连带把 GitHub release 降成 `draft`。

**验签**（本环境 curl 直连 github.com 返回 HTTP 000，勿用 curl 判可达）：

```bash
gh api repos/<owner>/<repo>/commits/main --jq '.sha[0:7] + "  verified=" + (.commit.verification.verified|tostring) + "  " + (.commit.verification.reason // "-")'
# 期望: verified=true  valid
```

## 发布后验证：等扫描队列

SkillHub 发布成功 ≠ 立即可验证。平台返回 `securityScanStatus/reviewStatus: pending` 期间：

- `skillhub install <slug>@<ver>` → 下载端点 HTTP 404
- `skillhub search <slug>` → 索引无精确匹配（被模糊结果淹没）
- `skillhub verify <slug>@<ver>` →「找不到该版本」

**判据**：以 publish 返回的 `tags.latest` 与 `skillId` 为准，扫描通过后再补验。

```bash
# 查扫描状态（securityReports 下按平台返回的 key 逐个看；两家扫描器都通过才放通下载，key 名以平台实际返回为准）
TOKEN=$(skillhub auth token)
curl -s -H "Authorization: Bearer $TOKEN" "https://api.skillhub.cn/api/v1/skills/<slug>" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print({k:v['status'] for k,v in d['securityReports'].items()})"

# 通过后补验（先装到临时目录，勿污染技能目录）
skillhub --dir /tmp/sh_verify install <slug>@<ver>
skillhub --dir /tmp/sh_verify verify <slug>@<ver> --json   # ok=true 退出码 0
```

**板块归属**：`publish` 固定发到社区源（`source: community`，即 Skill 板块）；
插件板块属另一发行渠道，CLI 无此选项，`skh_` 个人 token 不会误发。

| SkillHub 拒收 `.log` / `.enex` | 平台文件类型白名单比文档认知更窄：评测产物 run.log、Evernote 夹具 .enex 均报 400「不允许的文件类型」，且 400 逐文件报、一次只报一个 | 发布前清 evals/case-\*/output/ 与 benchmark.json（可再生产物）；含 `.log`/`.enex` 等非常规扩展名的资产（evals fixture）走「SkillHub 不带、GitHub 全量带」策略——临时移出目录发布后还原。⚠️ 别给「SkillHub 侧应含几个文件」写死数字：白名单随平台迭代变化，**按类核对**（入口 `SKILL.md` + `scripts/` + `references/` 全部 md，逐类对平台文档），写死个数必然随版本过期 |
| `git push` **各种姿势全败**，误判为「网络彻底不通」而放弃发布 | 上一行的代理降级只治 HTTPS 传输层；当透明代理把三种姿势（直连 / 清代理变量 / 降 HTTP/1.1）**全部**拦掉时，`git` 侧已无路可走 | **判据：`gh` 子命令仍可用 ⇒ 断的不是网络，只是 git 的传输通道**。此时换通道而不是反复重试——`scripts/gh_push_files.py` 走 GitHub Contents API 推送目录（命令与适用边界见 `脚本速查.md` §6）。三轮重试不成功即转兜底，别把「再试一次」当方案 |
| 用 Git Data API 在**空仓库**建 blob 报 `409 Conflict` | Git Data API 的建树/建 blob 假定仓库已有至少一个提交；新仓库尚未 init 时无父提交，blob 无处挂 | 先走 Contents API 提交一次完成初始化，再切 Git Data API；或**直接用 Contents API 全程推送**（本技能 `gh_push_files.py` 即此路线，天然不踩该坑）。读外部素材若见 Git Data API 方案，先确认它是否附带了空仓库初始化这一步 |
| `python3 -m py_compile scripts/*.py` 做语法检查后，preflight 报 **`scripts/ (6 个文件)`**（实际只有 3 个） | `py_compile` 会就地生成 `scripts/__pycache__/*.pyc`；preflight 的文件计数**不过滤缓存目录**，于是把编译产物算进了包体 | **顺序问题**：语法检查 / 脚本自测 → **先清 `find . -name __pycache__ -exec rm -rf {} +` 与 `*.pyc`** → 再跑 preflight 与打包。`make_skillhub_zip.py` 会排除 `__pycache__`，但**目录直发路径不排除**（同 LICENSE 那条坑的同一根因）；计数异常先看有没有缓存目录 |
| `gh skill publish` 子命令不存在 | 多份流程文档把它当作 GitHub 发布入口，实际 CLI 只提供 `install` / `list` 一类子命令，调用直接报未知命令 ⇒ 照抄文档会卡在发布链最后一环 | GitHub 发布走 `gh repo create` + `git push` + `git tag -s`（命令见「一键执行顺序」第 5 步）。凡文档里出现 `gh skill publish`，一律按失效处理 |
| **对外包的版本说明写成了开发口径** | Changelog 的读者是使用者，开发口径不该出现；若该检查只覆盖 SKILL.md / README.md，而 `references/` 被整片豁免、版本档案恰好躺在 `references/` 下 ⇒ **结构性放行、必然 PASS**（立规者未自守：规矩写在文档里却没有检查实现，就只能靠自觉） | ① 版本档案与 `references/` 已一并纳入检查面，且**本技能自身必须通过同一检查**；② 另查「**写作规则自曝**」——在对外文本里声明「这份说明是过滤给谁看的」，等于告诉读者另有一版内部记录；③ 凡「规范要求 X」必同时问「有没有检查实现 X」，**只有文档的要求等于没有要求** |
| frontmatter 值含 `: `（未加引号）⇒ 整份 frontmatter 解析失败 | YAML 里 `key: Core rule: a checker` 这种**裸冒号 + 空格**直接报 `mapping values are not allowed`；而平台侧只表现为「元数据读不出来」 | preflight 的「**frontmatter 引号卫生**」覆盖此形态（对所有 key，不只已知字段），但它是 **warning 级**⇒ **发布必须带 `--strict` 才会阻断**。⚠️ 它**不等价于真正的 YAML 解析**（缩进 / 嵌套非法抓不到）；本包零第三方依赖、不内置 pyyaml，要更强保证请自行在发布机上跑一次真解析。含英文冒号的值即使加引号也可能被平台按首个冒号截断（症状是「技能莫名不触发」），同样要改写成不带冒号的表述 |
| `gh` 操作注入 `GH_TOKEN` 后报 `403 Resource not accessible` | 环境里那把 token 权限不足（如无 release 写权限），却**覆盖了 gh 自带 keyring 里的可用凭据** ⇒ 本来能成的操作反而失败 | **先看 `gh auth status` 的 scopes，再决定用哪套凭据**；不要盲目注入 `GH_TOKEN` 覆盖 keyring。keyring 凭据够用时，直接让 `gh` 用它 |
| tag 保护 ruleset **建了但形同虚设** | `conditions` 为空时**不匹配任何 ref**（不是「对所有 ref 生效」），删 tag / 强推全部不被拦；创建接口照样返回成功，脚本也不报错 ⇒ 只能靠出事才发现 | 建 ruleset **必须显式写** `conditions.ref_name.include=["refs/tags/*"]`（`v*` 这类写法会 422，要写完整 ref 语法）；建完**回读 conditions 自证非空**。`scripts/setup_gh_ruleset.py` 已改成强制写入 + 回读自证 + `--list` 标注空 refs；验保护要用**可牺牲的探针 tag**，别拿真版本 tag 试 |
