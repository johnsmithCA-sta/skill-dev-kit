# 版本说明写作模板

> 从社区通行实践提炼并收敛为可直接套用的模板：主流开源项目的 Changelog 约定（分类与原则）/ 若干项目的贡献指南（收录判据）/ 代码评审笔记（条目粒度）/ Stripe 与 GitHub 的 release notes（具体化写法）。
> 判据始终只有一条：**读的人能不能看懂「这次我能得到什么」。**

## 一、收录判据：什么进、什么不进

先决定"这条要不要写"，再决定"怎么写"。

**进**（用户可见的变更）

- 新增能力、行为变化、边界调整
- **修复类必须进**——用户正是靠这一栏判断「我上次遇到的那个毛病好了没」
- 安全相关修复（可单独成节）
- 破坏性变更（**必须**写，并给迁移方向）

**不进**（对使用者无价值的内部动作）

- **纯开发者向变更**：重构、技术债清理、测试套件调整、依赖锁文件更新
- 同一版本内"引入又立刻修掉"的回归
- 实验性 / 未定型的内部尝试
- 纯文档、纯注释、纯格式变更
- 内部统计与过程口径（覆盖率、体积、命中数、文件数、脚本数）

> 拿不准时问一句：**使用者会因为这条改变他的使用方式或预期吗？** 不会，就不写。

## 二、四类条目模板（日常迭代用这套）

| 类型 | 公式 | 例 |
|---|---|---|
| 新增能力 | `新增 <能力名>，支持 <场景 / 输入>` | 新增批量体检：一次给一批对象跑完同一套检查并汇总成对照表 |
| 优化体验 | `优化 <对象>，<读者能感觉到的变化>` | 优化中断恢复：中途中断后重跑，已取到的内容不会重复获取 |
| 修复问题 | `修复 <读者会遇见的错误现象>` | 修复切换任务后旧错误提示仍然出现的问题 |
| 调整边界 | `调整 <对象> 的行为，<变化点>` | 调整浏览器收尾：只关闭本次任务自己打开的窗口 |

**破坏性变更**（MAJOR）追加一行迁移方向：

```
- 调整配置格式，由 YAML 改为 TOML。升级前请按 `references/迁移说明.md` 转换既有配置文件。
```

**首版发布**（0.1.0）用一段说清"它解决什么、给谁用、怎么开始"，不必分四类。

## 三、一行公式（每条都按这个尺子量）

```
【动作词】+【对象】+【读者感知到的结果】
```

- **动作词**用祈使/现在时：新增 / 优化 / 修复 / 调整 / 移除（不要"新增了""已优化"）
- **一条一行说完**，最多两句；不嵌套、不编号、不用「① ② ③」
- 同名对象在多条出现时，写法保持一致

## 四、量化：什么时候能写数字

**能写**——**读者能直接感受到的效果**：

- `扫描耗时从约 2 MB/s 提升到约 10 MB/s`（体感：以前要等半小时，现在几分钟）
- `单次处理上限由 3 个提高到 9 个`

**不能写**——只有维护者关心的数字：

- 内部分子分母：`检查项覆盖率由 N% 提升到 100%`、`该字段长度由 N 字符压缩到 M 字符`
- 内部统计量：`命中 N 处`、`文件数 N → M`、`脚本数 N → M`、`其中真实命中 N 处 / M 种`
- 任何需要先理解内部机制才看得懂的量

> 分歧点就在这：**「提速 5 倍」可以留，「改用了什么算法 / 什么库」必须删**。前者是结果，后者是实现。

## 五、三问过滤法（写完逐条自检）

1. **用户会遇到吗？** 不会 → 整条删（属于"不进"那一类）。
2. **一句话能说清"我能得到什么"吗？** 说不清 → 说明还在讲实现，回去重写。
3. **有没有实现词？** 有 → 换成结果。实现词清单见下一节。

## 六、禁用的词与写法

**字面禁用**：函数名 / 类名 / 正则表达式 / 内部字段名 / 行号 / 内部任务编号 / 内部评审方名 / 内部文档名（书名号）/ 内部渠道与平台名 / 本机路径

> ⚠️ **两个高频误判，别一刀切**：
> - **脚本名 / 命令名该留**——它是**使用者要敲的命令**（`新增「依赖自检」：跑 `check_deps.py` 即可核对环境`），属使用者界面。**要删的是函数名、类名、正则写法、行号**这类只有维护者才用的标识。
> - **领域词不算治理词**——`统计口径` / `支出双口径` / `脱敏字段口径` 是**业务概念**，该留；`版本口径` / `事实源` / `口径对齐` 才是讲维护流程的治理词。

**写法禁用**：

| 写法 | 为什么禁 |
|---|---|
| 「原实现是 X，现改为 Y」 | 讲怎么修，不讲修好了什么 |
| 「因接入 X 而新增」 | 内部动因；读者只要知道能力 |
| 「重构 / 口径 / 事实源 / 对齐 / 收口 / 落地」 | 治理词，读者看不懂 |
| 「本次实测 / 当天发现 / 复盘后」 | 过程叙述，不依赖"本次"才能成立的才是规则 |
| 「未发布 / 审核中 / 平台版停留在 x.x.x」 | 发布节奏自曝，读者只关心"这版我能得到什么" |
| 「（用户侧口径）」「只写使用者能感知的变化」 | 写作规则自曝，等于告诉读者另有一版内部记录 |
| 「本仓真实案例」「我们自己的反例」「结合本仓踩过的坑」 | 自我指涉——等于告诉读者这些错是我们犯过的 |

## 七、正反例对照

下表左栏写的是**病灶形态**，不是任何真实条目的原文——照病灶形态自查，别去对照某条具体的旧文案。
> ⚠️ **反例本身也会自曝**：把"要禁掉的那句真实文案"原样抄进来当反面教材，等于换个地方把它发布出去；同理，模板里也不写「这是我们的真实案例」。左栏只用**抽象形态**描述病灶。

| 病灶形态（别写） | 改成（用户可感知） |
|---|---|
| **讲实现**：先说原本用了什么算法 / 什么库 / 哪个分支反复试探，再说改成了什么 | 只写改善结果：`大文件处理速度明显提升——GB 级日志此前要数十分钟，现在只需数分钟` |
| **讲内部规则**：把规则的匹配细节、命中条数、阈值调整过程写出来 | 只写现象：`修复误报——把正常字段名误判为凭据值；公钥文件被误报为凭据泄漏` |
| **内部统计量**：覆盖率 / 体积 / 命中数 / 文件数等分子分母，或"扣掉误报后真实命中 N 处" | 整条删——使用者无感 |
| **说架构动作**：`重构 X 模块为 Y 架构`、`用某机制替换某机制` | 说它带来的能力变化：`兜底通道不再只认一个代码托管平台` |
| **括号塞实现**：`新增 X 检查（正则命中 N 类词）` | `新增一项：<何时会提示什么>` |
| **工具内部指标**：`扩展了输入缓冲区` / `Strip out nils in the array` | 说清上限或结果：`单次可处理的内容上限提高到 512KB` / `修复特定条件下大量报错的问题` |

## 八、版本段落与文件结构

```markdown
# <技能名> 版本发布说明

## <版本号> 版本发布（YYYY-MM-DD）

- 一条一行
- 一条一行

## <更早版本号> 版本发布（YYYY-MM-DD）

- …
```

- 一个版本一段，**最新在最上**；标题只写版本号与日期，不写「未发布 / 待同步」
- 日期用 `YYYY-MM-DD`（ISO，无歧义）
- 分类用二级标题（`### 新增` 等）**仅在条目超过 8 条时**才用；日常迭代直接平铺列表更好读
- 只保留**用户可感知部分**；问题机理、修复过程、内部分析留开发侧档案（不入包）

## 九、发布前自检（逐项打勾）

- [ ] 每条都能让**零上下文读者**看懂"我能得到什么"
- [ ] 没有脚本名 / 函数名 / 正则 / 字段名 / 行号 / 内部编号 / 内部文档名
- [ ] 没有「原实现…现改为…」这类实现叙述
- [ ] 留下的数字都是读者能感受到的；内部分子分母与统计量已删
- [ ] 修复类**保留**了（没有因为怕提问题而整条删掉）
- [ ] 破坏性变更有迁移方向
- [ ] 没有「未发布 / 审核中 / 平台版停留在…」这类发布状态
- [ ] 没有「（用户侧口径）」这类写作规则自曝
- [ ] 版本段落标题只有版本号 + 日期
