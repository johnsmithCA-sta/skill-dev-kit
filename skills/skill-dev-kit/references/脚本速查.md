## 1. preflight_release.py — 发布预检

发布前一键检查 9 节：敏感信息扫描 / frontmatter 字段校验 / 必含文件 / git 未跟踪文件告警 / 归属检查 /
§ 章节引用校验 / 版本与 tag 一致性 / 评测宣称—证据一致性 / **结构规范检查**。
其中第 6–8 节与第 9 节的告警项，均属「目标平台不校验、但应当满足」的规范项，一律 warning 级。
⚠️ **「节」与「检查项」是两套数，别互相套用**：「节」指脚本输出的 9 个分段（含只登记的信息级）；「检查项」指实际判定的项（另做**六项**：归属检查 / name 规范 / 正文体积 / § 章节引用 / 版本与 tag / 评测宣称一致性，**加**结构规范检查）——**name 规范与正文体积不在「9 节」里**，它们属于「另做六项」。逐项清单以本节表格与 `references/发布检查清单.md` 为准。

**第 9 节 · 结构规范检查**（10 项能力，分两档）：

| 档 | 项 | 判据 |
|---|---|---|
| 告警（`--strict` 阻断） | 引用完整性 | SKILL.md 正文反引号内的 `scripts/` `references/` `evals/` 路径是否存在 |
| 告警 | description 触发面 | 复用 `eval_trigger.py --desc-check`：自称构式 / 动作动词 / 排他边界 / 触发词示例 |
| 告警 | 保留词 | frontmatter 不得含 `claude` / `anthropic`（正文提及官方文件名不受限） |
| 告警 | 引号卫生 | frontmatter 值含裸冒号 / 英文冒号 / 未加引号的多行纯量（跨解析器会被截断） |
| 告警 | **打包卫生** | 包内不得有 `.bak` / `.tmp` / `~$*` / `.swp`——这类扩展名不在打包脚本排除名单里，**会真被发出去** |
| 只登记（不判定） | 无 README · 孤儿引用 · references 元数据 · 索引体量漂移 · **路由表缺 doNotUse 列** | 不影响技能使用，只打印 `-` 行，不进退出码 |

```bash
# SkillHub 平台预检（默认）
python3 scripts/preflight_release.py <技能目录> --platform skillhub
# GitHub 平台预检（严格模式：低危告警也判失败）
python3 scripts/preflight_release.py <技能目录> --platform github --strict
# 静默输出（只打印结果行，便于 CI；FAIL 的修复指引照常打印）
python3 scripts/preflight_release.py <技能目录> --quiet
# 豁免告警项（可多次 --waive，--reason 必填）：落盘 <目标目录>/.preflight-waiver.json 留痕
python3 scripts/preflight_release.py <技能目录> --strict \
  --waive localpath --waive email --reason "文档示例路径，非真实个人信息"
# 向后兼容：--skip-ownership = --waive ownership 的别名（跳过归属检查，但不落盘）
python3 scripts/preflight_release.py <技能目录> --skip-ownership
```

- **退出码**：`0` = PASS（仅告警可放行）/ `1` = FAIL（存在高危）/ `2` = 参数错误（豁免了 critical 项、未知 key、或 `--waive` 缺 `--reason`）。
- **敏感分级**：`critical`（skh_/ghp_/sk-/AKID/COS secret/token 赋值/明文密码）→ 必然 FAIL 且**拒绝豁免**；`warning`（/Users 路径/邮箱/疑似密码/手机号）→ 默认仅告警，`--strict` 时 FAIL，可 `--waive` 豁免。

**门禁分级**（完整枚举，与 `references/发布检查清单.md`「门禁分级」同源）：

| 级别 | 项 | 默认 | `--strict` |
|---|---|---|---|
| **critical（阻断）** | 敏感信息命中（API key / 云凭据 / 明文 token / 明文密码赋值）、LICENSE 缺失或无 `Copyright (c)` 行、必含文件缺失或必含目录为空、frontmatter 必填字段缺失 / `version` 非 X.Y.Z | FAIL（exit 1） | FAIL（exit 1） |
| **warning（告警）** | author 缺失、**name 不符合 kebab-case 或与目录名不一致**、**§ 章节引用断链**、**version 低于已有 tag**、**声明了评测却无 `evals/`**、**引用完整性 / description 触发面 / 保留词 / 引号卫生 / 打包卫生**、本地路径 / 邮箱 / 疑似密码格式、git 未跟踪文件 | WARN（exit 0） | FAIL（exit 1） |
| **只登记** | 包内含 README / 孤儿引用 / references 缺加载元数据 / 索引体量漂移 / 路由表缺 doNotUse 列 | 打印 `-` 行，不计入判定 | 同左 |
| **可豁免** | warning 级全部 | `--waive <项> --reason` 落盘留痕后放行 | 同左 |

- **豁免 key**（稳定标识符，别拿中文说明当匹配键）：**全集 19 个**，与 `preflight_release.py --help` 同源（两者不一致时以 `--help` 为准），完整表见 `references/发布检查清单.md`。⚠️ **查 key 只认全集**——不完整的表会缺 key，照着查会以为 `dev_process` 这类 key 不存在。
- **敏感扫描降噪（自动豁免，无需 `--waive`）**：技能自身名及其片段、已声明的依赖包名、标准 HTTP 头 / CSS 厂商前缀、纯词形 kebab 串（每段全字母且有元音）不计为疑似密码；测试假号与低数字多样性号码、路径段形式的 11 位数字不计为手机号；`/Users/xxx`（`xxx`/`your`/`<…>` 占位）不计为本机路径。**同一命中串散在多个文件会折叠成一行汇总**（处数 + 文件清单）。
- **落盘**：`.preflight-waiver.json` 记 项/理由/时间/操作者/版本号；复用已有留痕用 `--waive-file <留痕件>`（只读，不写盘）。默认打包路径下脚本已排除该文件；只有目录直发会把它一起上传（见 §2）。
- **FAIL 带修复指引**：每条 critical 后跟一行「修：…」，`--quiet` 也打印。
- **归属检查（分级，恒开）**：源码目录 LICENSE 含 `Copyright (c)` 行 → **critical**（正则，兼容全角/©写法；LICENSE.md/.txt 自动识别）；frontmatter `author` 非空 → **warning**（可 `--waive author` 单独豁免，不影响 LICENSE 判定；`--waive ownership` 则整组跳过）。homepage 仓库真实性由人工/`gh api` 核验。
- **平台规范**：skillhub 需 frontmatter 含 name/slug/displayName/summary/description/version/license + SKILL.md/scripts；github 需 name/description/version/license + README/LICENSE/SKILL.md（支持 skills/<name>/SKILL.md 放宽）。
- **name 规范检查（warning 级）**：官方规范对 `name` 的硬线是「1–64 字符 / 小写字母·数字·连字符 / 不以连字符开头或结尾 / 无连续连字符 `--` / 必须与父目录名一致」。目标平台不校验这几条，属「应当满足」的规范项，故降为 warning，`--strict` 时才阻断——自建门禁严于目标平台会把正确写法误杀。规则来源见 `references/SKILL.md编写规范.md` §一。
- **§ 章节引用校验（warning 级）**：检查「…`某文件.md` §4.1」这类点明了目标文件的章节引用，目标文件里是否真有该章节。只判定**同行、紧邻 § 之前 40 字符内**写出目标文件名的形态——这是唯一能可靠解析目标的写法。按「同行最近的文件名」猜目标会双向猜错（把文件内自引用判成别的文件、把跨文件引用判成自引用），故一律不做。未写明目标的 § 引用只列清单交人工核对，不参与判定。
  - ⚠️ 刻意**不查文件路径存在性**：文档里合法地提到大量并不存在的文件名（写法示例、运行时产物、第三方锁定文件），路径口径的命中绝大多数是误报。
- **版本与 tag 一致性（warning 级）**：目录在 git 仓库内时读 `git tag -l "v*"`。**只拦版本回退**（`version` 低于最新 tag）；「尚未打 `v<version>` tag」属正常时序（预检跑在发布之前），只提示不告警。非 git 目录静默跳过。
- **评测宣称—证据一致性（warning 级）**：SKILL.md / README 里出现「评测闭环 / benchmark / 评估集 / evals/ / 触发词评估 / 回归重跑」等**已做评测**的声明时，校验 `evals/` 存在且非空；声明了却拿不出证据 → 告警。
  - 查的是「**说了没做**」，不是「有没有做评测」——目标平台不要求 `evals/`，多数技能也没做，判「没做」就是误杀（也与 `references/评测方法论.md` §1.1「无数据不得判 FAIL」相悖）。未做声明的技能完全不触发本项。
- **正文体积检查（warning 级）**：按规范 §2 口径现场核算 SKILL.md **正文**（不含 frontmatter）token 数，超硬上限 5000 即告警、`--strict` 时阻断；目标值 ~2000 只作参考不作红线。⚠️ 口径必须剔掉 frontmatter——含 frontmatter 会虚高数百 token，拿错的命令去比会把达标文件误报为超线。
- **打包卫生（warning 级，豁免 key `pack_hygiene`）**：扫技能目录（跳过 `.git/`）里有没有 `.bak` / `.tmp` / `~$*` / `.swp`。判据是「**它会不会被发出去**」——这四个扩展名**不在打包脚本的排除名单**（共四类，见 §2）里，所以会**真的进包**。缓存文件**不在扫描范围内**：它们出不了包，且门禁自身运行就可能生成，报了只是噪音。
- **references 加载元数据 · 强路由句式（info 级）**：除判「有没有 `加载条件` / `命中标签` 两个键」外，另统计键值是否为**强路由句式**——须同时含 ① 信号词（`当` / `若` / `if` / `命中` / `出现`）② 指向文件（含 `.md` 或 `references`）③ 时序词（`之前` / `before` / `先`）。三缺一即计为「非强路由句式」，只报计数、不逐个刷屏、不阻断（防误报）。
- **面向用户端写作（warning 级，豁免 key `dev_process`；`references/` 深层面可按文件豁免 `dev_process@references/<文件名>.md`）**：检查面 = **随包对外 markdown** —— 对外入口（`SKILL.md` / `README`）+ 版本档案（包内**任意深度**）+ `references/**` 的 markdown（含子目录与点目录、后缀不区分大小写）+ 包根其余 `.md`。**只对 markdown 文档负责**：非 `.md` 资产与 `evals/**`（评测夹具）**明示不承诺**（它们同样随包发布，这是口径，不是遗漏）。
  - **两档**：**第一读者面**（对外入口 + 版本档案）**恒判**——前者是使用者第一眼看到的、后者随市场页展示（summary），与这份包发不发布无关；**references 深层面**按 `--scope` 分档，`--scope release`（默认）进判定、`--scope local` 只登记。
  - **报告三行读数**：`目标 N 份 / 实查 M 份（第一读者面 x/N ｜ references 深层面 y/M）` —— **目标 ≠ 实查**，差值即「没读到的」（不存在 / 非 UTF-8）。另报 `frontmatter 段跳过 K 行`（入口与渐进披露元数据按约定不查；版本档案不跳）。
  - **豁免披露在结果行（quiet-proof）**：`… ｜ 豁免 N 项（休眠 M）`；用了全局 `dev_process` 时追加 `；dev_process 全局豁免连带放行第一读者面 X 处`。判据取**生效的豁免集合**（含 `--waive-file` 读入），不是命令行参数——**CI 里最隐蔽的形态就是「命令行干净、全局豁免从留痕件继承」**。
  - 查 §4.1 禁止的开发过程信息，但**词表只静态匹配 5 类**：版本归属标注 / 实测日期与过程 / 过程叙述 / 治理口吻 / 过程数字、写作规则自曝）。**§4.1 禁写表共 12 类，其余 6 类没有正则实现**（维护者指令 / 商业意图 / 受众说明 / 单一平台品牌绑定 / 变更来源与内部动因 / 内部踩坑表 / 发布状态自曝）⇒ 必须靠 `SKILL.md` §七 步骤 2 三视角通读与人工核对。**别把「脚本没报」读成「这几类没问题」**。
  - 词表按「新规则先跑存量、误报率 <10%」校准：存量技能上未出现误报。
  - 检查面含 `references/` 时，命中量会**显著上升**，且数字对口径高度敏感（含不含入口、含不含 frontmatter、跳不跳点目录，结果都不同）⇒ 启用「阻断」档之前**须按当前检查面重新标定阈值并留痕**。命中集中在两类：**主题即规则**的方法论文档（靠逐文件豁免）与**内部台账**（在 `--scope local` 下不判定）。
  - 误报仍存时用 `--waive dev_process --reason "..."`（⚠️ **全局 key 会把第一读者面的命中一并放行**；只想放行深层面请用逐文件语法）；**能力背书**（如「实测坐标常量零误报」）属 §4.1 允许保留项。
  - 留痕件里每项都带 `suppressed_hits`(真实处数) 与 `waiver_state`（`休眠` = 本次零命中，请复核后删掉）；`--waive-file` 的用途是让批量体检 / CI 与发布命令拿到同一结论。
  - ⚠️ **带 `--waive` 的调用会写技能目录**（只读复核场景：验收 / 审计请用副本并核对哈希）。
  - ⚠️ **在副本上复跑时，副本目录必须与本技能同名**：`preflight` 校验 `name` 与父目录名一致，副本目录名与原技能不一致时会得到一个与本次改动无关的假 FAIL，还会掩盖真正的检查项。
- **路由表 doNotUse 列（info 级，条件触发）**：仅当 SKILL.md 存在路由表（表头含 `路由` / `加载` / `场景`）时才查是否带 `不路由` / `Do NOT route` / `doNotUse` / `不建议路由` 列——路由表只写「该读什么」不够，还要写「千万别路由到哪」。无路由表的技能直接跳过，不报错。

## 2. make_skillhub_zip.py — 打包归档（SkillHub 发布的默认路径）

> **定位**：**发 SkillHub 走这一步**。目录直发（`skillhub publish <目录>`）由 CLI 直接收集文件、不做任何排除，LICENSE 会被平台以 400「不允许的文件类型」拒收 ⇒ 先打包、再发 zip。
> 目录直发**只在已人工确认**目录内无下列四类排除项时才用——直发等于把排除工作交给人工，打包则由脚本兜住。
> 其他用途：留档 zip、`--keep-license` 出 GitHub 包、无 skillhub CLI 环境下预生成上传包。

读 SKILL.md `version` 自动命名 `<顶层名>-v<version>.zip`，排除四类（目录 / `.pyc`·`.pyo` / `.DS_Store`·`.preflight-waiver.json` / LICENSE 与 README 系列名），校验 ≤10MB。

```bash
# 默认打包（自动版本命名，排除 LICENSE）
python3 scripts/make_skillhub_zip.py <技能目录>
# 指定输出路径
python3 scripts/make_skillhub_zip.py <技能目录> --out skill.zip
# 文件名不带版本号
python3 scripts/make_skillhub_zip.py <技能目录> --no-version
# 保留 LICENSE（仅 GitHub 用）
python3 scripts/make_skillhub_zip.py <技能目录> --keep-license
# 保留 README（离线归档 / 自定义包用）
python3 scripts/make_skillhub_zip.py <技能目录> --keep-readme
```

- **退出码**：`0` = 成功 / `1` = 失败（超 10MB / 无 version / 目录不存在）。
- **踩坑**：SkillHub 接口对包内 LICENSE 返回 400「不允许的文件类型: LICENSE」，故默认排除；License 由 frontmatter `license: MIT` 字段声明即可。**注意：目录直发路径不做任何排除** —— 改走本脚本打包后发 zip，就不必逐项人工核对。

## 3. setup_gh_ruleset.py — GitHub tag 保护

用完整 JSON body 经 `gh api` 创建 ruleset（规避 `-f/--input` 混用 422 坑），默认 tag 保护：禁止删除 + 禁止强制覆盖。

```bash
# 当前 git 仓库目录下运行（自动解析 owner/repo）；先打印将发送的 JSON
python3 scripts/setup_gh_ruleset.py --dry-run
# 实际创建（默认 pattern 为 `refs/tags/*`，即对全部 tag 生效）
python3 scripts/setup_gh_ruleset.py
# 列出现有 rulesets
python3 scripts/setup_gh_ruleset.py --list
# 显式指定仓库 / 名称 / 生效模式
python3 scripts/setup_gh_ruleset.py --repo owner/repo --name "Tag Protection" --enforcement active
```

- **退出码**：`0` = 成功 / `1` = 失败（同名已存在需手动处理 / gh 未认证）。
- **依赖**：`gh` CLI 已认证（`gh auth status`），仓库 admin 权限。
- **踩坑**：传 `pattern="v*"` 触发 422（需完整 ref 语法 `refs/tags/*`）；**必须显式写完整 ref 语法 `refs/tags/*`**——**空 conditions 不匹配任何 ref，等于没建**（不是「对所有 tag 生效」）。

## 4. eval_trigger.py — 触发词评估

对标官方规范里的「description 触发词优化」：生成 should-trigger / should-not-trigger 评估集，并静态检查 SKILL.md 触发词覆盖率。

```bash
# 生成评估集模板（should + should-not 各 N 条，人工/LLM 审阅扩充）
python3 scripts/eval_trigger.py <技能目录> --gen --count 20
# 静态检查触发词覆盖率（默认动作，正文「触发词」口径）
python3 scripts/eval_trigger.py <技能目录> --check
# 两侧同时验（覆盖率 + description 质量）；退出码取较严一侧
python3 scripts/eval_trigger.py <技能目录> --check --desc-check
# description 口径评测（平台真实路由行为：自动发现只看 description）
python3 scripts/eval_trigger.py <技能目录> --check --from-description
# 注入外部意图清单（判定基准由你提供，工具不替你编）
python3 scripts/eval_trigger.py <技能目录> --check --intents my_intents.json
# 留出集验证（防过拟合；推荐：留出 40%，重复 3 次独立切分看稳定性）
python3 scripts/eval_trigger.py <技能目录> --check --holdout 0.4 --reps 3
# 注入本域场景词（desc-check 时避免"未识别到场景"误报）
python3 scripts/eval_trigger.py <技能目录> --desc-check --scene-words my_scenes.txt
# 自定义阈值（默认 0.7）/ 宽松匹配最短触发词长度（默认 3）
python3 scripts/eval_trigger.py <技能目录> --check --threshold 0.8 --min-trigger-len 3
# 指定评估集输出路径
python3 scripts/eval_trigger.py <技能目录> --gen --out evals.json
# 校验 description 本体质量（FAIL 级 2 项 + WARN 级 5 项，共 7 项）
python3 scripts/eval_trigger.py <技能目录> --desc-check
# WARN 级也计入失败
python3 scripts/eval_trigger.py <技能目录> --desc-check --strict
# 直接校验给定描述文本（快速试错，无需技能目录）
python3 scripts/eval_trigger.py . --desc-check --desc "Helps with documents"
```

- **退出码**：`0` = PASS / `1` = FAIL（覆盖率不足且有未覆盖意图，或 desc-check 命中 FAIL 级项）/ `2` = REVIEW（覆盖率达标但有遗漏；**或没有评估集 / 没有触发词章节**——无数据不等于不合格，绝不给 FAIL）。
- **原理**：解析 SKILL.md「## 触发词」章节（一行内 `A / B / C` 会拆成独立触发词），与意图清单做归一化比对。命中两个方向：意图整句被测触发词包含（强）；或触发词是意图的实质子串且长度 ≥ `--min-trigger-len`（弱，默认 3，防止 2 字泛词虚高覆盖）。
- **双口径**：正文口径查「触发词写全了没」；`--from-description` 把整段 description 作为判定源，查「平台能否把用户说法路由过来」（自动发现只看 description）。两个口径回答不同问题，**不共用一把尺**；技能无「触发词」章节时不再静默降级——会提示改用 description 口径或补写章节。
- **意图清单三级回退**：`--intents` → `<技能目录>/evals/trigger_eval.json` → **无（→ 退出码 2 + 操作指引）**。工具不自带"通用意图表"。
- **desc-check 分级（共 7 项）**：FAIL 级 2 项（自称构式 / 无动作动词）命中即不合格；WARN 级 5 项（缺场景 / 含 how / 缺排他边界 / **缺触发词示例** / **含流程摘要**）默认只提示，`--strict` 才计入失败。规则来源见 `references/SKILL.md编写规范.md` §七。
- **值可跨行**：`--desc-check` 读 description 时会按 YAML 纯量规则把缩进续行折成一行——只取首行会让校验建立在残缺文本上（诊断指向错误的原因）。
- **留出集（防过拟合）**：`--holdout <比例>`（默认 `0` 关闭，推荐 `0.4`）按固定种子确定性切分意图清单为训练集 / 留出集，两侧分别报覆盖率，**判定以留出集为准**——只用同一批意图调 description，等于拿考过的题当考试。留出集不足 2 条时退出码 2（REVIEW，先扩量）。
- **重复采样**：`--reps <次数>`（默认 `1`，推荐 `3`）重复 N 次独立留出切分（种子 0…N-1），输出留出集覆盖率的**均值 ± 标准差**；标准差偏大（>15 个百分点）说明评估集切分不稳，对策是**扩量**，不是继续调措辞。⚠️ 静态工具的口径：它衡量的是**评估集切分稳定性**，不是模型随机性——「同一条 query 跑 N 次求稳定触发率」需要真实调用通道，**当前未实现**。
- **⚠️ 已知边界**：动词表、场景提示词都是封闭集合，域外写法可能误判。判定为 WARN/REVIEW 的项一律需人工确认，不可当作"已通过"。

## 5. eval_loop.py — 评测循环

对标官方规范的评测循环编排（run_eval + aggregate_benchmark）：with-skill vs baseline 对比 + 断言评分聚合为 benchmark.json。

> ⚠️ **双跑需人工编排**：脚本不自动派发两臂——`with_skill` 与 `baseline`（或旧版）两种运行要人工并行发起，各自产出到用例目录后分别 `--aggregate`。自动双跑**当前未实现**，详见 `references/评测方法论.md` §1.7。

```bash
# 执行各用例 run_cmd.txt 并聚合（目录约定见下）
python3 scripts/eval_loop.py <evals目录> --run --aggregate
# 仅聚合已有 grading.json → benchmark.json
python3 scripts/eval_loop.py <evals目录> --aggregate
# 指定聚合输出路径
python3 scripts/eval_loop.py <evals目录> --aggregate --out bench.json
# 只统计指定扩展名的产物（默认按内容探测读全部非二进制文本）
python3 scripts/eval_loop.py <evals目录> --aggregate --exts .md,.txt
```

**目录约定**（每个测试用例一个子目录）：

```
evals_dir/
├── case-01/
│   ├── eval.json        # {"prompt":..., "assertions":[...]} 断言=期望输出应包含的要点
│   ├── run_cmd.txt      # 可选：执行命令，产物写入 output/
│   ├── output/          # 运行产物（带技能）
│   ├── baseline/        # 基线产物（不带技能）——**会被判分**，产出 with_skill/baseline/delta 对照列
│   └── grading.json     # 评分结果：{"assertions":[{"text":..,"pass":true,"evidence":..}]}
└── case-02/ ...
```

- **退出码（三态）**：`0` = PASS（均分 ≥0.7，可放行）/ `2` = REVIEW（均分 <0.7，**或未产生任何评分**）/ `1` = 运行期失败（目录不存在等硬错误）。
  > ⚠️ 退出码语义：REVIEW 一旦被当作 `0`，低分技能会被 CI 直接放行。CI 必须写「1 阻断 / 2 告警 + 人工确认」，只判 0/1 等于把 REVIEW 当通过。
- **评分降级策略**：grading.json 存在 → 直接读取；否则按 eval.json.assertions 做子串包含启发式评分；无断言 → skip。
- **判定**：均分 ≥0.7 → PASS；0–0.7 → REVIEW；无可评分用例 → NO-DATA（同样返回 2）。
- **产物读取**：默认按**内容探测**读全部非二进制文本（前 4KB 无 NUL 且可 utf-8 解码）。**不用扩展名白名单**——白名单只覆盖"想得到的"类型，`.html` 这类真实产物会被漏评。`--exts` 显式指定时才按扩展名过滤。
- **基线对照**：`--aggregate` 会对用例的 `baseline/` 目录用**同一套断言**再判一次，产出 `with_skill` / `baseline` / `delta` 三列与顶层 `baseline_avg` / `delta`。⚠️ 脚本**不自动派发**两条运行（那需要模型执行器），产物由用例侧生成后落到 `output/` 与 `baseline/`；无 `baseline/` 目录时该行 `baseline`/`delta` 为 `null`，不计入成对均值。「无技能基线」是**结构性基线**（不加载技能 ⇒ 不产工程产物 ⇒ 命中 0），不是模型运行基线——要后者须自行接运行通道。

## 6. gh_push_files.py — 推送兜底（git push 不可用时）

`git push` 连续失败且降级无效时的兜底通道：改用 GitHub Contents API 逐文件推送整个目录。

```bash
python3 scripts/gh_push_files.py <本地目录> <owner/repo> [branch] [commit message]
python3 scripts/gh_push_files.py ./my-skill owner/my-skill main "feat: v1.0.0"
```

- **何时用**：走代理报 `CONNECT tunnel failed`、直连报 `Recv failure: Operation timed out`，或 `Error in the HTTP2 framing layer`——此时 `gh` 通常仍可用，改走 API。
- **适用**：首次推送本地新建的仓库（无需 `git remote` 可用）；只改少数文件、不需要本地 git 历史。
- **不适用**：需要保留完整提交历史、或文件量大——逐文件 PUT 会慢。
- **行为**：已存在的文件自动先 GET 再 PUT（带 `sha`），因此可重复运行做增量同步；每次运行是**独立提交**，不做历史重写。
- **依赖**：已登录的 `gh` CLI（`gh auth status` 通过）。
- **适用边界**：Contents API 天然支持空仓库与无本地 git 历史，代价是文件多时慢 ⇒ 只作兜底，默认仍走 `git push`。

## 7. check_deps.py — 依赖自检

回答一个问题：脚本用了哪些第三方依赖，**声明齐了吗**。

```bash
python3 scripts/check_deps.py <技能目录>
# 追加声明来源（可多次传入：文件路径或单个包名）
python3 scripts/check_deps.py <技能目录> --declared requirements-extra.txt
# 额外探测本机能否 import（会执行目标技能的 import 语句，默认关闭）
python3 scripts/check_deps.py <技能目录> --probe
```

- **退出码**：`0` = PASS（无未声明依赖）/ `1` = FAIL（有第三方 import 未出现在任何声明来源）/ `2` = REVIEW（目录不存在、无 `scripts/`、或全部脚本语法解析失败——「没数据」不判 FAIL）。
- **声明来源（自动）**：`requirements.txt` / `dependencies.txt` / `scripts/requirements.txt`，以及 SKILL.md 的「## 依赖」段落。
- **比对口径**：AST 取脚本顶层 `import` / `from … import`，跳过相对 import（包内引用不是外部依赖）与包内同名模块；与声明名做 PEP 503 归一化比对，并过一张常见别名表（`yaml`↔PyYAML、`PIL`↔Pillow、`Vision`/`Quartz`↔`pyobjc` 系列 等）。别名写成**无连字符的词根**，命中规则是「声明名是否包含该词根」——一个词根即可覆盖整族包名。
- **`--probe` 是显式开关**：默认只做静态分析，不执行目标代码。只有需要判断「本机装没装」时才开；开了也只把结论标为参考（本机没装 ≠ 读者没装）。
- **它不替你装依赖**：输出只有两件事——缺哪条声明、到哪个文件哪一行去补。

## 8. batch_skill_audit.py — 批量技能体检

一次给一批技能跑完同一套门禁与结构统计。**先扫全局、再逐个细查**：本节回答的是「哪几个技能需要细查」，单个技能的问题定位仍回 §1–§7。

```bash
# 体检默认根目录（~/.workbuddy/skills）下的全部技能
# ⚠️ `~/.workbuddy/` 是本文示例宿主的目录约定，换 harness 请换成你自己的技能根目录
python3 scripts/batch_skill_audit.py
# 只体检单个技能（试跑 / 复现，最快）
python3 scripts/batch_skill_audit.py --only skill-dev-kit
# 指定根目录、跳过模板目录、只看前 5 个
python3 scripts/batch_skill_audit.py ~/.workbuddy/skills --exclude _template --limit 5
# 机器可读：JSON 打到标准输出
python3 scripts/batch_skill_audit.py --json
# JSON 落盘（不带值 → ~/.workbuddy/batch-audit-<时间戳>.json）
python3 scripts/batch_skill_audit.py --json-out
# 被检技能里若有会执行真动作的脚本，关掉 --help 探测
python3 scripts/batch_skill_audit.py --only skill-dev-kit --no-help-probe
```

- **用途**：对每个技能跑同一套门禁——description 质量、发布预检常规档、发布预检严格档——再附一组结构统计（顶层文件 / references / scripts / evals 各自文件数、正文体积、触发词条数、§ 章节引用判定数），横向可比。
- **退出码（三态）**：`0` = 全部 PASS / `1` = 至少一个技能 FAIL / `2` = 无 FAIL 但有 REVIEW 或不可判（超时、跑不起来、拿不到结论）。CI 按「1 阻断 / 2 告警 + 人工确认」处理。
- **口径要点**：
  - **`--help` 覆盖探测只对构造了 argparse 的脚本执行**：对被检技能的任意脚本跑 `--help` 有可能触发它自身的副作用，那是「改了被检对象」，体检工具不能干；不构造 argparse 的脚本只计数、不执行。可探测对象为 0 时该项记「不可判」（列 `—`），**不因此判 FAIL**。
  - **严格档是更严视图，不参与全局退出码**：`--strict` 把 `author` 缺失、正文超目标值这类「应当有」的规范项升格成阻断，拿它当发布闸门会把正常状态判死；常规档 PASS 而严格档 FAIL 时只标 WARN，交人工判断（与 §1「自建门禁严于目标平台会把正确写法误杀」同一条纪律）。
  - ⚠️ **`--strict` 在三个脚本里同名不同义，别当成一个开关**：`batch_skill_audit.py --strict` = 更严视图（不改变退出码，见上）；`preflight_release.py --strict` = warning 升为 FAIL（真会阻断）；`eval_trigger.py --desc-check --strict` = desc-check 的 WARN 计入失败。**要「发布必阻断」只有 preflight 那个算数。**
  - **结构统计的正文体积口径与发布预检一致**（中文字数 × 1.0 + 非中文字符数 ÷ 4，先剥 frontmatter），触发词条数也与 §4 的章节解析口径对齐——两边数字必须对得上。
  - **报告只留工作区**：默认只打标准输出；`--json-out` 落盘时拒绝写进被检技能目录、被检技能集合根目录与本工具包目录（体检不改被检对象，报告也不是技能资产），命中即拒绝写入并判 REVIEW。
- **不适用**：要按失败项逐条定位、要看某条命令的完整输出时，回 §1–§7 单跑。

```bash
# 注：--strict 使 author 等 warning 项重新阻断；CI 若需「归属强约束」请显式加 --strict

```

> **封闭白名单只可用于「命中已知风险」，不可用于「未命中即不合格」。**
> 所有判定词表/阈值必须参数化；默认值缺失或无法判定时，输出 REVIEW（退出码 2）而非 FAIL。

**判定方法（新增脚本时照做）**：对每个模块级常量问一句——「这个集合只对本技能有效，却被用于评价别的技能吗？」是，则不得用于判定。

## 11. 脚本 ACI 规范（Agent–Computer Interface）

> §1–§8 面向人（命令与退出码），本节讲参数与输出怎么设计（真实调用方是 Agent）。
> **能力边界先行**：本节的 6 条是**规范要求**，本技能 8 个脚本只落实了其中一部分（help / schema 投入已达标；降噪与错误消息契约为部分；分页截断与低信号 ID 当前未实现）。**读者据此判断能不能用**；未实现的一律显式标注，不承诺。

### 11.1 描述与 schema 投入原则

`--help` 文本与参数设计，要按写系统提示的规格投入，不能当附带品。

**当前实现**：8 个脚本的 argparse `epilog` 均有可直接复制运行的示例（每个脚本 ≥3 条），且**全部参数都带 `help` 文本**——`--help` 输出已可直接当用法说明读。

### 11.2 输出冗余控制

支持 `--json` 时优先输出结构化精简结果；没有该能力的，退一步用 `--quiet` 降噪。

**当前实现（部分）**：`--json` / `--quiet` 的支持范围见下方实现边界表。**此条对外作为规范保留**——本技能按该边界使用。

### 11.3 大响应分页 / 截断

单次输出预估超过 2–4k token 时截断，并显式提示如何取剩余部分（分页参数或落盘路径）。

**为什么**：一次打爆上下文 ⇒ Agent 后续步骤全部失明。

**当前实现（未实现）**：8 个脚本**均无** token 计数、截断或分页逻辑；`--list`、全量敏感命中清单等长输出目前是裸打全量——**调用方须自行控制读取量**。

### 11.4 返回去低信号 ID

返回自然语言描述优先于裸 UUID / 内部数字 ID。

**当前实现（部分）**：`setup_gh_ruleset.py` 成功行为 `✓ ruleset 创建成功: <名称> (id=<数字>)`——名称在前是对的，但尾部的裸数字 ID 无可执行价值，**调用方可忽略该 ID**。其余脚本不输出内部 ID。

### 11.5 示例质量原则

示例必须**可真实运行**、覆盖「最小 / 部分 / 完整」三档、**禁用占位符**。

**写法**：占位符换成能直接跑的真实写法，如 `<技能目录>` → `.`。§1–§7 通篇用 `<技能目录>` 是**面向人**的排版惯例，本节不追溯修改；**§8 起的新脚本示例按本条写**（给出真实路径，不用占位符）。

### 11.6 错误消息契约

失败输出必须同时给出「问题定位 + 正确示例」，只说「缺什么」不给修法等于没说。

**为什么**：报错是 Agent 唯一能自纠错的信号。

**当前实现（部分）**：`preflight_release.py` 的 critical 项后跟一行「修：…」，`--quiet` 下照常打印，是本条的正例；除它之外的其余脚本**均未实现**——未实现者不提供修复指引。

### 实现边界表

| 11.3 | 分页 / 截断 | **未实现**：无 token 计数 / 截断 / 分页，长输出裸打全量 |
