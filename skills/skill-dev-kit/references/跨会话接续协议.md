# 跨会话接续协议（长任务不烂尾）

> 适用：单个技能的开发、重构、批量改造跨多个会话时。
> 零外部依赖——只用两个纯文本文件加 Git（无 Git 时的兜底见 §二 第 4 步）。
> 与技能包内「全生命周期」类文档互补：那边解决「做什么」，这边解决「换会话时怎么接上」。

---

## 一、状态三件套

### 1. `todo.json`：feature list 必须用 JSON

**为什么不用 Markdown**：模型会顺手「美化」Markdown——调标题层级、合并条目、把 `- [ ]` 重写成一段流畅文字。列表被重写一次就无法再脚本校验、无法可靠 diff，条目在润色中静默丢失。JSON 键名固定，改动可被机械比对。

结构（每 feature 一条）：`id` / `desc` / `verify` / `status`。

```json
{"features":[{"id":"f-001","desc":"一句话说清是什么","verify":"怎么证明通过","status":"failing"}]}
```

四条纪律：

1. **初始全部 failing。** 不是悲观，是契约：没跑过验证就是没通过。
2. **禁止删改 `verify` 来变绿。** 放宽判定等于进度造假，比不做更糟。
3. **只允许 `failing → passing`**，并在 `verify` 里留下实际跑过的动作。
4. **粒度：一个 feature 应能在一个会话内做完。** 跨会话的必须拆到可独立提交的粒度；确实不可拆的（如贯穿全库的重构）才允许占多个会话，并走第 5 步的分支方案。

### 2. `progress.md`：追加式日志

每会话结束追加一段，三段式：**做了什么**（文件/命令/结论，不写感受）· **当前状态**（哪些转 passing、卡在哪）· **下一步**（写到能直接照做）。只追加，不回改历史段落——改历史等于抹掉证据。

### 3. 恢复入口

新会话先读这两个文件：`todo.json` 看还剩什么，`progress.md` 看上次停在哪。

---

## 二、每会话起步序列

1. **读状态。** 读两个文件；没有状态文件即冷启动，跳到第 2 步 B 路。
2. **测基础功能。**
   - **A 路（接续）**：跑一遍已有能力，确认基线是好的。**端到端验证优先**——能跑通完整链路就别只看中间产物，单元全绿但端到端挂掉是最常见的假进度。
   - **B 路（冷启动，无状态文件）**：不测，改为建库——列 feature 全集写进 `todo.json`（全部 failing）、`progress.md` 写第一段「下一步」，再进第 3 步。
3. **只做一个 feature。** 挑一个 failing 项，做完、验证、标 passing，然后停。一次贪多会留下无法复现的中间态。
4. **commit + 追加日志。** 一个 feature 一次提交，随后向 `progress.md` 追加三段式记录。**无 Git 时的兜底**：自有目录且可初始化 → 先 `git init`；只读、共享目录、他人仓库等不能初始化的场景 → 把 `todo.json`、`progress.md` 与产物复制到带时间戳的副本目录做快照。快照能接续、不能回滚，属降级方案。
5. **留干净状态。** 允许 WIP 中间态，不允许**无法复现的**中间态——即下一个会话读完两个文件就能判断该干什么。中间态二选一：改动局部、一句话能描述 → WIP commit；改动贯穿全库、单次 commit 无法自洽 → 独立分支，分支上允许 WIP，合回主干时 squash。

---

## 三、恢复流程

summary + 两个状态文件都在即可无损恢复，不需要回忆：

1. summary 定位这是哪个技能、哪一轮改造。
2. `todo.json` 拿剩余 feature 与各自验证方式。
3. `progress.md` 最后一段拿下一步。
4. 按起步序列第 2 步往下走（有状态走 A 路，无状态走 B 路）。

丢掉的只有对话中的推理过程；能复现的结论都在文件里，不能复现的过程本就不值得恢复。

一致性校验（`todo.json` 与 `progress.md` 是否同步、有无孤儿 feature）当前只能人工读文件比对，**自动校验脚本：待实现**。
