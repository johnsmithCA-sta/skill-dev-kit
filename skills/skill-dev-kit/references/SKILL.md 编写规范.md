# SKILL.md 编写规范（生产级骨架 + description 触发命门）

> 来源：社区共识 + 官方规范（Agent Skills 规范）提纯。新技能 SKILL.md 的「填空模板」——从 frontmatter 到五要素到生产骨架一次到位；含 description 编写方法论（触发命门）。
> 配套：体积预算见 `references/核心公式与量化基准.md`（L2 正文 <5000 token 为**硬上限**，另设 **~2000 token 目标值**锚点；Token 降本纪律见同文件 §5）。
> **骨架是上限不是下限**：官方给出的最小骨架，正文只有 7 token 也合规。不要为了「把模板填满」而注水。

---

## 一、frontmatter 命名规范

| 字段 | 官方约束 | 说明 |
|---|---|---|
| name | 1–64 字符；小写字母 / 数字 / 连字符；不以连字符开头或结尾；禁止连续连字符 `--`；**必须与父目录名一致** | 「与目录名一致」「禁连续连字符」两条最易漏，发布前逐条核对；命名取向按「**你做什么**」写（动名词 / 动词优先），见下方命名说明 |
| description | 1–1024 字符；非空；写 what + when | 1024 是**字段自身**的上限，不是整个 frontmatter 的总计；社区建议 ≤500（写法见 §七） |
| compatibility（可选） | ≤500 字符；仅在有环境要求时写 | 多数技能不需要 |
| metadata（可选） | 任意 string→string map | 官方合规的可选字段；但本技能发布链路的 `author` / `version` 必须保顶层，不要挪进子块 |
| allowed-tools（可选，实验性） | 空格分隔的预批工具，如 `Bash(git:*) Bash(jq:*) Read` | 安全收敛面：预先收敛可用工具范围；不写则走默认权限 |

> ⚠️ 另需遵守：`version` 语义化且与发布 tag 一致；其余平台字段各平台不同（SkillHub 需 slug/displayName/summary；GitHub 需 name/description/version/license）。
> ⚠️ SKILL.md 文件名大小写敏感；技能文件夹内**禁止放 README.md**（避免与发布目录 README 冲突）。
> ⚠️ **`name` 按「你做什么」命名（动名词 / 动词优先）**：`generating-reports` 优于 `report-generator`、`extracting-tables` 优于 `table-extraction`——名字本身就说出动作，读的人不必先猜它是什么名词。动名词形式（`generating-reports`）依然是 kebab-case，与上面的字符约束**不冲突**。**目录名已定时以目录名为准**：「必须与父目录名一致」优先级最高，要改命名就重命名父目录，不靠让两者对不上来迁就。

## 二、个人实战五要素（缺一不可）

1. **适用与触发**：先写清什么时候该用它、什么时候**不该**（适用 / 不适用），再给覆盖所有说法的触发词（口语变体 + 任务类型）。只说「能做什么」不够——读者判断不了该不该叫它。
2. **分步流程**：可直接照做的步骤，含完整命令。
3. **依赖清单**：环境要求（Python 版本、可选工具）。
4. **边界与安全**：明确红线（隐私约束、敏感数据不上云、凭证用后即删）。
5. **使用示例**：一次完整对话的模拟流程——缺失会导致审查不过，**务必补齐**。

> **引用纪律**：文件引用一律用**相对路径**，且保持**一层深**（如 `references/x.md`）。不要制造「A 引用 B、B 引用 C」的嵌套引用链——链越长越容易断，也让模型在真正需要之前就一层层加载、白烧上下文。
>
> **什么时候该拆文件、什么时候不该**：默认**能内联就内联**——内容放得进 SKILL.md 就直接放，不为「结构完整」而拆。只有两种情况值得拆：
>
> - **重参考**：单个片段 **100+ 行**，内联会把正文撑出预算 → 拆到 `references/<主题>.md`；
> - **可复用工具**：会被**多个流程**调用的脚本 / 模板，复制两份必然各改各的 → 拆到 `scripts/`。
>
> 反过来说，不足 100 行、只被一个流程用一次、或拆出去后正文仍得重复解释它的，**都不拆**。这里要留神：「固定三件套」（SKILL.md + references/ + scripts/）说的是**形状**，不是**任务清单**——它最大的副作用是诱使作者为凑齐三个目录而把本该内联的内容拆散，结果正文变薄、引用变多，读者要跳几个文件才能拼出全貌。
>
> **多域技能按 variant 拆，不按目录拆**：同一技能覆盖多个并列领域时，拆成 `references/<域>.md`，让模型**只读当前这单相关的那一份**；不要写成「一份总索引 + 每个域都点名一遍」，那会让每一单都把全部领域读一遍，拆了等于没拆。该拆法仍是**一层深**（`references/<域>.md`），与上面的引用纪律不打架。

## 三、生产级最小骨架（填空模板）

```markdown
---
name: <skill-name>          # kebab-case
description: <做什么 + 何时用>   # 第三人称、无 how
version: 0.1.0
license: MIT
---

# <技能名>

<一句话价值主张：把什么变成什么>

## 定位
<这是什么 / 解决什么问题 / 凭什么用它——三行以内。不写背景故事与开发过程>

## 何时用（适用 / 不适用）
- 用它：<症状场景，读到能对号入座>
- 不用它：<看着像、其实该走别的路的场景>

## 触发词
- <说法 1> / <说法 2> / ...

## Goal（可验证输出物）
<!-- 落笔前先答「质量条五问」，见下方 §3.1 -->
<完成时应交付的具体产物，可被断言校验>

## Inputs（必填 / 可选）
- 必填：<用户必须提供的>
- 可选：<有默认值或可从环境推断的>

## Constraints（不做什么 + 质量门槛 + 逃逸条款）
- 不处理：<明确边界>
- 质量门槛：<如"错误路径必须拦截""结构化输出">
- 逃逸条款：当本技能的 MUST/NEVER 与用户明确意图/其他指令冲突或不适用时，
  优先保障用户数据与意图，并显式说明偏离理由与替代动作——不得静默偏离。

## Steps（读取 → 处理 → 验证）
1. <读取：输入来源 + 方式>
2. <处理：核心逻辑，含完整命令>
3. <验证：验收三件套 数量统计 + 逐条抽查 + 失败清单>

## 决策路径（可选）
<!-- 只在出现非显然分支 / 回路 / A-B 取舍时保留；否则整节删，边界见下方说明 -->
- 若 <判断条件> 成立 → <分支一>
- 否则 → <分支二>（回到「Steps」第 2 步）

## Verification Checklist
- [ ] 关键字段齐全
- [ ] 结果可复现
- [ ] 引用资源已标注路径

## 使用示例
> 用户："<真实诉求>"

1. ... 8. ...

## 常见错误（可选）
- <什么会搞砸> → <怎么修>   # 只收真实踩过的坑，不写臆测的坑

## 速查（可选）
| <高频操作> | <命令 / 要点> |
|---|---|
| ... | ... |
```

> **排序依据（按读者的决策顺序排，不按作者要交代什么排）**：分四拍——① **要不要读下去**（定位）② **要不要叫它**（何时用 + 触发词）③ **怎么干**（Goal → Inputs → Constraints → Steps）④ **干完怎么收**（Verification → 使用示例 → 常见错误 → 速查）。
>
> 社区共识的分布：「定位 / 概览」类小节几乎恒为第 1（方差最小）；「适用 / 触发」居次；「产物 / 输出」出现频率低；「反面 / 错误」与「示例」靠后；「速查 / 参考」居末。**把「产物」放第一节、把「触发词」压到倒数第二节，两处都与主流相反。**
>
> **骨架是上限不是下限**：上面是最小完整形状，不是必须填满的表格；`## 常见错误` 与 `## 速查` 是**可选**节——没有真实踩坑就不写「常见错误」，没有高频操作就不写「速查」。官方骨架样本正文仅 7 token 同样合规。为对称而凑节，只会让正文变长、可读性变差。
>
> **拆不拆文件，见 §二「引用纪律」下的判断块**：能内联就内联，只有「重参考（单片段 100+ 行）」与「可复用工具（会被多个流程调用）」两种情况才拆；多域技能按 variant 拆成 `references/<域>.md`，模型只读当前相关的那一份。
>
> **`## 决策路径（可选）` 的使用边界（可判，三类之外一律不写）**：只在 ① **非显然决策点**（不同输入走不同分支，且分支怎么选不显然）② **流程回路**（有循环 / 回退）③ **A vs B 的选择**时保留该节。三类之外，各自换回本来的形式——**参考材料**改用表格；**代码展示**改用代码块；**线性指令**改用编号列表；**无语义标签**（`step1` / `helper2` 这类纯编号、不承载判断的节点）直接删，拿它们画图只是把列表换了个形状，判断信息一条没多。命中不了三类就整节去掉，不要留空壳。

### 3.1 Goal 节的质量条五问

写 `<完成时应交付的具体产物>` 之前，必须能回答这五问；答不上来就说明目标还停在「活动」层面：

1. 完成时，什么**具体的事情为真**？
2. 什么**证据**能证明它？
3. 什么**量化或二值阈值**定义成功？
4. 哪些**范围边界**要紧？
5. 什么情况应该**停下来问人**、而不是闷头继续？

两条配套纪律：

- **拒绝纯活动目标**：「make progress」「keep investigating」「work on X」一律打回——除非把它锐化成可验证结果（谁、在什么条件下、产出什么、怎么验）。
- **澄清要有节制**：只在「合理的改写可能追错结果」时问**一个**简洁的澄清问题，问题围绕**缺失的验证器**或**范围边界**，不要一次性抛五问当成访谈。

### 3.2 六类量化启发式（把目标写成可验证）

按任务类型取量化口径，避免「处理好」这类不可校验的措辞：

| 任务类型 | 量化启发式 |
|---|---|
| bug 修复 | 复现优先：先给稳定复现步骤，再谈修 |
| 测试 | 点名确切命令 + 通过条件（哪条命令、看到什么算过） |
| 性能 | 指标 + 阈值 + 测量方法 + 重复次数 |
| 质量 | 可观测的验收条（逐项可勾） |
| 研究 | 决策 + 范围 + 证据标准 |
| 运维 | 健康态 + 监控窗口 + 回滚触发条件 |

## 四、写作原则（共识）

- **模板模式优于散文**：放 `## Report Template` / `ALWAYS use this structure`，让模型填空而非自由发挥。
- **少而精的示例**：明确边界情况处理方式，「好的示例胜过十条规则」。**数量不是判据、完整度才是**——一个能跑通的完整示例 ＞ 三个被截断的示例；不要为了凑「覆盖面」把同一件事用 5 种不同语言 / 写法各写一遍，那是稀释，不是覆盖。
- **按失败类型选形式（不是一律 MUST/NEVER）**：先给 baseline 失败定性，再决定用禁令、正向配方还是结构化槽位——四行对照表见 §4.2。MUST / NEVER 照旧保留，但**只留给纪律型场景**；它们不是禁忌，是不能乱用。
- **本机绝对路径反模式**：用相对路径或环境变量，禁用本机绝对路径硬编码（形如 `/Users/<账号>/…`，也是脱敏第一道防线）。
- **不给过多库选项**：给默认 + 退路，避免模型在选项间犹豫。
- **「魔数」必须注释理由**：`max_retries = 4  # 指数退避封顶 60s，覆盖 95% 瞬时故障`。
- **别把「何时使用」写进 body**（应放 description）——最高频错误。
- **单技能单职责**，不做「万能指令」。
- **固化必带逃逸条款**：SKILL.md 的 MUST/NEVER 是「可更新指南」而非不可置疑的法律。Constraints 节必须写明：与用户明确意图冲突时优先保障用户意图 + 显式说明偏离理由（防「硬编码铁律不容偏离」反模式 #19）。
- **先给任务定型，再决定怎么写指令**：纪律型 / 技法型 / 模式型 / 参考型四型，类型同时决定「指令多硬 + 用什么测试 + 怎么算过」——矩阵见 §4.3。写 Steps 前先定型。
- **面向用户端写作（硬约束）**：SKILL.md 与 README 的读者是**技能的最终使用者**，只写「怎么用」，不写「我们怎么开发的」——版本治理章、实测日期与数据、变更来源与内部动因、维护者指令、商业意图一律不写（详见 §4.1）。
- **不写目标受众、不绑单一平台品牌**：「本技能面向谁」删（定位隐喻可留）；「适配 X 平台」改为能力特征描述（「适用于任意 Agent 对话场景」），避免技能在别的环境里读起来像不适用。

### 4.1 面向用户端写作（硬约束）

> 一句话：**SKILL.md 与 README 的读者是技能的最终使用者，不是维护者。**只写「怎么用」，不写「我们怎么开发的」。

**判定问句**：这一行，使用者看了能帮他决定怎么用吗？不能，就删或改写。

**禁止写入（开发过程信息，一律删）**

| 类别 | 典型写法 | 处理 |
|---|---|---|
| 版本治理章 | `## 版本与事实源`、`## 版本口径`、正文「当前版本已是 X，标注保留原样」 | 整章删；版本史只保留 `references/Changelog.md` 一处 |
| 治理口吻 | 「唯一事实源」「版本口径」「事实源对齐」 | 改中性：「完整版本史见…」 |
| 版本归属标注 | `v1.1.0 新增`、`（v1.2.0）`、`自 v1.4.0 起支持` | 删版本号，只留能力本身 |
| 变更来源与内部动因 | Changelog 的「来源」列、「因接入 X 连接器而新增」「移除商业化定位说明」 | 删来源列；动因改写为用户可感知的变更 |
| 实测与过程数据 | 「2026-09-09 实测」「三个实测坑」「覆盖率 58%→100%」「444→238 字符」 | 删日期与过程数字；**结论**对使用者有用的保留（如「覆盖更多口语问法」） |
| 内部踩坑表 | `## 踩坑内嵌（经验教训，勿重蹈）` | 重写为「结果解读与已知误报」，只留解读输出所需 |
| 维护者指令 | 「改动本技能后跑一次…」「发布前先清产物」 | 删；确需保留的转使用者视角（「可用于验证能力是否符合预期」） |
| 内部商业意图 | 「可作为付费技能上架」「商业化定位（v1.2.0）」 | 整段删 |
| 受众说明 | 「本技能面向…用户」「用户是开发者不是消费者」 | 删（定位隐喻可留） |
| 单一平台品牌绑定 | 「适配扣子等对话场景」 | 通用化：「适用于任意 Agent 对话场景」 |

> **版本升级说明（changelog）另有专条**：它既要给用户看、又必须提到「修好了什么」，边界与「SKILL.md 不写开发过程」不是一回事——四类条目模板与正反例见 `references/知识产权边界与护城河判定.md` §6.1。

**改写三原则（不是删了就完）**

1. **内部动因 → 用户可感知能力**：不写「因接入 X 连接器」，写「可选：取法条原文 + 时效性 + 溯源 URL」。
2. **踩坑 → 结果解读**：踩坑表的价值是防重复犯错，对使用者无意义；但「哪些现象属已知误报、如何处理」有——转成后者。
3. **平台绑定 → 能力特征**：去掉具体平台名，描述为通用能力。

**两类易误删，应保留**

- **能力背书**：「实测坐标常量零误报」——面向用户的能力承诺，不是开发过程。
- **用户侧操作约束**：「退出码 0=PASS / 2=REVIEW，CI 判据务必写成…」——使用者接 CI 用得上。

**边界**：`references/Changelog.md` 是版本档案，可记变更事实，但同样不写内部商业意图与动因；README 里的 Changelog 摘要只保留用户可感知部分。

**写完自检**：全文搜「实测 / 事实源 / 口径 / 覆盖率 / 字符 / 来源列 / `（v1.` / 改动本技能 / 付费 / 上架 / 平台品牌名」，命中即逐条复核。

### 4.2 按失败类型选形式（替代「一律 MUST/NEVER」）

先给 baseline 失败定性，再选形式。选错形式不是「不够硬」，而是会**反向制造失败**：

| baseline 失败形态 | 该用的形式 | 反效果的形式 |
|---|---|---|
| 知道规则、有压力时仍违反（纪律型） | 禁令 + 合理解释对照表 + 红旗清单 | 软指导（"prefer…" / "consider…"） |
| 遵守了，但输出形状不对（啰嗦、结论被埋、复述需求） | 正向配方 / 契约：直接写清产物由哪几部分组成、按什么顺序 | 禁令清单（"不要复述"、"禁止叙述"） |
| 该产出的东西里漏了必备元素 | 结构化槽位：在模板里设 REQUIRED 字段 | 模板旁边的文字提醒 |
| 行为应随条件变化 | 条件式，绑定可观察谓词（"若简报存在，则引用它"） | 无条件规则 + 豁免条款 |

两条硬规则：

1. **不写含糊从句**：「Don't X unless it matters」会重开谈判。在一条已经生效的配方后面追加含糊从句，效果从稳定退化为噪声。
2. **豁免条款不能限定作用域**：「本限制不适用于代码块」仍然会压制代码块——被点名的东西反而更容易被当成需要注意的对象。要豁免就**改结构**（把内容移出该规则的作用对象），别加从句。

> **与反模式 #19 的分工（不可互相借用）**：#19 讲的是**元层级**——技能的 MUST/NEVER 与用户明确意图冲突时，优先用户意图并显式留痕；本节讲的是**任务层级**——这条指令本身该怎么写。尤其不能拿 #19 的逃逸条款当「含糊从句」的借口：逃逸条款是**冲突时的出口**，不是措辞可以模糊的许可。

### 4.3 技能类型矩阵（定型 → 指令强度、测试方法、成功判据）

类型一确定，指令多硬、目录怎么拆、用什么测试、怎么算过都跟着定了：

| 类型 | 例子 | 怎么测 | 成功判据 |
|---|---|---|---|
| 纪律型 | TDD、完成前验证 | 学术问答 + 压力场景（时间 / 沉没成本 / 疲劳叠加） | 最大压力下仍守规则 |
| 技法型 | 条件等待、根因追踪 | 应用场景 + 变体场景 + 信息缺失测试 | 能把技法用到新场景 |
| 模式型 | 降复杂度、信息隐藏 | 识别场景 + 应用场景 + 反例 | 知道何时不该用 |
| 参考型 | API 文档、命令手册 | 检索场景 + 应用场景 + 缺口测试 | 找得到且用对 |

**互补判据（决定要不要建测试用例）**：**客观可验证输出**的技能（文件变换、数据抽取、代码生成、固定流程）适合建测试用例；**主观输出**的技能（写作风格、艺术）常常不需要——不要硬给需要人判断的东西套断言，那只会把评估做成走过场。

### 4.4 上下文经济（消费方视角：省着用）

`references/脚本速查.md` 要求把 `--help` 当系统提示来写，这是**供给方**视角；下面是**消费方**的两条配对纪律——「写得好」+「用得省」，缺一不可：

1. **脚本当黑盒**：先 `--help` 再调用，**不要读脚本源码**。脚本可能很长，读一遍就污染上下文窗口；它们的存在意义就是被当作黑盒直接调用。只有 `--help` 说明不足、且确认非看实现不可时，才读，并只读相关片段。
2. **禁 `@` 式强制加载**：`@skills/xxx/SKILL.md` 会在真正需要之前就**强制立即加载**、一次性吃掉大量上下文。正确做法是**只用名字引用 + 显式要求标记**，例如 `**REQUIRED SUB-SKILL:**`——让模型在需要时自己按名字去加载。

> **自省纪律（本规范须反向对自己执行一次）**：本规范对技能提什么要求，本技能自己先做到——否则就是反模式 #23「立规者未自守」。按上面第 1 条自检：本技能 8 个脚本的消费方式，是否已写成「**先 `--help`、别读源码**」？不是就先补自己的文档，再要求别人。

### 4.5 面向协作者的术语校准

§4.1 管的是**技能最终使用者**读到的东西；本条管的是**一起开发 / 访谈的协作者**听到的东西。读者不同，两条是互补关系，**不得合并**——写给使用者要的是「怎么用」，说给协作者要的是「他听不听得懂」。

同一个词，不同协作者的熟悉度不一样，用词要跟着**对方的熟悉度**走，不是跟着自己的习惯走。按两档处理：

- **通用档（「评测」「基准」）**：属勉强可用的通用词，多数协作者能直接接住，不必先铺垫；
- **专有档（「JSON」「断言」）**：**必须先看到对方懂这些词的信号再用**——他前面自己用过这个词，或上下文里已经出现过。

**可判操作判据**：落笔写一个专有档术语之前，先自问「对方上一轮用过这个词吗？上下文里出现过吗？」。答不上来就二选一——**换上位替代词**（「JSON」→「结构化数据文件」、「断言」→「检查点是否成立」），或**先解释再用**（一句话说明它指什么，再往下讲）。两条都不做，就是拿对方的理解赌自己的词汇量。

## 七、description 编写方法论（触发命门）

> 定位：**description 是技能唯一的触发凭据**——模型通过语义匹配决定是否加载技能。描述写不好，技能等于不存在。

### 7.0 为什么它是「命门」

- description 决定**是否触发**，不决定**执行质量**；执行不一致时查正文指令特异性，而不是改 description。
- 触发阈值：**简单单步任务不触发、复杂多步任务必触发**——测试触发率低 90% 的原因是「测试指令太简单」。
- 监控真实使用中的意外触发与过度依赖；把「某 prompt 没触发」的反馈当**新测试用例**补进评估集。

### 7.1 高精准 description 五策略

| # | 策略 | 做法 | 示例 |
|---|---|---|---|
| 1 | **能力标签（名词性）+ 触发场景**双维度 | 动作动词 + 具体文件类型 / 领域 + 场景；**不得写入步骤序列、流程顺序、判定结论** | 「提取 PDF 表格转 CSV」「创建带修订标记的 Word 文档用于法律审查」远胜于「文档处理」；❌「执行计划时逐任务派发子 agent 并在任务间做代码审查」——这就是把正文的 Steps 缩进了 description |
| 2 | 推动性语言 | 加「必须优先触发此技能」类指令——模型默认倾向自己处理简单任务，描述要「略显强势」 | "MUST trigger when the user asks to convert PDF tables" |
| 3 | 关键词罗列 | 末尾罗列高频口语化触发词/请求变体 | "Trigger words: 提取表格、PDF 转 Excel、表格转换…"（**此处的口语触发词不受 §7.2 规则 1 限制**——「我的订阅 / 我要导出」是关键词罗列，不是自称） |
| 4 | 排他边界 | 写明「不做什么 / 何时不用」，防误触发 | "Not for data visualization or chart generation." |
| 5 | **写「触发前一刻的症状」，且描述问题而非工具** | 触发时机取用户**还没动手、正要动手**的那一瞬，写他的处境与心声；要触发的那件事，写**问题本身**而非某个语言 / 工具特有的症状，**除非技能本身就是技术特定的** | 「在动手写实现之前」「测试跑起来时好时坏」远胜于「提供实现相关能力」；写「消除竞态条件带来的不确定性等待」，而不是把某语言定时器 API 的函数名当触发条件 |

> **为什么不能写步骤**：description 是唯一常驻上下文的内容，正文是按需加载的。description 一旦把流程和结论说完，正文就失去了被读取的理由——技能退化成一行 prompt。写「分两步做审查」，模型就可能只做一次。

### 7.2 三条硬性规则

1. **必须非自称构式**：禁止「I can / 我可以 / 本助手…」等技能自称的表述；**用户口语触发词中的「我的 / 我要」属 §7.1 策略 3 的关键词罗列，不受此限**。
   > 历史缺陷：这条曾按字符表面形式判定，把按规范写出的「我的订阅」判为违规——**按规范写出的内容被规范自己的检查器判为违反规范**。判语义属性不能只看字符形式。
2. **只写「做什么 + 何时用」**，把「怎么做」留给正文——description 试图解释 how 是高频错误。
3. **泛泛描述必死**：「Helps with documents」触发条件过宽，会在错误时机激活或从不激活。

### 7.3 触发机制要点（与正文的分工）

- description 只管触发 → 触发信息只放 description；**「何时使用此技能」写进 body 是最高频错误**。
- 正文负责执行质量 → 触发正确但执行不一致，改正文：先按 §4.2 给失败定性再选形式（禁令 / 配方 / 结构化槽位），而不是一律加 MUST/NEVER。
- 触发词章节（SKILL.md 正文）与 description 互补：description 供语义匹配，触发词章节供人工/脚本检视，两者需同步维护。

### 7.4 正反例对照

| # | 反例 | 问题 | 正例 |
|---|---|---|---|
| 1 | Helps with documents. | 泛泛，无功能无场景 | Extracts tables from PDF documents and converts them to CSV for spreadsheet analysis. |
| 2 | I can help you create Word documents. | 第一人称 + 只有动作无场景 | Creates professionally formatted Word documents with tracked revisions for legal review. MUST trigger on 合同/修订/法律文档. |
| 3 | This skill processes data. | 无动作动词、无对象、无边界 | Cleans and normalizes Excel/CSV data: detects duplicates, format errors and missing fields before report generation. Not for data visualization. |
| 4 | 这个技能可以处理文档。 | 无动作动词、无文件类型、无场景 | 从 PDF/图片提取表格并转为可编辑 CSV，用于数据整理与报表；用户说「提取表格」「PDF 转 Excel」时必须优先触发。不用于文档排版。 |

### 7.5 自查清单（写完 description 逐条过）

- [ ] 无自称构式？（无 I can / 我可以 / 本助手；用户口语里的「我的 / 我要」不算）
- [ ] 有动作动词？（Extracts / Creates / Converts / 提取 / 生成 / 校验…）
- [ ] 有具体对象？（文件类型 / 领域 / 数据形态）
- [ ] 有场景 / 触发时机？（何时用）
- [ ] 无 how 描述？（没有「怎么做」的步骤细节）
- [ ] 末尾有口语化触发词？
- [ ] 有排他边界？（不做什么 / 何时不用）
- [ ] 用计划上线的所有模型实测过触发？（60/40 切分测触发率）
- [ ] 把 description 单独读一遍——它是否泄露了「先做什么再做什么」？若是，删。

### 7.6 与工具链的衔接

- `scripts/eval_trigger.py --check`：校验「## 触发词」章节覆盖率（阈值默认 0.7）。
  - **判定基准必须由技能自己提供**：优先 `--intents <file>`，其次 `<技能目录>/evals/trigger_eval.json`；
    **两者都没有时输出 REVIEW（退出码 2），不判 FAIL**——没有评估集不等于写得不合格。
  - 修好评估集再判：先 `--gen` 出模板，把 should_trigger 替换成本技能的真实用户说法后回存。
- `scripts/eval_trigger.py --gen`：生成 should-trigger / should-not-trigger 评估集模板。
  ⚠️ 模板里的说法取自工具自身语境，**必须整体替换**，否则测的是工具、不是你的技能。
- `scripts/eval_trigger.py --desc-check`：静态校验 §7.5 各项，分两级：
  - **FAIL 级 2 项**：自称构式 / 无动作动词 —— 命中即不合格（退出码 1）；
  - **WARN 级 4 项**：缺场景或文件类型 / 含 how 描述 / 缺排他边界 / **含流程摘要**（出现「先…再…」「第 N 步」「step 1/2/3」这类步骤序列标记）—— 默认只提示（退出码 0），`--strict` 才计入失败。
  - 未识别到本域场景词时给 WARN 而非 FAIL：场景词高度依赖领域，用封闭词表判不合格会误杀域外写法；本域场景词用 `--scene-words <file>` 注入。
  - **策略 3「关键词罗列」不受「含流程摘要」这条影响**：口语触发词（「我的订阅」「我要导出」）不是流程摘要，照旧豁免。
- `scripts/eval_trigger.py --holdout <比例>`（默认 0 关闭，**推荐 0.4**）：按固定种子**确定性**切分意图清单为训练集 / 留出集，两侧分别报覆盖率，**判定以留出集覆盖率为准**——这是防过拟合的关键；留出集不足 1 条时降级 REVIEW。
- `scripts/eval_trigger.py --reps <次数>`（默认 1，**推荐 3**）：重复 N 次独立留出切分（种子 0…N-1），输出留出集覆盖率的**均值 ± 标准差**。标准差偏大说明**评估集切分不稳**，对策是扩量（补更多真实说法），而不是继续调措辞。
  - ⚠️ 边界：静态工具的口径下，`--reps` 衡量的是**评估集切分稳定性**，不是模型的随机性。「同一条 query 跑 N 次求稳定触发率」需要真实调用通道，**当前未实现**——别把它当模型稳定性指标读。

## 八、改动已有技能：先判定适用条件，再选改造方式

改动一个**已存在**的 SKILL.md 时，第一步不是动手，而是判定它处于哪个状态——**适用条件决定改造方式**，选反了要么放大线上风险，要么留下一地中间态。

| 当前状态 | 改造方式 | 为什么 |
|---|---|---|
| **已发布的稳定技能**（线上在用、有存量用户） | **最小侵入 patch**：前置 hook + 覆盖优先于重构 | 用户正在跑，重构会一次性翻动所有行为面，回归面不可控；patch 只改动点，其余行为原样保留，线上风险最小 |
| **开发中的新技能**（未发布、无存量） | **一次性批量重构** | 没有存量要护，逐个修补反而留下不一致的中间态——新旧两套写法并存、命名各异、示例与规则对不上 |

### 最小侵入 patch 的三条执行纪律

1. **前置 hook 优先**：能在入口处拦截/改写就不动主流程；新逻辑挂在原流程**之前或之后**，不插进中间。
2. **覆盖优先于重构**：能用新增条目覆盖旧行为（如补一条例外规则）就不改原条目——改动面只剩"新增"，diff 一眼能审完。
3. **一次 patch 只解决一类问题**：不要在"修触发词"的 patch 里顺手改 Steps，会让回归失去归因。

### 什么情况下不该 patch（命中任一 → 转批量重构）

- 同一文件已累积 ≥3 处 patch，且彼此有交互——补丁层本身成了新的复杂度来源；
- 缺陷是**结构性**的（整份 frontmatter 不满足平台新规范、章节划分本身就错）；
- 新旧两套写法已并存，使用者无法判断该听谁的。

### 验收

patch 后的 diff 应当能被一句话说清"改了什么、影响哪个行为面"。说不清，就说明改大了，退回批量重构。

> ⚠️ 判定顺序不能反：不要因为"重构更干净"就对已发布技能动刀。**干净是开发期价值，稳定是线上期价值**，两者冲突时后者优先。
