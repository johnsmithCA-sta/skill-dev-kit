# 评测方法论

> 来源标注口径：**官方**（平台官方评测与 Agent Skills 规范）/ **社区共识**（社区评测实践共识）/ **个人实战**（本技能自身 eval_trigger.py / eval_loop.py 实测）。

## §0 定位与分工

本文件是「怎么给技能打分」的判定规则来源；`scripts/eval_trigger.py` 与 `scripts/eval_loop.py` 只负责**执行**（收集信号、算分、出退出码），本文件负责**判定**（什么信号算达标、什么情况该放行还是该拦、拿不准时往哪走）。两者冲突时以本文件为准，并同步修脚本。

退出码语义（全工具统一，不得各写各的）：

| 退出码 | 判定 | 含义 | 下游动作 |
|---|---|---|---|
| 0 | PASS | 达标，可放行 | 继续发布流程 |
| 1 | FAIL | 明确不合格，阻断 | 必须修改后重跑 |
| 2 | REVIEW | 信号不足或结论不确定，需人工确认 | 人工看一眼再决定放行与否 |

关键分野：**FAIL 只用于"有证据证明它错了"，不用于"没证据证明它对"**。后者一律走 REVIEW。

## §1 Grader 设计六条铁律

### 1.1 Unknown 出口：无数据不得判 FAIL

**反例**：技能里没有「触发词」章节 → 覆盖率算出来是 0 → 直接 FAIL；evals 目录里一个用例都没评分 → 判 FAIL。这两种都是"没数据"，不是"做错了"，判 FAIL 会逼着使用者删掉评测环节绕过工具，反而失去信号。

**正例**：区分三种状态——有数据且达标 → PASS(0)；有数据且不达标 → FAIL(1)；无数据 / 数据残缺 / 判定逻辑自身无法覆盖该形态 → REVIEW(2)，并在输出里写明"缺什么数据、为什么判不了"。

**本工具包的落点（已实现）**：三处无数据场景全部改为 REVIEW(2)——
`eval_trigger.py --check` 无评估集 / 无「## 触发词」章节；`eval_loop.py` 有目录但无评分用例（NO-DATA）。
唯一保留 FAIL(1) 的是**运行期硬错误**（如目录不存在），那不是"判不了"，是"根本没跑起来"。

### 1.2 按产物评分，不按路径评分

**反例**：断言"必须先调用 X 脚本、再写 Y 文件、最后更新 Z 索引"，或断言"执行过程里应出现第 2、3、5 步"。这类断言把实现路径钉死，重构成等价写法就全红。

**正例**：只断言**结果应当具备的性质**——产物存在、产物含某要点、产物不含禁止内容、产物能被下游消费。允许被测方自选路径，换个顺序、换个工具只要结果对就得分。

**kit 落点**：`eval_loop.py` 的 `grade_case()` 只读 `output/` 目录拼接出的产物文本做匹配，不看 `run_cmd.txt` 执行了几步、什么顺序，正是这条的体现——新增断言时不得破坏这一点。

### 1.3 不 rigid 检查固定模式

**反例**：要求 description 必须匹配某个句式模板、必须以某个动词开头、必须写满 N 个字段。这类刚性检查会惩罚创意解法，也会误杀正确但写法不同的产物（同义改写、句式倒装就判不合格）。

**正例**：检查**语义要素是否齐备**，不检查要素的排列与措辞。能被多个等价表达满足的检查才是好检查；能写成正则黑名单的，优先写成"缺什么要素"的正面清单。

**kit 落点**：`eval_trigger.py --desc-check` 共 7 项校验、分两级（FAIL 级 2 项 / WARN 级 5 项），查的都是**要素有无**，不是句式模板。两条经验：
① 判定**语义属性**（如"是否第三人称"）不能只看字符表面形式——曾经按「我」字匹配，把用户口语触发词「我的订阅」判为违规，即按规范写出的内容被规范自己的检查器判为违反规范；现收窄为**自称构式**（我可以 / 本助手 / I can）。
② 域强相关的要素（场景词）判不出就给 WARN 不判 FAIL，本域词用 `--scene-words` 注入。

### 1.4 给部分分，不要 0/1 二分

**反例**：所有断言全过才记 1，否则记 0。两次改动从 4/6 提升到 5/6，分数从 0 跳到 0，观察不到改进趋势，也无法定位是哪一项拖后腿。

**正例**：连续分（命中数 / 总数），并保留逐条明细，让人一眼看出哪项没过。聚合时用均分 + 阈值，阈值之上 PASS、附近 REVIEW、明显之下 FAIL。

**kit 落点**：`eval_loop.py` 的 `heuristic_grade()` 输出 `score = passed/total` 和逐条 `assertions[].pass` 明细，`aggregate()` 再按 `avg_score` 与阈值判定；`eval_trigger.py` 的覆盖率同样是比值并配 `--threshold`（默认 0.7）。

### 1.5 防 cheat：断言可被绕过时必须加产物校验

**反例**：只做关键词子串包含。被测方只要把断言里的要点原样抄进产物（甚至抄进一段无关的话），就能满分——评分通过了，技能其实没干活。

**正例**：每加一条断言先问"最省事的作弊方式是什么"。若答案是"抄一句话"，就必须补产物级校验（文件确实生成、内容能被解析、结构字段齐全、能过下游消费），或对关键用例改用人工 `grading.json` 评分。

**kit 落点**：`eval_loop.py` 默认的启发式评分模式是 `heuristic-substring`（子串包含），天然可抄；因此重要用例应人工产出 `grading.json`（pre-graded 模式），脚本已支持优先读取 `grading.json`。

### 1.6 瑞士奶酪模型：多层互补信号，不盲信单一指标

**反例**：只看"均分 ≥ 0.7"就放行。均分高可能是用例太少、断言太松、或某个用例被 skip 掉了；单一指标上的一层奶酪总有洞。

**正例**：同时看几层互补信号——用例数 / 已评分数（覆盖够不够）、断言通过总数（绝对量）、均分（相对质量）、逐条明细（哪里塌）、以及有没有 REVIEW 状态。任一层异常都值得人工看一眼，多层同时亮红灯才判 FAIL。

**kit 落点**：`eval_loop.py aggregate()` 的输出里同时给 `cases / graded / assertion_passed / avg_score / verdict`，供人工多层判读。
⚠️ **待实现（勿当作已生效）**：当前 `verdict` 只由 `avg_score` 与阈值 0.7 决定，`graded` 明显小于 `cases` 时**不会**自动降为 REVIEW。**本项尚未实现**。在此之前，请人工按上面的原则判读输出，不要只看 verdict 一行。

### 1.7 双跑基准：没有基线就没有信号

> 来源：官方（双跑基准与 baseline 先行）

**核心信条**：**没有看过不带技能时的失败，就不知道技能是否教对了东西**。对测试同样成立——**没看过测试失败，就不知道它在测对的东西**。只跑带技能一臂，能回答「能不能用」，答不了「值不值得用」。

**做法**：每个用例在**同一轮里并行派发**两臂——`with_skill` 与 `without_skill`（新建技能），或 `with_skill` 与 `old_skill`（改进既有技能：先 `cp -r` 快照旧版，再把基线臂指向快照）。汇总成 benchmark，输出 **pass_rate / 耗时 / token 的均值 ± 标准差与 delta**。

| 层级 | 做法 | 验收 |
|---|---|---|
| 基线对照 | 同 prompt 跑不带技能（新建）或旧版快照（改进） | 带技能版本在关键指标上**可量化优于**基线；**无差异说明技能没教新东西**，不是「反正也能用」 |

**三条执行纪律**：

1. **两臂同一轮并行派发**——不要先跑完带技能的，再回头补基线。先后跑会让两臂落在不同的环境与上下文条件上，delta 里混进时间差。
2. **基线选择随技能状态切换**——新建技能对「无技能」，改进既有技能对「旧版快照」。拿错基线（改进型却对空）会把既有能力算成新技能的功劳。
3. **产出的 `benchmark.json` 须含均值 ± 标准差**——只看均值会被高方差用例骗：一条用例偶尔全对、偶尔全错，均值看着差不多，标准差暴露它不可信。

⚠️ **半实现，边界必须写清**：`eval_loop.py --aggregate` **现在会读** `baseline/` 目录，用同一套断言对它判一次，并在 `benchmark.json` 里逐用例输出 `with_skill` / `baseline` / `delta`，顶层输出 `baseline_avg` / `delta` / `methodology`。**但它仍不自动派发双跑**——不会替你生成基线产物。双跑依旧靠**人工并行派发两臂并各自落盘**（带技能 → `output/`，不带技能 → `baseline/`），再 `--aggregate` 一次性出对照。**不得把它写成「自动双跑已实现」。**

本技能自身 `evals/` 的基线是**结构性基线**：不加载技能时不产出对应工程产物，故断言命中数为 0——**这不是模型运行基线**。该口径已在 `benchmark.json` 的 `methodology` 字段显式声明；引用对照数字时必须连着这条边界一起引用。

## §2 能力 / 回归双轨设计

同时承担两个目标时两个都会失真：想测前沿就得加难题，难题多了分数难看，分数难看又不敢加难题。故拆成两条轨道。

- **能力评估**测「能不能做到宣称的事」，用例来自真实任务里还没做到、或刚做到还不稳的部分，**允许失败**——失败说明还没做到，是发现不是事故。
- **回归评估**测「之前做得到的事现在还做得到吗」，用例是已稳定通过的部分（含毕业进来的），**掉分即事故**，说明改动破坏了既有能力。

**毕业机制**：能力轨里连续多轮（建议 ≥3）稳定满分、已不代表前沿难度的用例，毕业转入回归套件，不再计入能力轨前沿指标——否则能力轨会被已经会的题刷高分、掩盖真短板。毕业单向为主但可回退：回归用例反复掉分说明能力不稳，应退回能力轨重观察，而非放着当噪声。

**判读方式不同，别共用一把尺**：能力轨看**趋势是否向上**（逐轮均分涨不涨、前沿用例从 0 到有分），某一轮低不等于要拦；回归轨看**有没有掉下来**，任一条从满跌到不满就是信号，即使全量均分 ≥ 0.7 也不应放行。

**落地**：脚本无套件参数——`--aggregate` 只吃一个 `evals_dir`，其下每个子目录是一个用例。建 `evals/capability/`、`evals/regression/` 各跑一次，人工分别判读。

⚠️ **当前未实现，须人工判读**：脚本不区分两轨、不因回归轨掉分降判、不做毕业判定、不记录某用例连续通过几轮。

## §3 评估集构建路线图

八步，①–④ 定「测什么」，⑤–⑦ 定「测得准不准」，⑧ 定「测出来的东西往哪去」。

**用例质量标准（六条）**：一条用例要留在评估集里，须同时满足下面六条；任一条不满足，先改用例，再谈分数。下表是**选例时的准入门槛**，路线图是**建集时的操作顺序**，两者不冲突。

| # | 标准 | 一句话判据 | 对应步骤 |
|---|---|---|---|
| ① | **独立** | 单独拿出来跑也成立：不依赖别的用例先跑过，也不依赖别的用例留下的中间产物或状态。 | — |
| ② | **只读** | 非破坏性：跑完不改动被评测对象的状态，文件、配置、索引与其被评测前一致。 | — |
| ③ | **复杂** | 需要多次工具调用才能完成；一次调用就出结果的单步任务测不出能力。 | — |
| ④ | **真实** | 源于真实场景：说得出来自哪一类真实任务、用户实际怎么说，不是凭空设想的需求。 | §3① |
| ⑤ | **可验证** | 有唯一明确答案，能字符串比对（含「不含某内容」这类反断言），不靠人主观判读。 | §3④ |
| ⑥ | **稳定** | 答案不随时间变：同一输入换个时间、换个环境跑，结论一致。 | — |

「对应步骤」列只标**与路线图某一步「标志」重叠**的条目——按哪一处判结论都一样，不是两套打架的标准；标「—」的条目在路线图里没有对应标志，按本表独立判。

**① 从真实任务收集种子**：用例要来自用户实际怎么说、期望什么产物，而非凭空设想的需求。**标志**：每条都说得出来自哪类真实场景，说不出的先不收。

**② 标注应触发 / 不应触发**：只标正样本会让技能被泛化触发，只标负样本会改得谁都叫不动。**标志**：两类都有，负样本是「看着像、其实不该管」的邻近任务。

**②附一 取例规范（负例必须是「近误」）**：负例不能是随手找个无关任务充数，必须是**近误**——共享关键词 / 概念，但实际需要别的东西（别的技能，或根本不需要技能）。反例：用「写个斐波那契函数」去测一个文档抽取技能，**太容易了，什么都没测到**——两者毫无竞争关系，测出来的触发率是虚高。正例要覆盖三类：① **不同说法**（正式表述与口语表述各来几条）；② **用户没点名技能但明显需要**的情形（描述症状，而不是叫技能名）；③ **与相邻技能竞争但本技能应胜出**的情形。**规模基准：20 条 query = 8–10 条 should-trigger + 8–10 条 should-not-trigger**，两边数量相当——一边倒的评估集只能测出「叫不叫得动」。

**②附二 防过拟合循环**：评估集按 **60% 训练 / 40% 留出**切分，训练集用来改 description，留出集只用来判定。每条 query **重复跑 3 次**求稳定触发率（单次会被采样噪声带偏），**最多迭代 5 轮**（再改下去就是在背训练集）。**按留出集分数而非训练集分数选 `best_description`**——这是显式为了防过拟合：训练集分数高只说明这条 description 记住了这些说法，留出集分数才说明它对没见过的说法还成不成立。

⚠️ **边界（勿混口径）**：「每条 query 跑 3 次求稳定触发率」需要真实调用通道，**当前未实现**；静态工具下的 `--reps` 量的是**评估集切分稳定性**，不是模型随机性（见 §4）。

**③ 覆盖典型与边界**：典型保主路径，边界（输入残缺、参数冲突、超长/极短、跨语种）保少见情况下不崩不胡说。**标志**：任挑一条都说得出它测典型还是哪类边界。

**④ 设定断言**：按 §1.2 只断言产物性质，按 §1.5 逐条问「最省事的作弊方式是什么」。**标志**：每条都写得出「抄一句话能不能过」，能抄过去的已补产物级校验或改人工评分。

**⑤ 小样本试跑校准**：先跑几条，目的不是打分是挑毛病——断言写错、产物路径对不上、分数异常高（多半断言太松）。**标志**：跑出来的分和人工直觉对得上；对不上的已查明原因，而非改阈值迁就。

**⑥ 扩量到统计有意义**：三五条时改一个用例均分就跳一大截，那种「改进」和「退步」都不可信。**标志**：增删一条均分不大幅跳变，两轨各有足够条目支撑趋势判读。

**⑦ 定期复核防饱和**：评估集会饱和——题都做会了、全绿，却已分不出好坏，只给虚假安全感。**标志**：每轮改动后问「这套题还能不能考出新东西」，长期全绿的按 §2 毕业进回归轨，同时给能力轨补新难题。

**⑧ 回哺脚本固化**：这一步读的不是分数，是**用例产物**。若同一段脚本、同一段逻辑在 **N ≥ 2** 个用例的产物里重复出现，说明它本来就是该能力的一部分，不该由每个用例各写一遍。**动作**：抽成 `scripts/` 下的脚本，用例改为**调用**它；抽完把各用例里那段「重复实现」**删掉**，只留调用与该用例特有的部分——两处并存会让下一次改动只改一处，评测当场失真。**标志**：同一段逻辑在产物里的出现次数降到 1，每个用例的产物里只剩「调用」与「该用例特有」两块。

**与「可执行工作流沉淀为 Skill」的分工**：那条管**入口侧**——技能正文里反复要做的可执行工作流该不该独立成技能；这条管**回哺侧**——评测跑出来的用例产物里反复出现的脚本该不该收进 `scripts/`。前者拆的是技能边界，后者收的是重复代码，补的是评测到脚本的闭环，不是把前一条换个说法重写。

## §4 与 eval_trigger.py / eval_loop.py 的衔接

`eval_trigger.py` 管**入口**（这个技能会不会被正确地叫起来），`eval_loop.py` 管**出口**（叫起来之后活干得对不对）。完整评测两边都要跑，只跑一边等于只测一半。

**`--check` 三级回退取意图清单**：① `--intents <file>` 显式指定，最可信，跨技能统一基准时用；② 目标技能自带评估集（`evals/trigger_eval.json`，另兼容 `evals.json`、`trigger_eval.json`），存本技能真实用户说法；③ 都没有 → REVIEW(2)，**不判 FAIL**（§1.1）。拿别家清单测本技能覆盖率会接近 0，那是基准不对不是技能差。无「## 触发词」章节同样 REVIEW(2)。`--threshold` 默认 0.7；`--min-trigger-len` 默认 3，防 2 字泛词刷虚高。

**`--desc-check` 共 7 项、分两级**（§1.3 查要素有无、不查句式）：FAIL 级 2 项——自称构式（我可以 / 本助手 / I can…）、无动作动词，决定会不会被正确触发；WARN 级 5 项——缺场景或文件类型、含 how 描述、缺排他边界、缺触发词示例、**含流程摘要**（出现「先…再…」「第 N 步」「step 1/2/3」这类步骤序列标记），默认只提示，`--strict` 才计入失败。`--scene-words` 注入本域场景词；`--desc <文本>` 直接校验一段描述。

**`--check` 的防过拟合参数**：`--holdout <比例>`（默认 0 即关闭；推荐 0.4）——按**固定种子确定性切分**意图清单为训练集 / 留出集，两侧分别报覆盖率，**判定以留出集覆盖率为准**；留出集不足 1 条时降级 REVIEW。`--reps <次数>`（默认 1；推荐 3）——重复 N 次独立留出切分（种子 0…N-1），输出留出集覆盖率的**均值 ± 标准差**；标准差偏大说明评估集切分不稳，对策是**扩量而不是继续调措辞**。

**`--aggregate`**：`evals_dir` 下每个子目录是一个用例；`--run` 先执行 `run_cmd.txt`，给不给都会聚合一次；`--out` 默认写 `<evals_dir>/benchmark.json`；`--exts` 只统计指定扩展名的产物，混了日志缓存时用它收窄，否则无关文件稀释断言匹配。退出码 0 = PASS（有已评分用例且均分 ≥ 0.7）／2 = REVIEW（均分 < 0.7，或 NO-DATA 一个可评分用例都没有）／1 = 目录不存在或运行期异常。

⚠️ **当前未实现，须人工判读**：`verdict` 只由均分与阈值决定，脚本**不检查**用例总数够不够、`graded` 是否明显小于 `cases`、断言是否过松、有无用例被跳过——`cases=10, graded=2, avg=0.9` 也会输出 PASS(0)。这四项须按 §1.6 把 `cases / graded / assertion_passed / avg_score / verdict` 一起看。

**两轨接法**：两个目录各跑一次 `--aggregate`。⚠️ 脚本不自动合并、不对比趋势、不因回归轨掉分把整体降为 REVIEW；退出码分别看，回归轨的非 0 优先于能力轨的 0。

**`preflight_release.py` 的评测宣称—证据一致性检查（对应 §1.1）**：发布预检扫 SKILL.md / README，若出现「评测闭环 / benchmark / 评估集 / `evals/` / 触发词评估 / 回归重跑」等**已做评测**的声明，则要求 `evals/` 存在且非空；声明了却拿不出证据 → warning（可 `--waive eval_claim` 豁免）。

这条**不是**「没做评测就拦发布」——那会与 §1.1 的 Unknown 出口直接冲突：多数技能没有 `evals/`，目标平台也不要求它，据此拦发布就是把「没有数据」判成「做错了」。它判的是**宣称与事实是否一致**：文档里写了评测资产，目录里就得拿得出来。**没做评测就别写做了；没写就不触发。**

## §6 措辞微型测试法（成本最低的验证手段）

> 来源：社区共识（措辞微型测试五纪律）

要验证的往往只是**一句指导语本身有没有 binding**。这类问题不必等整套评测跑完才回答——用微型测试先过一道**前置成本门**。

它是**五层闭环**（`references/SKILL.md 编写规范.md` §五：端到端 / 合成样例 / 增强样例 / 真实数据 / 错误路径 + 基线对照）的**前置成本门**：完整场景跑是最终关卡，但它慢且贵；措辞本身先微测，便宜且快。顺序是先微测、后整跑，不是二选一。

**5 条纪律**：

1. **每次调用用全新上下文样本**（裸 API 调用，或单发子 agent）。**理由**：同一上下文里的前几轮会污染后一轮——模型在上一次见过错误或纠正后，下一次「成功」可能只是记住了纠正，不是指导语起了作用。
   配套：system prompt 要用这条指导**真实会待的那个上下文**（完整技能或提示词模板），不是把指导语单独拎出来测。**理由**：指导语在真实上下文里与技能正文、工具说明相互作用；单独拎出来等于测了一个不存在的环境，结论迁移不回去。
2. **必须带一个无指导对照组**。若对照组压根不出现该失败，说明**没有东西要修——停手，别写这条指导**。**理由**：这是全条最有价值的一条，它防止为不存在的问题发明规则。没有对照，你会把模型本来就会做的事记成「指导语的功劳」，也会把偶发问题过度反应成规则。
3. **每个变体 5+ 次重复**。**理由**：单次样本会骗人——一次命中可能只是采样噪声，没有重复就分不清「指导语有效」和「这次碰巧」。
4. **人工读每一条命中**。**理由**：模板回声（模型复述了指导语里的词）和引用的反例会伪装成命中；纯自动计数会**同时**高估失败率（把回声当命中）与成功率（把复述当遵守）。
5. **方差本身是指标**。指导语生效时各次重复会收敛到同一形状；**5 次出现 5 种解读 = 措辞不 binding**，此时先**收紧形式**（换成更具体、更可观察的表述），而不是加字。**理由**：不 binding 是形式问题不是长度问题，加字只会把歧义摊薄成更长的歧义。

**纪律 2 是通用纪律**：它直接呼应本技能的「立规者未自守」反模式（#23）——本技能自己新增规则时，也应先跑一次无指导对照，确认要修的问题真实存在，再决定要不要写下这条规则。

**与留出集的分工**：本方法与 §4 的留出集机制是一对——**微测管「措辞本身有没有 binding」，留出集管「这条描述对没见过的说法还成不成立」**。前者在打磨 description / 指导语时用，后者在触发率评估时用，两者不可互相替代。
