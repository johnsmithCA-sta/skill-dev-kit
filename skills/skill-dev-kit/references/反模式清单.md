# 反模式清单

> 来源：社区共识反模式 17 条，另补 13 条个人实战，共 30 条。
> 定位：写 SKILL.md / 写脚本前**先扫一遍**，命中即改。每条 = 反模式 → 正确做法 → 可观测判据。**事前**清单看本表；**事后**机制（把实测中的借口反写成对照表再重测）见文末「堵漏机制」。
> 用法：新技能开发完成、发布前，对照本表逐条自检；发现自己踩过表中没列的坑，按同样格式补行。

## 总表（30 条）

| # | 反模式 | 正确做法 | 可观测判据 |
|---|---|---|---|
| 1 | 跳过需求分析直接开发 | 示例驱动设计：先写一个**能跑通的完整示例**，再照它写正文 | 技能目录里找不到「使用示例」小节，或仅有的示例是截断片段 / 跑不通（**数量不参与判定**——一个完整示例即达标，"三个示例"里有截断的不达标） |

| 3 | 把「何时使用」写进 body 而非 description | 触发信息只放 description | 正文出现「何时使用 / 适用场景 / When to use」类小节标题 |
| 4 | 所有内容塞进一个文件 | 渐进式披露，按需加载子文件 | 按基准公式算出的正文体积 ≥ 5000 token（口径见下方 #4 展开） |
| 5 | 测试用干净/简单 prompt | 带错字、缩写、复杂多步的真实用例 | 用例集里全部是语法完整、无错字、无缩写的标准句式，脏数据用例数为 0 |
| 6 | 一次成功就庆祝，不测边缘情况 | 覆盖边界、错误输入、边缘场景 | 用例集里边界值、错误输入、空值类用例数为 0 |
| 7 | 确定性逻辑让模型「想」出来 | 写脚本让 AI 运行（零幻觉） | 正文要求模型「计算 / 校验 / 统计」某个确定值，而同目录没有对应脚本 |
| 8 | 做「API 搬运工」原样包装端点 | 按用户意图设计高层工具 | 工具名与参数和上游接口 1:1 对应，且工具描述里出现「调用 / 转发某接口端点」字样 |
| 9 | 不处理错误、返回裸字符串 | 统一错误信封 + is_error + 可读消息 | 失败路径返回空字符串 / None / 纯消息，调用方拿不到错误码 |
| 10 | 写操作不幂等 | 幂等键 + 缓存结果 | 同一请求连发两次，第二次仍新建记录或重复扣减 |
| 11 | 堆功能不修指令 | 先修指令再叠功能 | 一次改动里新增了功能，而正文指令段未同步改动 |
| 12 | 一个会话干所有任务 | 一个任务一个会话，防上下文污染；one-shot 贪多留半成品 | 会话里后一任务的产物中出现前一任务的字段名或临时路径 |
| 13 | 打包/分发时文件夹层级错误 | ZIP 根目录即技能文件夹，bump version | 解压后 ZIP 根目录不是技能文件夹（多套了一层目录），或分发前 version 未变 |
| 14 | 工具命名含糊（search、do_thing） | verb_noun + 前缀命名空间 | 工具名命中含糊词表（search / do_thing / handle / process），或缺 verb_noun 结构与前缀 |
| 15 | 长提示词=好结果 | 精简、模块化、策略性冗余关键指令；context rot：token 越多回忆精度越低，控正文体积是正确性要求不是洁癖 | 正文体积已超预算仍继续追加段落；或同一关键指令在正文里被完整重复 2 次以上 |
| 16 | 工具技能不自检 | 用自身方法论对自身跑一遍（清单/预检/触发词/体积预算） | 发布前找不到自检脚本的运行输出留痕（清单 / 预检 / 触发词 / 体积预算任一项） |
| 17 | 硬编码文件名列表（个人实战①） | 目录自动扫描 + 正则提取编号/年份 | 脚本里出现字面文件名数组，目录新增一个文件就要改代码 |
| 18 | 正则缺边界致误报（个人实战②） | 加数字边界 `(?<![0-9])…(?![0-9])` + 校验器（MOD11-2/Luhn/GB32100） | 用该正则扫全量数据，出现把长串中的子串或四位数年份误判为目标的现象 |
| 19 | 硬编码铁律不容偏离（个人实战③） | 固化是「可更新指南」非不可置疑：SKILL.md 必带逃逸条款（冲突时优先用户意图+显式留痕/降级人工），见编写规范 §三 | 正文通篇 MUST / NEVER，而 Constraints 节里找不到逃逸条款 |
| 20 | 探索型/发散型任务写死流程（个人实战④） | 按任务类型定指令强度：确定性流程才写死 Steps；探索/发散任务只给方向与约束，不写死步骤 | 技能面向「分析 / 诊断 / 创作」类开放任务，正文却给出编号固定的 1-2-3-4 步骤 |
| 21 | 封闭白名单 / 词表 / 默认值用于**跨对象判定**（把本技能的参数当通用基准） | 判定对象参数化；无外部输入时输出 REVIEW（退出码 2），不得判 FAIL。白名单只用于"命中已知风险"，不用于"未命中即不合格"；覆盖词表/默认参数/匹配规则三种形态 | 无外部输入时输出 FAIL 而不是 REVIEW（退出码 2） |
| 22 | 自建门禁严于目标平台要求（甚至同一文件内两个规则集打架） | 区分「平台阻断项」与「规范建议项」，后者降 warning，`--strict` 兜底；验证器过严会误杀正确行为 | 平台不阻断的行为被本工具判 FAIL；或同一文件内两条规则对同一行为给出相反结论 |
| 23 | 立规者未自守（规范只约束被指导对象，不约束自身） | 规范落地时同步对自身执行一次 | 新增规则在 references/ 有对应条目，而同名关键词在自身正文里 0 命中 |
| 24 | 过早宣布完成（未达成就标完成） | 完成前按验收清单逐条实测，不靠"应该没问题" | 状态标为完成时，验收清单里仍有未勾选项 |
| 25 | 环境遗留缺陷无文档（已知问题只存在于口头/记忆） | 发现即落盘，标注影响面与规避方式 | 已知问题全库检索 0 命中，只存在于会话记录或口头交代里 |
| 26 | 未做端到端验证就标完成 | 先跑通端到端，再补分层测试 | 只有单元测试通过记录，找不到端到端用例的运行输出 |
| 27 | 按表面形式 / 固定路径评分，而非按产物语义评分 | 评"结果对不对"，不评"走了哪几步"；不 rigid 检查固定模式 | 评分代码断言固定文件名或固定步骤序号，而不校验产物内容 |
| 28 | 判定缺 Unknown 出口（二值判定，无法表达"需人工确认/无数据"） | 三值：PASS / FAIL / REVIEW；无数据一律 REVIEW，不判 FAIL | 判定函数的返回类型只有布尔两值，无第三态 |
| 29 | 评分可被 cheat（如子串命中即通过，无防作弊） | 加产物级校验；重要用例改用人工评分 | 构造一个只含关键词、不含实际产物的输入即可拿满分 |
| 30 | 内容名实不符（描述说做 A，实际行为是 B，或夹带恶意 / 利用性代码） | 行为与描述逐项对应；描述里未提及的行为一律删除；不含任何恶意 / 利用性代码 | 描述称「只读 / 仅本地」，代码里却有写盘、外发请求或下载执行；或描述未提及的能力出现在代码中 |

> 注：#30 与「脱敏」是两个独立维度——脱敏管「数据是否敏感」，#30 管「行为是否如描述所言」，两者互不替代；#30 的判据可作为内容安全扫描中「恶意」档位的判定依据之一。

## 高频条目展开（命中率最高的 8 条）

### #2 description 模糊 —— 命门级
```text
反模式: "文档处理" / "Helps with documents"
正确:   "提取 PDF 表格转 CSV" / "创建带修订标记的 Word 文档用于法律审查"

双维度口径: 旧表述「功能 + 场景」中的「功能」指「能力标签（名词性）」，不是步骤摘要——
            双维度 = 能力标签（名词性）+ 触发场景。

流程摘要反例 vs 正例:
  ❌ "执行计划时逐任务派发子 agent 并在任务间做代码审查"
  ✅ "当在当前会话中执行含独立任务的实现计划时使用"

机理:   description 概括了流程，agent 就会走这条捷径，技能正文退化成没人读的文档。
        常驻上下文里只有 description，正文是按需加载的——description 一旦把结论说完，
        正文就失去了被读取的理由。
纪律:   只写「能力标签（名词性）+ 触发场景」，不写步骤序列、流程顺序、判定结论。

检验:   eval_trigger.py <技能目录> --desc-check
        （6 项静态校验分两级：FAIL 级 2 项 / WARN 级 4 项；WARN 默认只提示，
         --strict 才计入失败。「含流程摘要」即 WARN 4 项之一）
```

### #4 所有内容塞进一个文件
```text
反模式: SKILL.md 一个文件约 1.5 万字符，正文同时承担方法论+命令速查+清单+示例
正确:   L2 正文 <5000 token；清单/方法学/速查拆到 references/，按需加载
检验:   中文字数 × 1.0 + 非中文字符数 / 4（口径见 references/核心公式与量化基准.md §2）
自检:   python3 -c "import re;t=open('SKILL.md',encoding='utf-8').read();t=re.sub(r'^---\s*\n.*?\n---\s*\n','',t,count=1,flags=re.S);cn=len(re.findall(r'[\u4e00-\u9fff]',t));print(round(cn+(len(t)-cn)/4))"
口径:   体积一律按**字符数**计，禁止用「KB」——中文 UTF-8 为 3 字节/字，同一文件按字节读会虚高近 2 倍，跨人比对必然对不上
示例:   同一份正文 8,318 字符 / 16,088 字节 → 按上式 ≈ 4,586 token（字节:字符 ≈ 1.93）
```

### #7 确定性逻辑让模型「想」出来
```text
反模式: 让 LLM 心算/脑补校验码、日期计算、数据聚合
正确:   确定性计算/校验/排版写成脚本让 AI 运行；创作部分才交模型
```

### #9 不处理错误、返回裸字符串
```text
反模式: 接口失败返回 "" 或抛出笼统异常码，下游无从判断
正确:   {ok:false, error:{code, message, retryable}}；错误消息含问题定位+正确示例
详见:   references/错误处理与可靠性纪律.md（纪律 4/7）
```

### #17 硬编码文件名列表（个人实战①）
```text
反模式: FILENAMES = ["某季度表.xlsx", "另一季度表.xlsx", ...]——新增文件要改代码
正确:   目录自动扫描 + 正则提取：
    import re, glob
    files = sorted(glob.glob("data/*.xlsx"), key=lambda p: re.search(r"(\d{4})[-_]?Q[1-4]", p).group(0))
    # 脱敏 + 复用前提：新文件加入目录即自动纳入，无需改脚本
```

### #18 正则缺边界致误报（个人实战②）
```text
反模式: 手机号匹配 \d{11}——命中身份证里的 11 位连续数字；四位数年份被当价格/金额
正确:   加数字边界 + 校验器：
    import re
    PHONE = re.compile(r"(?<![0-9])1[3-9]\d{9}(?![0-9])")   # 前后非数字
    def is_valid_phone(s):
        return bool(PHONE.match(s)) and s[1] in "3456789"   # 再加号段/校验器兜底
    # 同法：身份证 MOD11-2 校验码、银行卡 Luhn、统一社会信用代码 GB32100 校验器
```

### #19 硬编码铁律不容偏离（个人实战③）
```text
反模式: SKILL.md 全是 MUST/NEVER 且无出口——用户意图与规范冲突时模型要么硬撞要么静默偏离，
        固化反过来限制了 agent 的判断力
正确:   ① Constraints 节必带「逃逸条款」：冲突时优先保障用户数据与意图 + 显式说明偏离理由
            与替代动作（偏离留痕，必要时降级人工）；
        ② 固化是「可更新指南」：版本治理里标注失效触发条件（见 知识分层与版本治理.md §三）
```

### #20 探索型/发散型任务写死流程（个人实战④）
```text
反模式: 给"帮我分析这份数据有什么规律"类开放任务写成 1234 固定步骤——把探索压成流水线，丢失发散空间
正确:   先判任务类型：确定性/流程型（发布、转换、校验）→ 写死 Steps + 完整命令；
        探索型/发散型（分析、创作、诊断）→ 只给目标、约束、质量门槛与工具清单，步骤留给模型
```

## 堵漏机制（事后清单）

30 条是**事前**清单（写之前扫一遍）；本节是**事后**机制——从实测里收集模型的实际借口，反写成对照表，再重测。两者是姊妹：事前预防，事后补漏。

### 合理解释对照表

逐条来自 baseline 实测：左边是模型的原话借口，右边是这句话为什么不成立。

| 借口 | 现实 |
|---|---|
| "太简单了不用测" | 简单的代码也会坏。测一次 30 秒。 |
| "我写完再补测试" | 测试立刻通过证明不了任何事。 |
| "事后补测效果一样" | 事后测问「这段代码做了什么」；先测问「这段应该做什么」。 |

### 生成流程

1. **跑 baseline**——用真实 prompt 让模型在无指导条件下做一遍，全程留 transcript。
2. **逐条记录模型的原话借口**——不要转述、不要归类、不要替它润色。原话才有措辞力度；一归类就丢掉了具体托辞。
3. **反写成表**——左列原话借口，右列对应的现实。一条借口配一句反驳，不合并、不抽象。
4. **用同一批 prompt 重测**——看这些借口是否减少。
5. **仍出现的借口说明对照表没写到位**——回到第 3 步重写它的反驳，而不是再加一条新规则。

### 红旗清单（自我合理化自查）

模型准备绕开规则时，出现以下念头即为红旗：

`代码先于测试 / "我已经手工测过了" / "这是精神不是仪式" / "这次不一样因为…"`

→ 以上全部意味着：**删掉，重来**。

### 「无例外」清单（堵死绕道）

把规则的绕道逐个堵死：

`不要留作「参考」/ 不要在写测试时「顺手改一下」/ 不要看它 / 删就是删`

### 前置原则

`Violating the letter of the rules is violating the spirit of the rules.`——字面都没守，就谈不上守住精神。一句话切断一整类「我遵循的是精神」的辩解。

### 适用边界（必须与上面一起写）

⚠️ 这套「禁令 + 对照表 + 红旗」**只对纪律型失败有效**——即「知道规则、有压力时仍违反」。

对「输出形状不对」（啰嗦、结论被埋、复述需求）或「漏了必备元素」这两类，禁令式加固会**反效果**：这两类要用**正向配方 / 结构化槽位**（见 `references/SKILL.md 编写规范.md`「按失败类型选形式」），而不是再加一条禁令。不写这条限定，本节就会与编写规范打架——同一个问题被两套相反的处方治。

### 与调试三步法的衔接

本节的生成流程（跑 baseline → 记录原话借口 → 反写成表 → 重测）与 `references/调试三步法.md` 天然衔接：调试三步法负责把「哪一步塌了」定位出来，本节负责把定位出的失效**固化成下次不会再犯的对照表**。

## 铁律（跨条目通用，不占总表编号）

**代码是唯一事实源**：文档里写了什么不算数，脚本实际做什么才算数。改脚本必同步改文档，改文档必回验脚本；发现不一致时**以代码为准修文档**，并显式标注「当前未实现 / 待实现」，而不是把没做的写成已做。

- 触发时机：写 references/ 中任何描述脚本行为的段落、改 scripts/ 之后、发布前自检
- 反面实例：文档写「脚本会自动检查用例数是否足够」，而脚本 verdict 只看均分 → 使用者按文档信任，实际无人兜底
