## 总表（30 条）

> 每条写成三元组：`NEVER <动作>` + **后果** + `改为 <动作>`，右侧附可观测判据。前三项回答「别做什么 / 做了会怎样 / 该怎么做」，判据供发布前逐条实测。

| # | NEVER（反模式） | 后果 | 改为（正确做法） | 可观测判据 |
|---|---|---|---|---|
| 1 | NEVER 跳过需求分析直接开发 | 正文没有可信蓝本，写完才发现跑不通，返工重写 | 示例驱动设计：先写一个**能跑通的完整示例**，再照它写正文 | 技能目录里找不到「使用示例」小节，或仅有的示例是截断片段 / 跑不通（**数量不参与判定**——一个完整示例即达标，"三个示例"里有截断的不达标） |
| 2 | NEVER 把 description 写得模糊 | 模型无法语义匹配，技能要么不触发、要么乱触发 | 能力标签（名词性）+ 触发场景双维度：动作动词 + 具体文件类型/领域；不写步骤序列 | `--desc-check` 的 FAIL 级项命中；或 description 里出现「然后 / 接着 / 第一步」这类步骤连接词 |

| 9 | NEVER 不处理错误、返回裸字符串 | 调用方拿不到错误码，无从判断失败能否重试 | 统一错误信封 + is_error + 可读消息 | 失败路径返回空字符串 / None / 纯消息，调用方拿不到错误码 |
| 10 | NEVER 写操作不做幂等 | 超时重试重复写入、重复扣减，数据静默污染 | 幂等键 + 缓存结果 | 同一请求连发两次，第二次仍新建记录或重复扣减 |
| 11 | NEVER 堆功能不修指令 | 指令与行为脱节，正文逐渐失真 | 先修指令再叠功能 | 一次改动里新增了功能，而正文指令段未同步改动 |
| 12 | NEVER 一个会话干所有任务 | 上下文污染，后一任务带着前一任务的字段与临时路径 | 一个任务一个会话，防上下文污染；one-shot 贪多留半成品 | 会话里后一任务的产物中出现前一任务的字段名或临时路径 |

| 16 | NEVER 工具技能不自检 | 自身违反自己的规范，规则失去公信力 | 用自身方法论对自身跑一遍（清单/预检/触发词/体积预算） | 发布前找不到自检脚本的运行输出留痕（清单 / 预检 / 触发词 / 体积预算任一项） |

| 18 | NEVER 正则缺边界致误报（个人实战②） | 把长串中的子串或四位数年份误判为目标，产生假阳性 | 加数字边界 `(?<![0-9])…(?![0-9])` + 校验器（MOD11-2/Luhn/GB32100） | 用该正则扫全量数据，出现把长串中的子串或四位数年份误判为目标的现象 |

| 21 | NEVER 把本技能的封闭白名单 / 词表 / 默认值用于**跨对象判定** | 域外对象被误判不合格，正确写法遭误杀 | 判定对象参数化；无外部输入时输出 REVIEW（退出码 2），不得判 FAIL。白名单只用于"命中已知风险"，不用于"未命中即不合格"；覆盖词表/默认参数/匹配规则三种形态 | 无外部输入时输出 FAIL 而不是 REVIEW（退出码 2） |

| 23 | NEVER 立规者不自守 | 规则只约束被指导对象，自身违规却无人查 | 规范落地时同步对自身执行一次 | 新增规则在 references/ 有对应条目，而同名关键词在自身正文里 0 命中 |
| 24 | NEVER 过早宣布完成（未达成就标完成） | 未验证即标完成，缺陷留到下游才暴露 | 完成前按验收清单逐条实测，不靠"应该没问题" | 状态标为完成时，验收清单里仍有未勾选项 |
| 25 | NEVER 环境遗留缺陷不落盘 | 已知问题只存在于口头/记忆，换人即丢 | 发现即落盘，标注影响面与规避方式 | 已知问题全库检索 0 命中，只存在于会话记录或口头交代里 |
| 26 | NEVER 未做端到端验证就标完成 | 单元测试过了，真实链路仍不通 | 先跑通端到端，再补分层测试 | 只有单元测试通过记录，找不到端到端用例的运行输出 |
| 27 | NEVER 按表面形式 / 固定路径评分 | 产物内容错但形式对，照样拿高分 | 按产物语义评分：评"结果对不对"，不评"走了哪几步"；不 rigid 检查固定模式 | 评分代码断言固定文件名或固定步骤序号，而不校验产物内容 |
| 28 | NEVER 判定缺 Unknown 出口（二值判定） | 无数据被当成不合格，误伤正确写法 | 三值：PASS / FAIL / REVIEW；无数据一律 REVIEW，不判 FAIL | 判定函数的返回类型只有布尔两值，无第三态 |
| 29 | NEVER 让评分可被 cheat | 只含关键词、不含实际产物的输入即可拿满分 | 加产物级校验；重要用例改用人工评分 | 构造一个只含关键词、不含实际产物的输入即可拿满分 |
| 30 | NEVER 内容名实不符 | 描述说做 A、实际行为是 B，甚至夹带恶意 / 利用性代码 | 行为与描述逐项对应；描述里未提及的行为一律删除；不含任何恶意 / 利用性代码 | 描述称「只读 / 仅本地」，代码里却有写盘、外发请求或下载执行；或描述未提及的能力出现在代码中 |

> 注：#30 与「脱敏」是两个独立维度——脱敏管「数据是否敏感」，#30 管「行为是否如描述所言」，两者互不替代；#30 的判据可作为内容安全扫描中「恶意」档位的判定依据之一。

### #2 description 模糊
```text
机理:   description 把结论说完，正文就失去了被读取的理由（常驻上下文里只有 description，正文按需加载）。
双维度: 「功能 + 场景」中的「功能」= 能力标签（名词性），不是步骤摘要。
流程摘要反例 vs 正例:
  ❌ "执行计划时逐任务派发子 agent 并在任务间做代码审查"
  ✅ "当在当前会话中执行含独立任务的实现计划时使用"
检验:   eval_trigger.py <技能目录> --desc-check（7 项分两级：FAIL 2 / WARN 5，WARN 默认只提示）
```

### #4 所有内容塞进一个文件
```text
口径:   体积一律按 token 计，禁用「KB」——中文 UTF-8 为 3 字节/字，按字节读会虚高近 2 倍，跨人比对必然对不上。
自检:   python3 -c "import re;t=open('SKILL.md',encoding='utf-8').read();t=re.sub(r'^---\s*\n.*?\n---\s*\n','',t,count=1,flags=re.S);cn=len(re.findall(r'[\u4e00-\u9fff]',t));print(round(cn+(len(t)-cn)/4))"
示例:   同一份正文 8,318 字符 / 16,088 字节 → ≈ 4,586 token（字节:字符 ≈ 1.93）
```

### #7 确定性逻辑让模型「想」出来
```text
正确:   确定性计算 / 校验 / 排版写成脚本让 AI 运行；创作部分才交模型。
```

### #9 不处理错误、返回裸字符串

正确:   {ok:false, error:{code, message, retryable}}；错误消息含问题定位 + 正确示例。

## 堵漏机制（事后清单）

30 条是**事前**清单（写之前扫一遍）；本节是**事后**机制——从实测里收集模型的实际借口，反写成对照表，再重测。两者是姊妹：事前预防，事后补漏。

### 合理解释对照表

逐条来自 baseline 实测：左边是模型的原话借口，右边是这句话为什么不成立。

| 借口 | 现实 |
|---|---|
| "太简单了不用测" | 简单的代码也会坏。测一次 30 秒。 |
| "我写完再补测试" | 测试立刻通过证明不了任何事。 |
| "事后补测效果一样" | 事后测问「这段代码做了什么」；先测问「这段应该做什么」。 |

### 生成流程

1. **跑 baseline**——用真实 prompt 让模型在无指导条件下做一遍，全程留 transcript。
2. **逐条记录模型的原话借口**——不要转述、不要归类、不要替它润色。原话才有措辞力度；一归类就丢掉了具体托辞。
3. **反写成表**——左列原话借口，右列对应的现实。一条借口配一句反驳，不合并、不抽象。
4. **用同一批 prompt 重测**——看这些借口是否减少。
5. **仍出现的借口说明对照表没写到位**——回到第 3 步重写它的反驳，而不是再加一条新规则。

### 红旗清单（自我合理化自查）

模型准备绕开规则时，出现以下念头即为红旗：

`代码先于测试 / "我已经手工测过了" / "这是精神不是仪式" / "这次不一样因为…"`

→ 以上全部意味着：**删掉，重来**。

### 「无例外」清单（堵死绕道）

把规则的绕道逐个堵死：

`不要留作「参考」/ 不要在写测试时「顺手改一下」/ 不要看它 / 删就是删`

### 前置原则

`Violating the letter of the rules is violating the spirit of the rules.`——字面都没守，就谈不上守住精神。一句话切断一整类「我遵循的是精神」的辩解。

### 适用边界（必须与上面一起写）

⚠️ 这套「禁令 + 对照表 + 红旗」**只对纪律型失败有效**——即「知道规则、有压力时仍违反」。

对「输出形状不对」（啰嗦、结论被埋、复述需求）或「漏了必备元素」这两类，禁令式加固会**反效果**：这两类要用**正向配方 / 结构化槽位**（见 `references/SKILL.md编写规范.md`「按失败类型选形式」），而不是再加一条禁令。不写这条限定，本节就会与编写规范打架——同一个问题被两套相反的处方治。

### 与调试三步法的衔接

本节的生成流程（跑 baseline → 记录原话借口 → 反写成表 → 重测）与 `references/调试三步法.md` 天然衔接：调试三步法负责把「哪一步塌了」定位出来，本节负责把定位出的失效**固化成下次不会再犯的对照表**。

## 铁律（跨条目通用，不占总表编号）

**以脚本实际行为为准**：文档里写了什么不算数，脚本实际做什么才算数。改脚本必同步改文档，改文档必回验脚本；发现不一致时**以脚本实际行为为准改文档**，并显式标注「未实现」，而不是把没做的写成已做。

- 触发时机：写 references/ 中任何描述脚本行为的段落、改 scripts/ 之后、发布前自检
- 反面实例：文档写「脚本会自动检查用例数是否足够」，而脚本 verdict 只看均分 → 使用者按文档信任，实际无人兜底

## 正文论证与同义反复（写作面，判据可观测）

> 与候选池 #40（正文不留会漂的数值）是姊妹条：#40 管**数字**会漂，本条管**论证**会胀。二者常同时出现。

**判据（命中任一即改）**：

- **为设计选择辩护**：出现「为什么这样设计」「换来两件事」「比 X 更有说服力」这类段落 ⇒ 压成一句「因何而定」，或删。
- **同义反复**：同一句道理在同文件出现 ≥2 次（含「换言之」「也就是说」后接同一结论）⇒ 只留一处。
- **一句话写成一段**：一个判据用了 3 句以上铺陈动机、背景、类比 ⇒ 只留判据本身。
- **口语句收尾**：以「才是」「就是这一条」「都是玄学」这类口号收尾 ⇒ 删（它不提供判据）。

**允许保留（不算论证）**：说清「不这样做会坏成什么样」或「防止哪种误读」的一句因由；类比的**判据面**（如「看什么真的难抄，不是看起来像核心资产」）；反例的后果。

**改法**：把「为什么这个设计好」改写成「不这样会怎样」——前者是说服，后者是可迁移的因由。

**自查命令**：

```bash
grep -nE "^\*\*为什么|换言之|也就是说|才是|有说服力|换来" references/*.md
```
