# 核心公式与量化基准

> 来源：11 条主基准（社区共识 + 个人实战提纯），另附工具参数基准（skill-dev-kit 内置脚本默认值）。
> 定位：开发/评审技能时的**可度量参照系**——每条基准都是改进的锚点：超标即整改，达标才发布。
> 来源标注口径：**个人实战**（多个技能开发实测）/ **社区共识**（51 篇社区资料核验）/ **官方**（Agent Skills 官方规范与平台官方文档）。

## 1. 十一条主基准

| # | 基准 | 值 | 来源 |
|---|---|---|---|
| 1 | 固化判定 | 可复用 × 多步骤（≥8 步） × 有踩坑教训 | 个人实战 |
| 2 | 触发阈值 | 简单单步不触发、复杂多步必触发 | 社区共识 |
| 3 | L1 元数据预算 | description ≈100 token（常驻） | 官方 |
| 4 | L2 正文预算 | SKILL.md 正文 <5000 token（**硬上限**，触发后加载）；**目标值 ~2000 token**——优秀实践的中位数水平（样本中位数 1,878 token），只有官方线的约 38%；口径与自检命令见 §2，任何口径下都不放宽此预算 | 官方 |
| 5 | 工具输出预算 | <2–4k tokens/次（防上下文膨胀） | 社区共识 |
| 6 | 活跃工具数 | <20 个/调用，最佳 5–10 | 社区共识 |
| 7 | 可靠性数学 | 99%×8 步≈92%；25 步+工具调用 <70% | 社区共识 |
| 8 | Token 降本 | 四条纪律可压缩 50–60%；量化驱动单家降 80% | 个人实战 |
| 9 | 结构化输出收益 | 消除约 80% 生产问题；挽回约 85% 畸形输出 | 社区共识 |
| 10 | 触发率测试 | 60/40 切分（60% 应触发 / 40% 不应触发） | 社区共识 |
| 11 | 超支复盘线 | 阶段实际超预估 30% 即强制复盘，不得继续 | 个人实战 |

## 2. 速记公式（可直接套用）

```text
可靠性:  R(steps) = per_step^steps            # 99%^8≈92%、99%^25≈78%、97%^25≈47%
降本:     小样本先行 + 输出压缩 + 子代理隔离 + 验证收敛 ≈ 压缩 50–60%
L2 预算:  正文 token ≈ 中文字数 × 1.0 + 非中文字符数 / 4
          目标值锚点: ~2000 token（优秀实践中位数 1,878）；<5000 token 为硬上限
          ⚠️ 骨架是上限不是下限——官方最小骨架正文仅 7 token，五要素 + 生产骨架不是必须填满的配额
          （中文 UTF-8 = 3 字节/字，1 字 ≈ 1 token；西文 ≈4 字符/token；误差带 ±10%）
          ⚠️ 自检命令必须**先剔掉 frontmatter**——含 frontmatter 会虚高数百 token，
             拿不带剔除的版本去比，会把达标文件误报成超线：
          自检: python3 -c "import re;t=open('SKILL.md',encoding='utf-8').read();t=re.sub(r'^---\s*\n.*?\n---\s*\n','',t,count=1,flags=re.S);cn=len(re.findall(r'[\u4e00-\u9fff]',t));print(round(cn+(len(t)-cn)/4))"
          ⚠️ 同一文件用**含 frontmatter**的旧口径会凭空多算数百 token，足以把达标文件误报成超线。
             `preflight_release.py` 已内置同一口径的核算，不必手工换算。
          ⚠️ 已废弃的旧口径「按字节数除以 4 估中文 token」是错的：中文 3 字节/字，用 /4 会低估约 33%，
             照它测会得出"余量还很宽"的假象，直到某天突然破线。全文唯一口径即上面这行。
          ⚠️ 目标值 ~2000 是**形态中位数**，不是所有技能的达标线：「清单 + 流程 + 索引」型工具包
             （正文要常载检查清单、发布流程与参考索引）天然更厚。这类技能守**硬上限 + 不重复转述**
             两条即可，不要为凑目标值把正文拆散进 references——那与「能内联就内联」直接冲突。
结构化:   schema 约束输出 → 消除 ~80% 生产问题；校验器 → 挽回 ~85% 畸形输出
触发率:   测试集 60/40 切分，达标阈值 0.7（见 §3）
```

## 3. 工具参数基准（skill-dev-kit 内置默认值）

> 技能自身脚本的默认阈值，评审时直接引用，避免「拍脑袋」参数。

| 参数 | 默认值 | 载体 |
|---|---|---|
| 触发覆盖率阈值 | 0.7；**无评估集 → 退出码 2（REVIEW），不判 FAIL**（0–1.0 可调） | eval_trigger.py `--threshold` |
| 评测均分 PASS 线 | ≥0.7 PASS(0) / <0.7 REVIEW(2) / 无数据 NO-DATA(2)；**REVIEW 不等于通过** | eval_loop.py |
| 描述质量门禁 | 分两级：**FAIL 级 2 项**（自称构式 / 无动作动词）命中即不合格；**WARN 级 4 项**（缺场景或文件类型 / 含 how 描述 / 缺排他边界 / **含流程摘要**，即出现「先…再…」「第 N 步」「step 1/2/3」这类步骤序列标记）默认只提示，`--strict` 才计入失败 | eval_trigger.py `--desc-check` |
| 留出集比例 | `--holdout`：默认 0（关闭），推荐 0.4；判定以留出集覆盖率为准，留出集不足 1 条降级 REVIEW | eval_trigger.py --holdout |
| 重复采样次数 | `--reps`：默认 1，推荐 3；重复 N 次独立留出切分，输出覆盖率均值 ± 标准差；偏大说明评估集切分不稳，对策是扩量而非调措辞 | eval_trigger.py --reps |
| 预检退出码 | 0=PASS（可含告警）/ 1=FAIL（高危禁止发布） | preflight_release.py |
| 打包体积上限 | ≤10MB；自动版本命名；默认排除 LICENSE | make_skillhub_zip.py |
| 自合规自检（v1.1 新增） | 技能本体跑自身方法论全套（体积/触发词/预检/清单） | skill-dev-kit 自身实证 |

> ⚠️ **边界说明**：在静态工具的口径下，`--reps` 衡量的是**评估集切分稳定性**，不是模型随机性；「同一条 query 跑 N 次求稳定触发率」需要真实调用通道，**当前未实现**。

## 4. 使用方式（什么时候查）

- **写 description 时**：对照 #2/#3——双维度 + ≈100 token。
- **写 SKILL.md 时**：对照 #4——正文 **目标 ~2000 token、硬上限 <5000 token**，超了拆 references。
- **设计工具/函数时**：对照 #5/#6——输出 <2–4k、活跃工具 <20。
- **编排多步流程时**：对照 #7——步数 >15 必须补校验点/重试/降级。
- **改进 token 消耗时**：对照 #8——先量化归因，再上纪律。
- **加输出解析时**：对照 #9——schema 约束，不解析自由文本。
- **测触发率时**：对照 #10 与 §3——60/40 切分 + 阈值 0.7。

## 5. Token 降本纪律（#8 详表）

> 来源：个人实战 ~1.2M tokens 消耗归因 + 技能开发实录，2026-08-24 资产化。
> 铁律：**先小样本验证，再全量执行；能落盘不回流，能结论不 dump。** 四条纪律叠加可压缩 50–60%。

### 5.1 消耗归因基准（先知道钱花哪了）

| 消耗项 | 占比 | 根因 | 对策 |
|---|---|---|---|
| 调试循环 | 28% | 改一行跑一遍、反复试错 | 小样本先行验证（纪律 1） |
| 大文件反复读取 | 24% | 整文件 cat / 重复读同一大文件 | 输出压缩：head/tail/精准提取（纪律 2） |
| 代码写入 | 19% | 整段重写、反复覆盖 | 增量 Edit、避免整文件重写 |
| 上下文累积 | 17% | 中间产物长期挂在上下文不落盘 | 分阶段落盘、子代理隔离（纪律 3） |
| OCR 输出 + 图片 | 12% | 长 OCR 文本/截图反复进上下文 | 长文本 + 截图验证收敛（纪律 4） |

> 结论：**调试与重复读取占一半以上**——降本优先改「读」与「试」的方式，而不是压缩正文内容。

### 5.2 四条强制纪律（可压缩 50–60%）

1. **小样本先行验证（省 ~14%）**：解析/处理新格式前，先打印 1 页/1 条样本确认结构再全量。`head -5 大文件.csv`；全量前 `--sample 1` dry-run。
2. **输出压缩（省 ~15%）**：调试统一 `head/tail`、`python -c` 精准提取，**禁整文件 cat**；大文件只读需要的行段（`grep -n "ERROR" big.log | head -20`）。
3. **子代理隔离（省 ~22%）**：大文件读取/格式探测/耗时子任务交子代理，**主线程只收结论**，中间产物不回流上下文。
4. **验证收敛（省 ~5%）**：中间迭代用 DOM/JS/文本断言验证，**截图仅最终一次**；长任务分阶段落盘，不把中间产物留在上下文。

### 5.3 量化驱动优化（每轮改进都要算账）

**没有量化的降本都是玄学**。某批量化查询技能实测（案例档案留个人工作区，此处仅保留可复用归因数据）：

| 轮次 | 单家消耗 | 优化动作 | 降幅 |
|---|---|---|---|
| 初始 | 61.5k | — | — |
| 第 1 轮 | 35.4k | 识别「检索 45%」高消耗 → 合并重复检索 | -42% |
| 第 2 轮 | 12.5k | 识别「迭代 20k」→ 分阶段落盘 + 子代理隔离 | -65% |
| 累计 | — | 量化驱动，逐步收敛 | **-80%** |

度量方法（零依赖）：中文≈1 token/字、英文≈1 token/4 字符粗估；每轮记录输入侧（读取字节）+ 输出侧（打印字节），对比优化前后趋势。

### 5.4 降本自查清单（任务收尾前过一遍）

- [ ] 新格式先打印 1 条样本确认结构？
- [ ] 全程无 `cat` 大文件、无整段重复输出？
- [ ] 大文件读取/格式探测交子代理或落盘，中间产物未回流？
- [ ] 截图/长文本只在最终阶段输出一次？
- [ ] 长任务中间产物已写文件，下阶段从文件续读？
- [ ] 代码用增量 Edit，未整文件反复重写？
- [ ] 本轮消耗较上轮有记录、有对比、有结论？

> 每 3–4 个「否」就值得停下来重排执行方式——收益大头在**执行的第一次就做对**。

## 6. Token 预算治理

> 定位：§5 管「单条命令怎么省」，本节管「总量别失控」——实际超支多是阶段失控，不是某条命令不够省。
> 铁律：**先预算、后执行；每阶段回填；超 30% 强制复盘。**

### 6.1 阶段预算表（开工填预估，收工回填）

| 阶段 | 预估 token | 实际回填 | 超支率 | 处置 |
|---|---|---|---|---|
| 1 需求与字段契约对齐 | 8k | 11k | +38% | 超线，复盘：契约未前置确认 |

> 结论：**没有预估就没有超支**。

### 6.2 超支复盘线 30%（对应 #11）

- 阶段实际超预估 **≥30% → 强制复盘根因，不得继续烧**。
- 复盘只答三问：花在哪一项（对照 §5.1）、能否落盘不回流、下一步还该不该这么走。
- **先复盘、后续做**：结论出来前不启动下一阶段；通过 → 按原范围续做，不通过 → 按 6.3 调范围。

### 6.3 续接决策矩阵

| 超支率 | 判定 | 动作 |
|---|---|---|
| <30% | 正常波动 | 直接续做，沿用原预算 |
| ≥30% | **复盘触发线** | 先复盘；通过 → 按原范围续做，不通过 → 按下一行处理 |
| 30–60% | 范围偏大 | 降级范围（砍非必要阶段 / 降样本量）后续做 |
| >60% | 预估失效 | 止损重规划：回需求重排阶段与目标，不续烧 |

> 结论：**30% 是复盘触发线，不是范围调整线**——触发的是「停下来想清楚」，不是「自动缩范围」。

### 6.4 三条「必超支」场景（开工前先自检）

| 场景 | 典型表现 | 预防 |
|---|---|---|
| ① 字段契约未对齐 | 反复试错对齐字段名/类型，一轮改一次 | 先打 1 条样本确认契约再全量（纪律 1） |
| ② 只读摘要松懈 | 大文件整段读进上下文 | 输出压缩（纪律 2）：只读需要的行段 |
| ③ API 降级返工 | 接口不稳导致整阶段重跑 | 小样本先行 + 响应落盘，重跑只补失败段 |

> 共同点：**都是「第一次没做对」**。

### 6.5 链条步数与阶段划分

按本技能 §八 标注，发布链条约 30 个原子步；按基准 #7 串联可靠性随步数衰减，**建议阶段数控制在个位数（经验取 ≤5）**，每阶段单独预算。
> 口径：#7 只给出步数—可靠性衰减关系，未指定阶段数；≤5 为经验取值，非基准指标。

**token 计算口径见 §2**（中文 1 字≈1 token、西文≈4 字符/token，误差 ±10%）。
