# 调试三步法 + 迭代四步法（技能上线后的活诊断与长期演进）

> **本文件目录**（社区实践）：总览三类故障 ｜ 第一步 未触发 ｜ 第二步 执行不一致 ｜ 第三步 输出异常 ｜ 附 迭代四步法 ｜ 速查卡

> 与 `references/发布检查清单.md`「踩坑表」互补——踩坑表是「已经踩过的坑」，本文件是「当下发生了什么」的活诊断。
> 适用：技能已发布但「没触发 / 乱做 / 输出不对」时，30 秒内定位到本文件照做；**没故障时的长期演进见文末「迭代四步法」（默认不执行，仅在用户明确要求做长期演进时人工执行）**。

---

## 总览：三类典型故障

| 症状 | 对应步 | 一句话判因 |
|---|---|---|
| 技能根本没被加载 | 第一步 | description 触发面太窄或格式错误 |
| 技能被加载但做错、脚本报错 | 第二步 | 正文指令特异性不足 / 脚本依赖路径权限问题 |
| 技能跑通但产物不对、格式乱 | 第三步 | 中间步骤歧义，缺调试钩子 |

---

## 第一步：未触发 → 拓宽 description

**症状**：用户说的是你预期内的场景，但技能静默、模型自己硬扛。

检查清单：

1. **场景覆盖**：description 是否含「功能 + 场景双维度」（动作动词 + 文件类型 + 场景）？只有「文档处理」这种泛词必死。
2. **排他边界**：是否写了「不做什么」？缺边界会导致模型认为「这不该我触发」。
3. **YAML 格式**：frontmatter 的 `description` 是否被引号误断行、是否含未转义特殊字符导致解析失败。
4. **任务复杂度**：简单单步任务本就不触发——这是**设计预期**，不是 bug（触发阈值见 `references/核心公式与量化基准.md` #2；测试方法见 `references/SKILL.md编写规范.md` §7.0）。

对策动作：
- 按 `references/SKILL.md编写规范.md` §七 五策略重写 description。
- 用 `eval_trigger.py --desc-check` 静态校验；用 `eval_trigger.py --check` 确认「## 触发词」章节覆盖率达标。
- 把「某 prompt 没触发」当**新测试用例**补进 evals（评估驱动的反哺）。

---

## 第二步：执行不一致 / 脚本报错 → 增强指令特异性

**症状**：技能触发了，但步骤跳步、用错工具、脚本退出非 0、路径/权限报错。

检查清单：

1. **指令特异性**：是否用了 MUST / NEVER / ALWAYS 编码强制与建议？含糊的「可以」「建议」模型会自由发挥。
2. **脚本依赖/路径/权限**：脚本是否自包含？是否把本机绝对路径（形如 `/Users/<账号>/…`）硬编码进去了、该改成环境变量？运行账号是否对目标目录有读/写权限？
3. **指令歧义**：同一动作是否出现多种表述？示例是否只是一段截断片段、跑不通（应补一个**能跑通的完整示例**——判据见 `references/SKILL.md编写规范.md` §四）？
4. **工具选择**：是否出现「选错工具」vs「选对工具但参数错」两个独立失败面——分开定位、分开修。

对策动作：
- 歧义步骤改为**模板模式 / 少样本示例**（判据：数量不参与判定、完整度才是，见 `references/SKILL.md编写规范.md` §四）。
- 脚本参数化：硬编码路径/账号 → 环境变量或命令行参数；硬编码文件名列表 → 目录自动扫描。
- 用 `eval_loop.py` 跑 case，看 grading.json 定位是「漏用规则」还是「参数错」。

---

## 第三步：输出异常 → 加临时调试模式

**症状**：流程跑完，但产物字段缺失、格式不对、顺序错乱。

检查清单：

1. **正文步骤歧义**：是否某步「读 A → 处理 → 写 B」的顺序没写清？
2. **结构化输出缺口**：复杂产物是否要求模型自由文本拼装（应改为 schema 约束，消除约 80% 生产问题）？
3. **验证缺口**：是否缺少「数量统计 + 逐条抽查 + 失败清单」三件套验收？

对策动作：
- **临时调试模式**：在正文插一段「先输出 [路径/格式/步骤清单] 再执行」的调试指令，定位断点；确认后移除。
- 关键产物加**结构化校验**（Pydantic/Zod / 正则校验器），解析失败即显式失败，不静默继续。
- 补「错误路径」用例——错误输入必须被拦截（参考 SKILL.md §五 五层测试闭环）。

## 附：迭代四步法（长期演进，不是故障急救）

> **与上面三步法的关系**：三步法管「当下故障怎么定位」，四步法管「没有故障时怎么持续变好」——只做前者，技能会停在「能用但别扭」的状态不再进步。

> ⚠️ **默认不执行**：本四步法的第 ③ 步依赖**执行记录（transcript）采集机制**；**没有该机制就拿不到这一步的数据**。按「**无数据不判 FAIL**、也不默认执行」的口径，**无该机制时不默认执行**——强行默认执行只会产出假信号。**适用范围**：仅在用户明确要求做长期演进时人工执行。

**① 原型**：先把流程跑通一版，不追求完备、不追求优雅。目标只有一个：有一条能端到端走完的路。

**② 综合评估**：跑评测、跑真实任务，把失败的地方和「能跑但别扭」的地方一起收集起来。评估集构建路线见 `references/评测方法论.md` §3。

**③ 读 transcript**：把模型的完整执行记录从头到尾读一遍。
- **这是唯一能发现「没做但本该做」与「做了但很别扭」的手段**——只看最终产物与评分会以为一切正常。
- 读什么：它读错了哪个文件、绕了什么远路、在哪一步反复试错、哪些指令它其实忽略了。
- ⚠️ **前提**：需要 transcript 采集机制（会话记录／执行日志落盘）。**无该机制则该步无法自动取数**；**若要执行本方法，靠人工复盘会话记录来完成这一步**——机器取不到时，人才是数据源。但靠人工逐轮硬读，成本高、不可复现，无该机制时不作为默认动作。

**④ 一次性批量重构**：把 ②③ 收集到的所有问题**攒够一批一次性改完**，不要逐个修补。
- 逐个修补会留下不一致的中间态：改了 A 处的表述，B 处还留着旧说法，下次还得再改一遍。
- ⚠️ **与「最小侵入 patch」不是一回事，先判适用条件再选改造方式**：**已发布的稳定技能** → 最小侵入 patch（前置 hook、覆盖优先于重构），降低线上风险；**开发中的未发布技能** → 一次性批量重构。判定规则见 `references/SKILL.md编写规范.md` §八。

### 戒律：验证器过严会误杀正确行为

本步常见坑：把「验证器报错」当成「技能有错」，去改本来正确的东西。

- **实例**：description 里的「自称」检测规则若只按单字匹配，会把「我的订阅」这类口语触发词判为违规——但它恰恰是按编写规范写出来的正确写法，属误杀。**修法是把规则收窄为「自称构式」**（只有技能自称时才违规），而不是放宽阈值把真违规一起放过。
- **判据**：验证器报错时先问一句「被拦的这个，是不是其实是对的？」答案是「是」，要修的是**规则本身**，不是被拦的对象。
- 关联：`references/反模式清单.md` #21（跨对象判定未参数化）、#22（自建门禁严于目标平台要求）。

## 速查卡（贴墙版）

```
没触发  → description 太窄/格式错 → 重写(五策略) + --desc-check
做错/报错 → 指令含糊/脚本依赖 → MUST编码 + 参数化 + 少样本
输出错  → 步骤歧义/无校验 → 临时调试模式 + 结构化输出 + 错误路径拦截
长期演进 → 原型 → 综合评估 → 读 transcript → 攒够一批一次性批量重构
```
